# Notes for agents

- This repository runs Nintendo Switch games natively on Apple platforms, to play as they do on the console: the game's own code runs, rewritten only where Apple's kernel requires it (`dm/tools/patch_nso.py`), on a host that answers Horizon's SVCs and the SDK's services (`dm/host`) and implements NVN, Vulkan and NVIDIA's desktop OpenGL on Metal (`dm/gfx/nvn`, `dm/gfx/vk`, `dm/gfx/gl`). Every game in the [games table](dm/games/README.md#games) is playable, tested on the Mac or the iPhone (a Mac gameplay test is enough to count); the table links each game's note, `dm/games/<id>/README.md`. [README.md](README.md) is the player-facing page (games, packing, playing); [docs/development.md](docs/development.md) has the internals, the script's options, building by hand, prewarm lists and power.
- Before any work, read [docs/charter.md](docs/charter.md): the project's aim and priorities, the devices a change is judged on, what counts as a regression, the checks before starting (existing issues, pull requests and branches; the change's reach), how much a pull request must show for its reach and risk, and the rule for defaults every game gets ([docs/decisions.md](docs/decisions.md)).
- **Fetch the latest `main` and check for existing work before starting anything or filing an issue, every time:** pull requests and issues by game and area label (`gh pr list --label "game: <title ID>"`) and by title ID or name, active branches, recent commits to the same files ([06-dev-loop.md](docs/agents/06-dev-loop.md#0-before-you-start-existing-work-then-a-branch)). Build on it, or ask its author. **Make yours findable too:** a draft pull request early, the game's name and title ID in its title.
- Where to start:

Recipes (crash reports, lldb, probes, dumps) are in [05-debugging.md](docs/agents/05-debugging.md) |
  | A game that does not reach its frame loop | [03-bringup.md](docs/agents/03-bringup.md) (the run loop, reading the log), then the symptom index |

  | Work on one game, or a change to its profile | its note, `dm/games/<id>/README.md`, then [dm/games/README.md](dm/games/README.md) for the keys |

- Where a new finding goes, once: a fact about one game (its passes, shader keys, measurements, why its profile needs a key or a cut, its status) in that game's note, in the section it belongs to and marked current or resolved; a general mechanism (a host or tool change that holds for other games) as an entry in its `docs/reference/<subsystem>.md` section (Symptom, Cause, Fix, Found on with the game's note linked), then `python3 dm/tools/docs_symptoms.py` to update the symptom index, and a line under the game note's "Found on this game". Link to a finding instead of repeating it. Adding a game takes its note and its row in the games table. Once Mac gameplay testing passes, it joins README's gallery ([CONTRIBUTING.md](CONTRIBUTING.md)); testing milestones and remaining validation stay in the game note. This file changes only when a rule does; it states no game count (the games table is the count). `dm/tools/tests/test_docs.py` checks the links and anchors, the notes and their table rows, the symptom index, and the length of this file (1,500 words) and of each guide in `docs/agents` (6,000).
- Each game's constants and shader tables form a game profile in `dm/games/<id>/`, where `<id>` is the base game's title ID: `game.tsv` plus the tables (and `patches.py` when the rewriter has patches for its builds). Mario's profile is `010015100B514000`. Tools pick the profile with `DM_GAME`; `make -C dm/host` and `build_ipa.sh` pick it with `GAME`. There is no default game: set it every time (the tools stop and list the profiles otherwise). Put per-game values in the profile, not in code ([dm/games/README.md](dm/games/README.md)).
- Prefer general optimizations and fixes to game-specific rules. Performance (frame pacing, memory, power, load times) is a goal on every device, after correctness and no regressions; a gain on one class of Mac must not cost another ([charter](docs/charter.md#priorities)). First look for a change that holds for every game: Horizon / NVN / Vulkan semantics, or what the binary, its SDK version, its imports or its files show. Use a game-specific rule (a profile key, a rewriter cut, a build-ID gate, a per-game branch in the host) only when it is absolutely necessary, that is, when no general rule can do it.
- Find a bug's root cause and fix it there; do not just work around it. Before changing code, find why it happens: the faulting instruction and its decompilation, the value that went wrong and who wrote it, the Horizon / NVN / Vulkan / Metal semantics the host or the translator gets wrong. Then fix that place. A change that only hides the symptom (a stub, a skipped call, a clamp, a retry, a sleep or a longer timeout, a cache flush, a profile key that turns a feature off) is a workaround: use one only when the cause is known and lies where it cannot be fixed (the game's own code, which a rewriter cut changes deliberately, or a platform limit), or when the user asks for a stopgap. Then say so in the code comment and in the game note or reference entry: the cause, or what is still unknown, marked open.
- Per-build knowledge (rewriter cuts, observation gates, frame-step stubs, host code at fixed module addresses) is keyed by the NSO build ID: never let fixed addresses run on a build they were not found in ([06-dev-loop.md](docs/agents/06-dev-loop.md#9-per-build-knowledge)).
- To analyse or port **another** Switch title, first run `scripts/build_ipa_from_nsp.py` on its NSP folder. With no matching profile, it writes a survey to `<NSP folder>/<title ID>_survey/survey.md`, then a provisional profile guessed from the game files (`dm/games/profile_guess.py`; `<build folder>/profile/<title ID>/`; found by the tools through `DM_GAMES_DIR`), with a short heap check on the Mac when the game has virtual address memory, and a best-effort IPA that may not boot. Then follow [docs/agents](docs/agents/README.md) (extraction, binary survey, host bring-up, graphics specifics, debugging recipes; the [symptom index](docs/agents/symptoms.md) for each failure) and add a profile with its note.
- Scripts the user runs live in `scripts/` at the repository root. Each one runs from a terminal (non-zero exit on error). `build_ipa_from_nsp.py` also runs in Spyder (F5, configured by the settings block at its top; command-line options override those settings). Tools that only agents or other scripts call stay under `dm/`.
- Game files, keys and anything extracted from them live in the game's NSP folder, never in this repository and never in the home folder (it is nearly full): the work folder `<NSP folder>/<id>-work` for extraction, runs and analysis, beside the NSP script's `<id>_build/`. One tool venv serves every game (`<drive>/venv`); other large scratch data goes there too. Do not print key values.
- Language: everything is in English. Red log lines (something unimplemented or wrong) start with `[RED] `. Text that must match a game's own Chinese data is written as escapes (`"\xE8\xB5\xB7"`), never as characters.
- The shader translation chain has one version for every game (`DMSH_CHAIN` in `dm/gfx/nvn/dmsh_chain.h`): after changing a chain tool, run `dmsh_chain.py --header` and commit the header with the change, then rebuild each affected profile's shaders and the host ([06-dev-loop.md](docs/agents/06-dev-loop.md#8-the-shader-chain-version)).
- What a change must show grows with its reach and risk ([charter](docs/charter.md#pull-requests); judge the tier with [Which tier](docs/agents/06-dev-loop.md#which-tier) before starting): for the chain, host or tools, `regress.py impact` names the games it reaches and `scripts/regress.py check --games` runs those you have; its report, naming the games and why, goes into the PR ([06-dev-loop.md](docs/agents/06-dev-loop.md)).
- Measure on the device a claim is about and name it ([charter](docs/charter.md#devices)). The log's `GPU p50` is each frame's GPU span, idle gaps included, not busy time: judge whether the GPU or the CPU limits a frame from `DM_NVN_GPUPROF` busy time or an Instruments trace.
- Never work on your local `main`, which only mirrors `origin/main`: one effort per branch or worktree, from current `main` and merged back often: a game's bring-up and an optimization apart (docs go with the change they describe); a general fix found during a bring-up gets its own branch and pull request as soon as it works. Leave nothing uncommitted on `main`; name stashes, apply them by SHA, drop them once applied ([06-dev-loop.md](docs/agents/06-dev-loop.md#0-before-you-start-existing-work-then-a-branch)).
- Ask the user before anything long or destructive they did not ask for: a build or shader rebuild of more than a few minutes, a run that replaces an app they play, deleting build, work or game folders, changing their `env.txt` or launcher settings.
- iOS builds are unsigned IPAs that the user sideloads and tests; diagnostics come back as the app's `Documents/log.txt`. Do not sign or install builds on the user's devices.
- Commit only when asked, with `git -c user.name=seedds -c user.email=seedds@gmail.com commit`. Commit and pull request conventions (titles, `Front-ends:` lines): [CONTRIBUTING.md](CONTRIBUTING.md).

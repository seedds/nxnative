# SHIN MEGAMI TENSEI Ⅴ (`010063B012DC6000`)

Base game 1.0.0 (v0), SDK 9.3.1 (its own `sdk` build). ATLUS, Unreal Engine 4.23 (`++UE4+Release-4.23`): one pak with the shaders inline in the cooked packages, NVN, CRIWARE (ADX2 sound, Sofdec movies). Modules `main`, `subsdk0` (NintendoSDK_movie, which `main` imports from) and `sdk`. 60 fps (30 on the Switch) by the host's writes of Unreal's frame limits.

Status: plays on the iPhone 18 Pro Max (user: gameplay fine; IPA about 14.5 GB). On the Mac, a new game through the opening and the character naming to the first classroom (Jouin High School 2F) runs at 60 fps (frame time p50 16.7 ms) with no `[RED]` line. The iPhone build predates main's image-atomic changes (PR #178 and the native texture atomics).

## Frame rate

- **Current:** 60 fps (30 on the Switch). The game caps Unreal at 30 twice: its code sets `t.MaxFPS` 30 at run time (its config has no `t.MaxFPS` or `FrameRateLimit`; frame smoothing is off in `Engine/Config/Switch/SwitchEngine.ini`), and the engine's Switch device profile sets `rhi.syncinterval=2` (`BaseSwitchDeviceProfiles.ini`), the present interval 2 it asks for while `r.VSync=1` locks presents to vsync. The host writes 60 and 1 into the two console variables whenever the game sets them back; the rewriter finds them by their registered names, with no build ID ([Unreal's frame limit and present interval, found by name](../../../docs/reference/frame-rate.md#unreals-frame-limit-and-present-interval-found-by-name): registered at `main+0xc7ba64` and `main+0xbd00ac`; the TAutoConsoleVariable holds at +0x10 the pointer to its value, the game thread's copy then the render thread's, and the host writes both). `rhi.SyncInterval` 1 alone left it at 30.
- On the Mac the route from a new game to the classroom ran at frame time p50 16.7 ms at 60 fps and 33.3 ms at 30, at the game's own speed: the naming keyboard appeared at the same wall time at either rate. Unreal steps the game by the time that really passed.
- On the iPhone the GPU took 8–27 ms a frame at 30 fps, so busy scenes may fall back to 30. `DM_FPS_TARGET=30` (`Documents/env.txt`) or the settings screen's Frame rate keeps the game's own 30 and saves power.

## Memory

- `nninitStartup` (`main+0x1885750`) reserves the engine region with `AllocateAddressRegion`, 62 GB unless `-SwitchVirtualAddressSpaceSize=` (MB up to 4095) gives a size. This build allocates the region only when no size was given (`if (!size) { size = 62 GB; AllocateAddressRegion(&base, 62 GB); }`, `main+0x1885ae4`), so with the option alone the base stayed 0 and the engine's page allocator (`main+0x1872af0`) would have handed out [0, size). The default's path stores the size into a global of its own (`str x8, [x24, #0x650]`, `main+0x1885afc`), not the word after the base variable (`main+0x6abfcd0`), with x1 set from the same constant; the rewriter's region rule takes that store in its second pass and the host gives the region what the alias region has room for. The lazy initialisation at `main+0x1872a40` has the same test, but `nninitStartup` runs first and sets the size: [Unreal's engine address region and its options](../../../docs/reference/memory.md#unreals-engine-address-region-and-its-options). Until 2026-10-31 the port gave it 4064 MB with `game_args` and two cuts in a `patches.py` that let the option's path allocate.
- **Current: the allocator is the host's.** Its FMallocBinned3 would take 37 GB of the region (74 pools of 512 MB, pool index = offset >> 29; the alias region's high-water mark reached +38.5 GB of 64 GB at boot). `GCreateMalloc` mallocs 0x1c38 bytes on the first allocation and constructs them (`main+0x1713920` → `main+0x17098b0`), then stores GMalloc (`main+0x6abc8b8`). The rewriter's engine-wide rule (`ue_malloc.py`) finds the constructor from the `Binned3` name, its getter (slot 17 of the vtable) and the vtable's one constructor, cuts the call and puts the gate on it, where x0 is the object. It found the call this profile's own cut and gate (`main+0x1713928`, the store of GMalloc) were registered at until main's rule came. Nothing outside the allocator reads its pool base (`main+0x6a8f568`: every reference is in `main+0x170a0ec` … `+0x170e504`) or calls its methods directly (they are reached only through the vtable `main+0x57e6238`); the one call into its code from outside (`main+0x1872d70` → `+0x170aa50`) builds a bit tree in the caller's own object. UE 4.23's FMalloc has 18 slots, no `TryMalloc` / `TryRealloc` yet: [Unreal's FMallocBinned3 replaced by the host allocator](../../../docs/reference/memory.md#unreals-fmallocbinned3-replaced-by-the-host-allocator).
- **Current: a 4.06 GB region** (what the alias region has room for) with the SDK-wide rules' node-area and alignment cuts on this SDK 9.3.1 build (the AddressRegionManager constructor `sdk+0xd2230`, `VammManager::AllocateAddressRegion` `sdk+0xd2340`), in Engage's 5 GB block: the region starts 64 MB into the 4.375 GB alias region ([The SDK's address-region node area](../../../docs/reference/memory.md#the-sdks-address-region-node-area)). On the Mac from the opening to the first classroom, at 30 fps: the region mapped up to +1.25 GB (1.0 GB in use), the Unreal heap at 0.75 GB, a 2.9 GB footprint. On the iPhone: a 1.9 GB footprint in play.

## Rendering

- **Resolved: `[RED] MapVirtual: non-contiguous mapping (true sparse) not implemented`, a few hundred times.** Unreal's NVN RHI gives each streaming texture a virtual pool of its own (flags 0x2a1, 128 KB to a few MB, over a thousand by the opening) and maps it 64 KB page by page from some twenty physical pools, the first request often for a level past the pool's start. Pools that small kept the alias, so every request after the first that named another place failed. Every virtual pool now gets an address range of its own and its first mapping decides, as on OCTOPATH TRAVELER: [Virtual pools of one texture each, mapped before and after the texture](../../../docs/reference/nvn-objects.md#virtual-pools-of-one-texture-each-mapped-before-and-after-the-texture).
- **Resolved: Unreal's out-of-memory abort at boot** after a 0xffe00000-byte pool request: the RHI sizes a sparse texture's mip tail from `nvnTextureBuilderGetSparseTileLayout`, whose stub left a tiled level count past the texture's levels: [The sparse tile layout of a texture](../../../docs/reference/nvn-objects.md#the-sparse-tile-layout-of-a-texture).
- **Resolved: the whole picture black** in the classroom. The engine writes the classroom's 256x16 colour-grading LUT from the CPU into an ordinary pool after creating it; the LUT held its data in guest memory but read 0 on the host, so the tonemapper's LUT came out 0. Both `tex_flush_upload` and `tex_dirty_upload` are on: [CPU writes with no flush, caught by page protection](../../../docs/reference/nvn-objects.md#cpu-writes-with-no-flush-caught-by-page-protection-tex_dirty_upload).
- **Resolved: the classroom's walls in bright and dark patches.** Its 1024×1024 and 1024×512 DXT5 lightmaps are sparse textures with no packaged layout, read with the automatic block height (16 GOBs) and scrambled in 4-texel columns. With 8 GOBs, the block height of their 64 KB tile, the game's level 1 is its level 0 halved (mean difference of the blocks' first colour 23, against 139 or more with 16 in either level): [Sparse textures take the block height of their 64 KB tile](../../../docs/reference/rendering.md#sparse-textures-take-the-block-height-of-their-64-kb-tile).
- **Resolved: the naming cutscene green, then white** (every lit surface green from the cutscene's first frame, then the picture washed out). Unreal 4.23 captures its sky light again as the cutscene loads: it clears two 128×128 scratch cubes, every face and level, to (0, 10000, 0, 0) (`ClearScratchCubemaps`' "noticeable value"), draws each face of the source cube into them and projects the result to spherical harmonics, the sky irradiance every lit pixel reads (`SkyIrradianceEnvironmentMap` in the View uniform buffer). Face 0 kept the clear's green: its draw ran under the 1×1 scissor of the last level cleared, though the game had set 128×128 before it. The prewarm list is empty, so pipelines are built on demand, and the precompile look-ahead lost the scissor, the bug first found on OCTOPATH TRAVELER II: [The precompile look-ahead restores the scissor](../../../docs/reference/shaders.md#the-precompile-look-ahead-restores-the-scissor). Comparing each pass's first draw's scissor with the game's last `SetScissor` over 50 frames of the cutscene's load: 3 draws off before the fix, 0 after.
- **Resolved: 7 `[RED]` lines, two of Unreal's global compute shaders not translated** (`4f731ba19a5f2877` and `c073d1efaba9ac70`, from `GlobalShaderCache-GLSL_SWITCH.bin`). Their atomics on a 4-byte buffer image use the value they return: `c073d1efaba9ac70` adds to a counter and exchanges the result into a table of list heads (a linked list), `4f731ba19a5f2877` adds and appends. The translator once took only atomics whose result is discarded, so their dispatches were skipped; it now translates returning atomics, and image atomics run as Metal's texture atomics, so both build: [Image atomics](../../../docs/reference/shaders.md#image-atomics). Skipped, they left the classroom at frame 29,000 a little darker, mean luma 56.8 to 57.3; with them it is 58.3 to 58.6 (two runs), as with their translations from before that admission (58.8). Likely Unreal's light grid (not confirmed).

## Files and shaders

- Its one pak, `Project/Content/Paks/pakchunk0-Switch.pak` (the profile's `romfs_marker`): 8.8 GB, version 8, Zlib blocks, the index and the `.uasset` files AES-encrypted. The key comes from a key callback in `main` (`main+0x14180c0`) whose two 16-byte halves are literals 0x1460 bytes apart (`uepak.py` `code_keys`; it stays in memory, never printed).
- Shaders: 18,558 unique (6,440 vertex, 11,608 pixel, 478 compute, 32 geometry), inline in the cooked packages: the engine's global shaders (`Engine/GlobalShaderCache-GLSL_SWITCH.bin`), the engine's materials and the game's ([Unreal Engine 4.23 shaders inline in an encrypted version 8 pak](../../../docs/reference/shaders.md#unreal-engine-423-shaders-inline-in-an-encrypted-version-8-pak)). The game has no PC version in this repository, so the facts table holds only compute group sizes; every vertex shader is made to link with any pixel shader (`shader_split.py` `separable_pairs`). The `shader_note` is still the provisional profile's: `shader_*` keys are part of every shader's cache key, and the libraries were built with it.

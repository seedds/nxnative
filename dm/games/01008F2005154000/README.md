# South Park: The Fractured But Whole (`01008F2005154000`)

Update **1.05** (`v327680`) over the base game, SDK **3.5.1**, Ubisoft Snowdrop on NVN. Modules: `main`, `subsdk0`, `sdk`. The extracted update and six DLC packages have been identified, but DLC gameplay has not been tested.

**Current verification (2026-10-27):** The separate **large-memory Mac baseline** now has **4,615 compiled native Metal shader entries**, a finalized **17.2 GiB self-contained signed `.app`** (base 1.05 and six DLC folders), and a standalone runtime that passed **24,600 frames**, rendering the cinematic, character customization and first toilet minigame, with live audio output and an APFS-backed writable save. The runtime exited cleanly on SIGTERM; later gameplay and DLC are not yet validated. The **registered 5 GiB compact profile** with **4 GiB Snowdrop virtual allocator** was described as stalled because an unattended, no-input run remained at 13 draws/frame for 31,200 frames. Fresh isolated Mac tests with the same 13-draw/727-call title signature strongly suggest it was an **idle “Press A to Start” screen**, not a guest async deadlock: with input the compact build renders the main menu, Play → New Game, commits an APFS save, renders the opening cinematic, and reaches **character customization at frame 9,000** and the **Choose Difficulty screen by about frame 13,800**. A bounded run reached **frame 15,000**, without Break, crash or red NVN errors. The original 31,200-frame log did not include a frame-2,100 screenshot, so the prior run's actual scene is inferred from matching counters, not proven visually. Full compact gameplay, sustained allocator stress and DLC are **not** independently verified. All **4,615/4,615** iOS Metal shaders compiled and an isolated **17 GiB unsigned diagnostic IPA** was produced. I tested the packaged iPhone build successfully; detailed on-device logs and scenes are **not included** in this PR.

**iPhone frame rate (2026-10-28):** On an iPhone 15 Pro Max, the separate-RomFS 1.05 IPA launched and the player confirmed gameplay. The game requested NVN present interval 2 and the default `game` mode held 30 fps. With `DM_PRESENT_INTERVAL=display` in `Documents/env.txt`, the player reported smooth gameplay with no observed speed or input issue; the phone log confirmed the override and measured 60.0 fps through frame 3,300, with no dropped on-screen frames in its sampled windows. This is a short player check, not an exhaustive timing check across cutscenes, combat and DLC. `fps_target 30` makes the existing launcher **Frame rate** choice available, defaults to 30 fps, and lets the player choose 60; the host's presentation cap takes precedence over the game's interval. The frame-step state and host engine-memory FPS lock are not used for this build.

## Startup failure and address-space layout

- The unmodified provisional profile reserved a **5 GiB guest block**, with a **4.375 GiB alias region**. Static initialization crashed with `SIGBUS` at `main+0x17fb4b0`, address `0x20000ffff`. Snowdrop's `main+0x17fb2b0` requests **12 GiB** of *virtual address space*, split into three 4 GiB classes, from `AllocateAddressRegion`. That request cannot fit in the host alias range; the returned failure is unchecked, and an allocator writes into the resulting invalid 64 KiB page address. The original log is `southpark-mac-build.log` in the external work folder.
- On Mac, a **diagnostic-only** profile with `mem_reserve 0x1028000000` and `mem_alias 0x1000000000` passed startup. The alias high-water mark reached **+14.07 GiB** (including the SDK's node area and the 12 GiB engine reservation), although only about **1.5 GiB of pages had been mapped** by frame 300. A 64 GiB guest alias reservation cannot be used on an ordinary iPhone installation.
- This **experimental 5 GiB guest profile** gives the SDK a **62 MiB node area** and **32 MiB alignment for regions at least 1 GiB**. The *new* Snowdrop reservation is **4 GiB**, split into **1.5 GiB for large allocations**, **512 MiB for 512 KiB slabs**, and **2 GiB for 64 KiB slabs**. The large allocator's separate maximum number of 64 KiB pages shrinks from 65,536 to **24,576** to match the 1.5 GiB class boundary. The class sizes are based on the exact v1.05 code and the compact Mac runtime measurements, not on proven gameplay headroom.
- The memory profile remains `mem_reserve 0x140000000`, `mem_alias 0x118000000`, `mem_stack 0x10000000`, `app_pool 0xCD500000` and the NPDM's `sys_resource 0x1000000`. **Four GiB of reserved virtual address space is not four GiB of committed RAM or process heap.** At the previously observed 32 MiB-aligned engine base `0x7014000000`, a new 4 GiB reserve would end at `0x7114000000`, leaving **320 MiB** to the alias end `0x7128000000`. Whether that space is sufficient for all other reservations still requires a boot check.

## Exact build-gated cuts

All byte assertions are enforced by the normal rewriter. The game cuts are in [`patches.py`](patches.py) only for `main` build `df15edaaf603e00cd7d8a01bd05a15c2`:

| `main+` | Change |
|---|---|
| `0x17fb2b0` | Combined allocation size 12 GiB → 4 GiB (`x0`) |
| `0x17fb2b8` | Combined range-end size 12 GiB → 4 GiB (`x22`) |
| `0x17fb2dc` | Large allocator's 64 KiB-page capacity 65,536 → 24,576 (`w5`) |
| `0x17fb300` | Initialize first class boundary to 1.5 GiB instead of 4 GiB |
| `0x17fb304` | **Required companion cut:** preserve the 1.5 GiB high bits in the following `movk`; `0x6007ffff` becomes `0x60000000` on 512 KiB alignment |
| `0x17fb30c` | Second class boundary 8 GiB → 2 GiB |
| `0x17fb388` | 64 KiB slab range boundary 8 GiB → 2 GiB (following `movk` adds `0xffff` for 64 KiB alignment) |

The three SDK cuts are in [`sdk_patches.py`](../../tools/sdk_patches.py) only for `sdk` build `8bb65519bc6399ab432e0ba7cdb16e2b`: `sdk+0x8cc60` (node-area upper bound 1 GiB → 62 MiB), `sdk+0x8ccf4` (occupied node-area length 1 GiB → 62 MiB), and `sdk+0x8ce48` (large-region alignment 1 GiB → 32 MiB). Both node-area instructions must change together. These are SDK 3.5.1 instruction locations and encodings.

### Compact boot regression after the original nine cuts

The first 5 GiB compact Mac run got through `nnMain` but faulted at `main+0x17fd774` (`ldr w10,[x9,#0x18]`) because the owner pointer `x9=0xeed8e2da60157bc2` was read from what looked like payload rather than ownership metadata. The faulting address `0xeed8e2da60157bda` equals `x9+0x18`. The directly observable patch error was `main+0x17fb304`: unpatched `movk x10,#7,lsl#16` cleared the 2 GiB bit set at `+0x17fb300`. After `movk x10,#0xffff` and 512 KiB alignment, the 512 KiB slab range started at **the reservation base** instead of **base+2 GiB** (the reservation base was aligned on this Mac run), overlapping the large allocation range. The new companion cut at `+0x17fb304` uses `movk x10,#0x8007,lsl#16`, retaining the 2 GiB bit. This fixes the proven boundary error in source but does **not** yet prove the next compact boot will succeed.

### SDK Break after the corrected first-boundary compact run

The next compact Mac run (`shader-probe/compact-fixed-visible.log`) passed full Metal initialization and reached about 300 frames, then exited 42 via a deliberate SDK Break SVC. Immediately before the Break, **15,872 consecutive 4 KiB pages** of the SDK node-area range `0x7010000000..0x7013e00000` were mapped: exactly **62 MiB**. `sdk+0x8dcac` branches on exhausted node-area capacity, through the SDK reporting path at `+0x8dcc0`, to Break. This is not evidence that the node-area cut itself is the original fault.

The triggering caller is Snowdrop's **64 KiB slab allocator** at `main+0x17fb600`. Its initial 512 MiB class (`0x70b4000000..0x70d4000000`) held **8,191 distinct mapped 64 KiB pages out of 8,192** and reached the final pages in that range. It entered the unmodified **4 GiB grow fallback**, `main+0x17fb634` (grow amount in `x21`) and `main+0x17fb640` (new request). The `main+0x185ff04` wrapper calls SDK `AllocateAddressRegion`; a new 4 GiB region cannot fit in the remaining alias address space. The failed retries consume SDK metadata nodes until the 62 MiB area is exhausted. By contrast, the 512 KiB class had mapped only **340 unique slots** of 1,024 and reached about **170 MiB of 512 MiB**; the large class's highest observed map was about **705 MiB** above its start. Rebalancing the initial virtual reservation is the supported response: extending the fallback without using the new region's returned base would not guarantee contiguity and is not a safe instruction-only fix.

The new **4 GiB / 1.5 GiB + 512 MiB + 2 GiB** layout is a bounded experimental mitigation, not a proof of sufficient capacity for all game scenes. The original 4 GiB per-class growth paths in `main+0x17fb548/+0x17fb554` and `main+0x17fb634/+0x17fb640` remain unmodified: if any class fills again, a general solution will require reliable dynamic region handling or an explicit allocation-failure path rather than a misleading claim that the SDK node area alone can be made larger.

### The supposed 31,200-frame loading stall: resolved with input, not a patch

The unattended `shader-probe/compact-4gib-visible.log` showed 13 draws/frame and never mounted `SPTFBW_SAVE`; an older compact screenshot at frame 120 was black. A full-memory Mac trace instead had additional command-buffer flushes and eventually mounted SAVE. The hypothesis was that the new `nvnCommandBufferGetControlMemoryFree` implementation (last `AddControlMemory` block size) caused a stuck async loader, unlike the full host's older unimplemented **zero** getter.

On **2026-10-27** we independently built two Mac test hosts from the **same source checkout**, changing *only* that NVN getter's return in a source overlay under `compact-next/nvn-control-ab/`: `capacity` returns the current `ctl_size`, `zero` always returns zero. Both ran the identical 4 GiB compact NSOs, original RomFS/AOC/shader inputs (read in place), with **different isolated writable APFS saves** and per-variant screenshot/PSO folders. Neither test host overwrote the production Mac app, repository host binary, or original compact modules.

| NVN per-frame signature | `capacity` | `zero` | Earlier full-memory Mac host |
| --- | ---: | ---: | ---: |
| Init (total calls) | 2,037 | 2,044 | 2,044 |
| Frame 1 (total calls) | 102 | 109 | 109 |
| Frame 300 | 501 | 529 | 529 |
| Frame 600 | 501 | 529 | 529 |
| Frame 1,800 | 727 | 811 | 811 |

The precise seven missing calls per frame with the `capacity` getter are one fewer each of `AddCommandMemory`, `AddControlMemory`, `BeginRecording`, `EndRecording`, `GetCommandMemoryUsed`, `QueueFlush` and `QueueSubmitCommands`; the getter *does* affect recording behavior. **But both variants displayed the epilepsy warning at frame 120 and the fully rendered snowy “Press A to Start” title at frame 2,100.** The capacity variant ran untouched to frame 3,300 and the zero variant to 4,500, with no crash. Therefore the getter difference **did not cause the alleged menu-progression stall**. Do not introduce the old zero-return stub as a production fix: `nvnCommandBufferGetControlMemoryFree` correctly reports the unused game-supplied capacity for the host's command recording, and the existing `t_nvn` control-memory tests pass.

We then ran **input-driven capacity-getter builds**, without changing the NVN semantics. After `A` on the title at frame ~2,100, screenshots at frame 2,300 showed the complete menu with Play selected, and the SDK mounted transactional `SPTFBW_SAVE` on a dedicated APFS directory and successfully logged `save commit #1` (atomic swap). A second `A` opened Play → New Game. In a fresh isolated run, `A` after frames ~2,100, 2,700 and 3,200 advanced through title, Play and New Game; frame 3,800 rendered the Ubisoft San Francisco intro, frame 5,400 the outdoor raccoon/vehicle cinematic, and frame 6,300 a distinct interior cinematic with characters. It finished by a bounded clean shutdown at frame 7,200, **with zero `[RED]`, Break SVC or crash lines**. The scene became more complex after input (e.g. **31 draws at frame 2,400, 43 at 3,000, and 69 at 7,200**); 13 draws on an unattended title is normal. An additional clean isolated **15,000-frame** run with the same normal capacity getter and scripted inputs rendered the fully interactive **character customization** screen at frame ~9,000. Manual controls moved the menu selection to **NEXT** and pressing A reached **Choose Difficulty** at approximately frame 13,800. The test ended at the bounded frame limit before proving progress past difficulty or the first toilet minigame. The run mounted and committed APFS save, logged no `[RED]`/Break/crash, and kept about 1.5 GiB resident during observation. Artifacts and per-variant logs are under `compact-next/nvn-control-ab`, including `runs/capacity-newgame-long/`; saves are under `/Volumes/SSD WD/dev/switch/southpark-ab-saves`.

## Shaders and rendering

The initial GLSLC capture held **one** output; an early scan recovered **3,587** distinct outputs, and the final scan of **172 populated Snowdrop SDF files** found **4,614 unique GLSLC outputs**. Combined with the original, the external build has **4,615 shader keys**, all compiled to Mac and iOS Metal libraries, with six translated `Pixld` warnings and 50 conservatively bounded uniform accesses. The real full-memory Mac app rendered the character customization screen at frame ~6,000, then the first toilet minigame; an input script reached the guest control service and caused HUD changes. Mac app audio callback logs show real output with zero reported underruns, and its APFS save mount wrote `profile.sys`. The registered repository profile still contains only shader **placeholders**, not copyrighted game bytes or generated cache libraries. The compact 4 GiB layout independently reached the title, interactive main menu and opening cinematic as detailed above, **without any new general NVN getter patch**.

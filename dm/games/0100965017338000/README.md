# Super Mario Party Jamboree (`0100965017338000`)

Update 2.3.0 (`v458752`), SDK 17.5.9. NintendoWare Bezel Engine 2.9 on NVN, by NDcube. Modules `main`, `subsdk0` (NintendoSDK_movie) and `sdk`; the boards, minigames and modes are 139 NROs (`nro/NX_Release/*.nro`, registered by one NRR) that the game loads with `ro::LoadModule`. `patches.py` holds one cut of `main` (the pinned 3D render size, [Frame rate](#frame-rate)); the standard rewriter covers the rest of `main`, `sdk` and every NRO.

On the Mac (headless, docked): from a fresh save the opening movie with sound, the title, the player count and character setup, the Party Plaza with Toad's tour, the island map, and Mario Party on Mega Wiggler's Tree Party with CPU opponents: the turn-order roll, the dice block, moving on the board, the item shop, the 4-player minigame Snag the Flags (rules, practice and the match), its results, the save and turn 2. 60 fps on the board (frame time p99 about 18 ms), no crash, no `[RED]` line beyond those below. A shorter test than usual, at the user's request: one board, one minigame. The Mac app and the IPA are built and their contents checked; the phone run is [not done](#artifacts).

## Memory

- **Resolved: null from `nn::bezel::CoreSystem::Allocate` as the Party Plaza or a menu loads.** The provisional profile (16 MB system resource, so virtual address memory; 5 GB block, 4.375 GB alias region) crashed at `main+0x8d9a48` writing past a null 46 MB block, or first read a file into a null 4 MB buffer (`[RED] fs ReadFile into 0x0+0x400000 failed at +0 (EFAULT)`). `nninitStartup` (`main+0x98281c`) is Big Brain Academy's: with virtual address memory, malloc's StandardAllocator gets 2 GB of address space (`main+0x982838`) and Bezel's asks for 56 GB (`main+0x982968`), which the host's allocator gate lowered to the 2.06 GB left. Measured with a 64 GB alias region (`DM_ALIAS_SIZE=0x1000000000 DM_ALIAS_WINDOWS=512`): malloc's region held 5 MB, Bezel's 2.3 GB at the plaza (850 MB at the bottom of its region, 1.46 GB at the top). The profile reports no system resource, so the game takes its heap path ([Bezel Engine's two memory setups](../../../docs/reference/memory.md#bezel-engines-two-memory-setups)). With it the route above ran with nothing in the alias region.
- The heap check's 1 GB pool (made for the virtual-memory path) and the Switch's 3285 MB pool made no difference on that path: the game's regions do not depend on the pool there.
- Resident memory on the Mac was about 4.9 GB, with 2.4 GB of Metal allocations, on the board after the minigame (heap path, frame 51,300).

## Rendering

- 25,693 shaders (8,140 vertex, 17,501 pixel, 35 compute, 12 geometry, 1 hull, 4 domain), 25,447 of them in the archives (most in the 13,839 `.fshb` entries, type tag `_G3DSHA`) and 246 in `main`; 20,541 shader pairs. All build for the Mac. Window origin upper left (set after a lower-left default), depth mode near = 0, swapchain 1920x1080 RGBA8 sRGB, present interval 1.
- **Resolved: flat grey triangles on the board.** On the board and at the minigame podium, flat grey or background-coloured shapes with straight edges covered part of the scene (behind the dice block, beside the path, behind the item shop), changing shape from frame to frame while the camera stood still, and the board's spaces were missing. The spaces are GPU-driven instances: a vertex shader drawn as 62 points with rasterization off (`2b5485a2a731a231`) writes an 80-byte transform per visible instance and counts them, `276504dc5c987ecf` turns the count into nine indirect draw records, and the instanced draws (`5a805bbb08421b86` in the depth pre-pass, `4b05556737e9535f` and `eaa3a44ba28f0744` in the colour pass) read record = instance + `c0[0x644]`, the driver's base-instance word. The host could only put 0 there for an indirect draw, so every draw read the first records ([The base instance of indirect draws comes from Metal](../../../docs/reference/shaders.md#the-base-instance-of-indirect-draws-comes-from-metal)). Found by bisecting the colour pass with `DM_NVN_SKIP_FS` (which never removed the shapes), then following the vertex-stage storage buffer the instanced draws read back to its writer in the pass dump.
- `[RED] NVN unimplemented function called: nvnQueueGetTotalCommandMemoryUsed` / `…ControlMemoryUsed` / `…ComputeMemoryUsed` / `nvnQueueResetMemoryUsageCounts`, about once every few seconds: memory-usage statistics the engine reads; nothing depends on them in the route.
- One `SetRenderEnableConditional` (drawn unconditionally), one `stage 0 cb7 has no uniform buffer bound` and one `sampler ID 4095 not registered`, at boot.
- Run headless while someone works at the Mac: in a covered window the display link stalled for a second at a time and screenshots were not taken.

## Movies

- The opening movie (`movie/flow/op/movie/bq_op.mp4`, H.264 1080p) and the mode previews in the island map are native-texture movies (output 3, mode 2). The opening movie is unskippable on the first start; later −/+ skips it.
- **Resolved: the opening movie froze on its 16th picture.** This SDK returns the output index inside `GetOutputBuffer` in native-texture mode, and the game never releases one ([`GetOutputBuffer` returns the output index in native-texture mode](../../../docs/reference/movies.md#getoutputbuffer-returns-the-output-index-in-native-texture-mode)).

## Frame rate

- **The picture cycled soft and crisp on the island map: it was the game's own dynamic resolution, and it is now pinned at full size.** The 3D target is 1600x900 times a scale the controller moves — measured 1600x900, 1521x856, 1464x824, 1379x776, 1308x736, 1223x688, 1152x648, 1024x576, 967x544, 896x504, 853x480 and 796x448 (0.5 of 1600x900, its floor, the height rounded down to a multiple of 8) — with the UI and the composite at 1920x1080, and 1,064 `nvnCommandBufferReportCounter` calls a frame are what it steers by. `DM_NVN_TSDBG=1` over 306 sampled frames of the map and the screens around it: GPU work 7.62 ms p50, the GPU's span inside the frame 16.50 ms p50 (17.79 p90), so the GPU idles about 9 ms of every frame while the host translates (1,246 draws, 51 M instructions, 5.8 ms of CPU; the guest blocks about 6 ms a frame in its submit and present calls (`NVN submit+present` p50 5.97 ms)), and the frame interval sits at one vsync exactly (16.66 ms p50). The size moves the GPU's work a little and the frame not at all (same route, `DM_NVN_GPUPROF=every:15`: GPU work 7.5 ms p50 at 1600x900 against 6.4-6.8 at 796x448, frame time p50 16.66-16.68 ms either way), so the controller steps down for a frame it cannot shorten, gains nothing, and steps back up: [A dynamic resolution whose frame span does not follow its render size](../../../docs/reference/frame-rate.md#a-dynamic-resolution-whose-frame-span-does-not-follow-its-render-size).
- **Fixed: the render size is pinned** ([`patches.py`](patches.py), `FRAME_STEP` of `main` `d70ce1726c979e45ed4200e9c2b23b2a`). Bezel Engine 2.9's controller is one object of the renderer module (`bex::gfx::RendererModule` +0x148, `g_Module` at `main+0x1bfd890`): `main+0x795a0` measures the frame against 1/60 s, computes `scale x sqrt((budget - (t1 - t0)) / t0)`, clamps it to [`+0x18` = 0.5, 1.0] and stores it at `+0x68` (`main+0x79758`); `main+0x797ac` turns the scale into the size (height = 900 x scale rounded down to a multiple of 8, width in proportion) and the renderer's pass (`main+0x534a0`) resizes the scene's targets to it. The cut branches that store to a stub that writes 1.0 instead, unless `DM_DYNAMIC_RESOLUTION=1` (the launcher's **Dynamic resolution**, off by default) leaves the game's controller alone. Measured on the island map from the user's save (frame time p50 16.66-16.68 ms before and after): before, 73 size changes over 663 profiled frames and 32 of them at 796x448; after (`DM_NVN_GPUPROF=every:10`, 1,187 profiled frames), 588 profiled frames of the map at one size, 1600x900, and no half step. GPU work at 1600x900 is the same in both (p50 7.51 before against 7.60 after, mean 7.41 against 7.37); the all-frame GPU p50 rises from 7.33 to 7.60 only because the frames that were drawn at 796x448 no longer are. The picture at 1600x900 is the sharp one (two runs of the same static map, `DM_NVN_TSDBG` sizes 1600x900 and 796x448, compared 1:1: the half-size frame's karts and rock edges are visibly soft). `DM_DYNAMIC_RESOLUTION=1` was run to check the switch: the controller moves the size again (1,251x704 and 1,408x792 among 253 profiled frames).

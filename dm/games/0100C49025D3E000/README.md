# EA SPORTS FC 27 (`0100C49025D3E000`)

Updates 1.8d.310c (v393216) and 1.8d.6523 (v458752), SDK 22.2.0, on NVN (API 55.15). **Frostbite** 2025.1.2 (`Info_Nx_retail.BuildSettings`): its data in superbundles (`.toc` tables, `.cas` files, Oodle Leviathan), its NVN renderer in an NRO the game loads at run time, `Engine.Render.Core2.PlatformNvn.nro` (with its symbol file `.nrs` beside it in the RomFS). Modules `main` (185.6 MB of text) and `sdk`; the NRO is collected from the RomFS and rewritten like them.

On the Mac (2026-10-29): the accessibility settings, the EA SPORTS and FC 27 logos, the title, the offline notice (no EA servers), the user agreement, the favourite-team setup, the main menu over its 3D training ground, Kick Off, and a Classic Match (Atlanta United v Orlando City at Mercedes-Benz Stadium): the stadium and crowd, the pre-match presentation (tifo, coaches, line-ups), kick-off, and the first half and into the second (67 minutes of match time) played with the pad (passing, shooting, a goal for Orlando, a corner, the in-game tactics tutorial). The game runs at 30 fps on the Switch; here menus and the match run at 60 ([Frame rate](#frame-rate)): frame time p50 16.7 ms, the match clock at its 30 fps rate. Resident memory stays at about 3.5 GB, GPU allocated 1.9 GB.

The six `dual_want.tsv` hashes all exist; one more shader (`1029fc461a009a04`, its `_b` variant) logs a dual-source red line and is not listed yet.

Carried as a `hle_fpslock.c` row for `570dc9f1…`; the host writes 60 back when the game sets 30 again.
- **Native swapchain, 720p / 1080p / 1440p / 4K:** [`patches.py`](patches.py) cuts the NRO's `fb::SwapChainNvn` constructor and `resize` to 2560x1440 as the default; the host (`hle_nro.c`, keyed by the NRO build ID) rewrites the four size instructions at NRO load to the launcher's `DM_DISPLAY_SIZE` choice. `vi::ListDisplays` reports the same size as the layer. ## Shaders

- **Current:** 1.8d.6523: 7,875 shaders (1,522 vertex, 3,131 pixel, 3,222 compute) from the 10,401 `CompiledBytecode` resources of the bundles (1.8d.310c: 7,873, 1,520 vertex). The split decodes them with the game's own Oodle in the Mac host in about 30 s. All translate and compile for the Mac ([CompiledBytecode resources in Frostbite superbundles](../../../docs/reference/shaders.md#compiledbytecode-resources-in-frostbite-superbundles)).
- **The control-block cache:** `fb::ShaderPlatformDataNvn` (renderer NRO) copies each shader's code into its pool and keeps one copy of each control section in a cache keyed by a hash that leaves out GLSLC's compile information (`s_controlBlockCacheMutex`), so a program gets the control section of the first shader with the same rest: at run time +0x7d0..+0x7e7 name another shader. Without `shader_key_skip`, 10 of the first menus' programs were not in the map (their code areas were the files', their control sections another resource's); with it the 10,342 keys are 7,873 shaders ([Control sections shared among shaders that differ only in their compile information](../../../docs/reference/shaders.md#control-sections-shared-among-shaders-that-differ-only-in-their-compile-information)).
- **Open:** the resources name no vertex / pixel pairs (Frostbite pairs them in its pipeline data), so there is no pipeline prebuild list; the prewarm list (`pso_manifest.tsv`) is empty.
- **Resolved:** `dc446d7f52c14ea6` (pixel; `[RED] … B binding fp_t2d_cb196610_10570000 has no resolved slot number`), met in a match, did not load. Its loop over separate texture slots i = 1, 2, … reads each handle word at c2 byte 0x168 + 8i and samples an array of c2 handles at element 45 + i (the handle's byte offset ÷ 8), with one separate sampler word (c2 byte 0x570) ORed into every handle; the translator's 32-element array clamped every index to 31, the build did not decode the sampler word, and it refused the loop's own read of each handle word at a computed c2 index → [Arrays of c2 handles cover the whole table, with a separate sampler word](../../../docs/reference/shaders.md#arrays-of-c2-handles-cover-the-whole-table-with-a-separate-sampler-word).
- **Open:** in 1.8d.310c five shaders have a binding whose slot the build does not decode, and the translator leaves out seven (two with a bindless `texture2D` whose handle source it cannot find, four with `PrmtI`, one with `AtomCas`); none was met in the menus or a match. In 1.8d.6523 the split reports four undecoded bindings and the same five translator omissions.

## Memory

- Frostbite's `VirtualAlloc` (`main+0x17f9884`, `VirtualAlloc_Posix.cpp`) reserves each arena of `MemoryInit.ini` as an address region: 264 regions, 2.8 GB, in its first minute, three of them 512 MB, while it maps 0.7 GB. With the SDK's 1 GB node area they ran past the 4.38 GB alias region within seconds (`Couldn't reserve memory of size: 536870912 …`, then a deliberate store to address 0 at `main+0x17f98c4`). With the node-area cut they reach alias +3.5 GB at the title, +3.75 GB in the menus +4.25 GB 23 minutes into a match and +4.50 GB at 67 minutes (1.3 GB mapped) in a 4.75 GB alias region, hence the 5.25 GB one. Late in that match 655 live regions held 3.05 GB but spanned 4.52 GB: 1.41 GB lay in 654 gaps, nearly one after each region, as the SDK's AddressRegionManager placed them (open: whether the mark levels off over a whole match).
- Measured with a Switch-sized alias region (`DM_ALIAS_SIZE=0x1000000000`, `DM_REGIONS`).

## Frame rate

- **Current:** 60 fps in the menus and a Classic Match. 1.8d.310c (Mac): frame time p50 16.66 ms, p95 18.2 ms; the match clock went 02:40 → 04:00 → 05:20 at 10.3 s steps, as at 30 fps (01:20 → 02:39). 1.8d.6523 at native 1440p: frame time p50 16.68 / p95 17.29 ms, GPU p50 about 8 / p95 about 12.3 ms in a short match; menus p95 about 8-9 ms. `fps_target 30` runs the game's own 30.
- **120 fps (`fps_max 120`, launcher Frame rate 120, or `DM_FPS_TARGET=120`):** Frostbite's simulation rate and the regulator follow 120; the regulator's wait rate is 127.66 fps (the 0.5 ms margin) and the rate it reports is 120. The present runs at 120 Hz on the 120 Hz display link, one frame per tick. At native 1440p the menu measured p50 8.33 / p95 8.6 ms and GPU p50 4.1 / p95 5.2 ms; a match measured p50 8.32 / p95 about 9.4 ms, GPU p50 4.7 / p95 about 5.7 ms. The match clock was at 00:35 at the same point where 60 fps showed 00:34, so the game speed is unchanged. Heavier stadiums and MetalFX at 120 can drop below 120.
- **120 fps, long run (2026-11-04, rebased upstream):** 42,900 frames (about 6 minutes) at native 1440p, no crash; the last 300-frame window p50 8.35 / p95 8.71 ms, GPU p50 3.85 / p95 4.46 ms, 1 dropped frame. The earlier intermittent crash (`CRASH sig=11 addr=0x10 pc=main+0x96bd8d8`, after about 100 s) did not reproduce; it remains open.
- **100 fps:** the launcher also offers 100 for a 100 Hz display; it is one frame per display-link tick there. On a 120 Hz panel the link uses fractional ticks (five 8.33 ms frames, then one 16.7 ms frame), so p95 is 16.7 ms even though the average is 100 fps: measured at native 1440p p50 8.38-8.54 / p95 16.44-16.83 ms, GPU p50 4.1-7.1 / p95 6.1-7.4 ms, 0-5 dropped per 300. On a 120 Hz panel 120 fps is the even choice. On a 4K 120 Hz display, 100 fps is the better choice over 60 when the GPU has headroom: the cadence's long frame is 16.7 ms, the same as 60 fps, so 60 is the worst case rather than a steadier setting, while the average is 100. The 4K/120 gameplay windows measured GPU 6.3-6.6 ms, well inside 100 fps's 10 ms.
- **Credit:** the `fps_max` key, the 0.5 ms regulator margin and the 120 Hz link follow the [FC 26 120 fps patch](https://github.com/imnotsharingmyname/nxnative-fc26-120fps) by imnotsharingmyname (MIT). This profile adds 100 fps, the screen-Hz link rate and the FC 27 regulator row.
- **4K / 60 fps:** native 3840x2160 swapchain; measured frame time p50 16.6-16.7 / p95 17.4-18.5 ms, GPU p50 8.7-11.5 / p95 9.7-15.3 ms, 0-3 dropped per 300. A perfectly even cadence; 4K/100 is better if you want a higher average with the same worst case.
- **4K / 120 fps:** 45,600 frames (about 6 minutes), no crash. Gameplay windows p50 median 8.42 / p95 9.77 ms, GPU p50 6.64 / p95 7.01 ms, 0 dropped per 300; cutscene/heavier windows p50 median 11.22 / p95 13.82 ms, GPU p50 8.38 / p95 8.73 ms, 27-75 dropped per 300. On this 120 Hz display, 100 fps is the better fallback than 60: its worst-case frame is the same 16.7 ms as 60, with a higher average. 4K/60 is only for a perfectly even cadence.
- **What sets 30 on the Switch:** three things, each needed. Frostbite's `SimulationTimeSettings` (`ForceSimRate` 30, `MaxSimFps` 30) caps the simulation's ticks; the game's frame regulator, an object at `[main+0xda20e38]` whose tick (`main+0x99ea580`) waits 1 / `[+0x8]` s from the last frame (the constructor sets 60.0 at `main+0x99e80c8`), gets 30.0 in `[+0x8]` and `[+0x10]` from `main+0x5d501c0` whenever `GameRenderSettings.Enable` is 1, a constant of this build; and `BaseDisplaySettings.PresentInterval` is 2.
- **What the host does:** the simulation settings are found by name in `main`'s reflection data, on any build ([Frostbite's simulation rate, found by name](../../../docs/reference/frame-rate.md#frostbites-simulation-rate-found-by-name)); the regulator is a build-gated row of `hle_fpslock.c` (the game sets 30 again at some screen changes; the host writes 60 back); `present_interval display` ignores the interval. Only the simulation and the regulator at 60 together give 60 at the right speed: the regulator and present interval alone gave 60 frames a second with the match clock at half speed (3.65 game seconds a second); the simulation at 60 with the regulator at 30 (a build without the row) gives 30 fps at the right speed.
- **Not needed:** `GameplayFeatures.DeltaTicks` (4.0; it becomes the int at `main+0xd10b6d8` that sets the gameplay rate `60 / DeltaTicks` at `[regulator]+0x1e54c`) stays as the game sets it. Forcing that int to 1 instead crashed the match at kick-off (`main+0x4ccd66c`).
- **Open:** a future build needs the regulator row carried over (`nso_fnmap.py`, then check the setter and the regulator's global by disassembly): `main` has unwind entries for only 405 functions, so a function-matched cut cannot follow it. 1.8d.6523 was carried over this way (setter `main+0x5d66b70`, global `main+0xda450d8`, tick `main+0x9a0b690`); until a build has a row it runs at 30 fps at the right speed.

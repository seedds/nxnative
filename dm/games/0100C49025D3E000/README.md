# EA SPORTS FC 27 (`0100C49025D3E000`)

Updates 1.8d.310c (v393216) and 1.8d.6523 (v458752), SDK 22.2.0, on NVN (API 55.15). **Frostbite** 2025.1.2 (`Info_Nx_retail.BuildSettings`): its data in superbundles (`.toc` tables, `.cas` files, Oodle Leviathan), its NVN renderer in an NRO the game loads at run time, `Engine.Render.Core2.PlatformNvn.nro` (with its symbol file `.nrs` beside it in the RomFS). Modules `main` (185.6 MB of text) and `sdk`; the NRO is collected from the RomFS and rewritten like them.

On the Mac (2026-10-29): the accessibility settings, the EA SPORTS and FC 27 logos, the title, the offline notice (no EA servers), the user agreement, the favourite-team setup, the main menu over its 3D training ground, Kick Off, and a Classic Match (Atlanta United v Orlando City at Mercedes-Benz Stadium): the stadium and crowd, the pre-match presentation (tifo, coaches, line-ups), kick-off, and the first half and into the second (67 minutes of match time) played with the pad (passing, shooting, a goal for Orlando, a corner, the in-game tactics tutorial). The game runs at 30 fps on the Switch; here menus and the match run at 60 ([Frame rate](#frame-rate)): frame time p50 16.7 ms, the match clock at its 30 fps rate. Resident memory stays at about 3.5 GB, GPU allocated 1.9 GB.

## Shaders

- **Current:** 1.8d.6523: 7,875 shaders (1,522 vertex, 3,131 pixel, 3,222 compute) from the 10,401 `CompiledBytecode` resources of the bundles (1.8d.310c: 7,873, 1,520 vertex). The split decodes them with the game's own Oodle in the Mac host in about 30 s. All translate and compile for the Mac ([CompiledBytecode resources in Frostbite superbundles](../../../docs/reference/shaders.md#compiledbytecode-resources-in-frostbite-superbundles)).
- **The control-block cache:** `fb::ShaderPlatformDataNvn` (renderer NRO) copies each shader's code into its pool and keeps one copy of each control section in a cache keyed by a hash that leaves out GLSLC's compile information (`s_controlBlockCacheMutex`), so a program gets the control section of the first shader with the same rest: at run time +0x7d0..+0x7e7 name another shader. Without `shader_key_skip`, 10 of the first menus' programs were not in the map (their code areas were the files', their control sections another resource's); with it the 10,342 keys are 7,873 shaders ([Control sections shared among shaders that differ only in their compile information](../../../docs/reference/shaders.md#control-sections-shared-among-shaders-that-differ-only-in-their-compile-information)).
- **Open:** the resources name no vertex / pixel pairs (Frostbite pairs them in its pipeline data), so there is no pipeline prebuild list and no pulling stand-in on a first miss: every pipeline no prewarm list names is compiled while its draw waits.
- **Current, 2026-11-12:** the prewarm list (`pso_manifest.tsv`) holds 1,976 rows (797 shaders, 1,023 render pipelines, 156 compute pipelines) recorded on 1.8d.6523 at 1440p and 4K over boot, the menus, Kick Off and several matches, and at 4K / 60 over two Be A Pro matches, whose loads and presentation froze for 0.4 to 2.2 s in single frames (16 to 74 new pipelines each) before their 517 rows were added; the prepare step builds them before the first frame (1,377 of them in 6.7 s on an M1 Max). Without it, the first match load froze for 2.3–6.1 s in single frames (29–62 new pipelines each) even with the boot and menu rows prewarmed; the remaining cold misses compile in parallel ([A burst of pipeline misses compiled one after another](../../../docs/reference/shaders.md#a-burst-of-pipeline-misses-compiled-one-after-another)). On the Mac a run keeps `pso_user.tsv` and `pso_archive/` beside its save's folder: a test harness that copies the save into a new folder each run starts every run cold.
- **Resolved:** `dc446d7f52c14ea6` (pixel; `[RED] … B binding fp_t2d_cb196610_10570000 has no resolved slot number`), met in a match, did not load. Its loop over separate texture slots i = 1, 2, … reads each handle word at c2 byte 0x168 + 8i and samples an array of c2 handles at element 45 + i (the handle's byte offset ÷ 8), with one separate sampler word (c2 byte 0x570) ORed into every handle; the translator's 32-element array clamped every index to 31, the build did not decode the sampler word, and it refused the loop's own read of each handle word at a computed c2 index → [Arrays of c2 handles cover the whole table, with a separate sampler word](../../../docs/reference/shaders.md#arrays-of-c2-handles-cover-the-whole-table-with-a-separate-sampler-word).
- **Open:** in 1.8d.310c five shaders have a binding whose slot the build does not decode, and the translator leaves out seven (two compute shaders, `b4f2c3223681dc02` and `d02731c7f3de095b`, with bindless `texture2D` accesses whose handle source it cannot find: [Losses a shader build reports](../../../docs/reference/shaders.md#losses-a-shader-build-reports), four with `PrmtI`, one with `AtomCas`); none was met in the menus or a match. In 1.8d.6523 the split reports four undecoded bindings and the same five translator omissions.

Memory is from the host's `memory up to frame` lines during the match. **Total** is the process's memory footprint (`phys_footprint`, the figure Activity Monitor's Memory column shows), which on Apple silicon includes the GPU's allocations, as CPU and GPU share one memory. **GPU** is what Metal has allocated for the game (`MTLDevice.currentAllocatedSize`, logged as `GPU allocated`). **App** is the rest, total minus GPU: the game's own memory and the host's. The resolution moves the GPU part; the app part stays about 1.9 GB.

Measured 2026-11-12 on an M1 Max (`applegpu_g13s`) with a 120 Hz display, the Mac app built after the upstream merge, in a Classic Match played by hand with one DualSense: medians of the host's 300-frame windows (`timing up to frame`, `on-screen up to frame`), launcher settings fullscreen, MetalFX and present snapshots. At 120 the frame step holds 120 while frames fit and 60 after late ones ([120 fps follows the frame step](../../../docs/reference/frame-rate.md#120-fps-follows-the-frame-step)), so the game's speed stays right in both; a window counts as held at 120 when its on-screen p99 is 8.33 ms. 4K / 120 held 120 in 34 of 51 match windows, 1440p / 120 in 64 of 109; 4K / 60 is 37 windows. The three sessions ran 20,700, 13,500 and 36,000 frames, each ending with the host's exit 0. At 1440p the windows held at 60 have GPU p50 6.6 ms, so their limit is not the GPU; the sessions are different stretches of play, so the two resolutions' shares are not a like-for-like comparison.

**Recommended: 4K / 120.** It shows 120 where frames fit and falls back to 60, the same rate as 4K / 60, where they do not.

- **60 fps:** the simulation and the regulator at 60 in the menus and matches, at the right speed: on 1.8d.310c the match clock went 02:40 → 04:00 → 05:20 at 10.3 s steps, as at 30 fps (01:20 → 02:39). `fps_target 30` runs the game's own 30.
- **120 fps (`fps_max 120`, launcher Frame rate 120, or `DM_FPS_TARGET=120`):** Frostbite's simulation rate and the regulator follow the frame step's hold, 120 or 60; at 120 the regulator's wait rate is 127.66 fps (the 0.5 ms margin) and the rate it reports is 120. The present runs on the 120 Hz display link, one frame per tick at 120. The match clock was at 00:35 at the same point where 60 fps showed 00:34, so the game speed is unchanged.
- **100 fps (not measured):** the launcher offers 100 for a 100 Hz display; there it is one frame per display-link tick. On a 120 Hz panel the link uses fractional ticks (five 8.33 ms frames, then one 16.7 ms frame).
- **Credit:** the `fps_max` key, the 0.5 ms regulator margin and the 120 Hz link follow the [FC 26 120 fps patch](https://github.com/imnotsharingmyname/nxnative-fc26-120fps) by @imnotsharingmyname (MIT). This profile adds 100 fps, the screen-Hz link rate and the FC 27 regulator row.
- **Screen fill (Mac):** the launcher's Screen fill `stretch` (`DM_PRESENT_FILL=stretch`) fills a 16:10 screen with no black bars; it stretches the 16:9 picture. `fit` keeps the aspect ratio. From the same FC 26 patch.
- **Button layout (Mac):** the launcher's Button layout `xbox` ("Xbox / PS labels") maps an Xbox or PS pad by its printed labels (A / Cross the game's A, B / Circle B, X / Square X, Y / Triangle Y); `position` keeps the Switch's places. From the same FC 26 patch.
- **4K / 60 fps:** native 3840x2160 swapchain; the table's row. Its GPU time (p50 9.58 ms) is over the 8.33 ms a 120 fps frame has, which is why 4K / 120 holds 60 in the heavier scenes.
- **Open, intermittent crash at 120:** one crash at 1440p / 120 after about 100 s, `CRASH sig=11 addr=0x10 pc=main+0x96bd8d8`, a null list insertion in the game's code. It did not come back in the Frame rate table's sessions.
- **What sets 30 on the Switch:** three things, each needed. Frostbite's `SimulationTimeSettings` (`ForceSimRate` 30, `MaxSimFps` 30) caps the simulation's ticks; the game's frame regulator, an object at `[main+0xda20e38]` whose tick (`main+0x99ea580`) waits 1 / `[+0x8]` s from the last frame (the constructor sets 60.0 at `main+0x99e80c8`), gets 30.0 in `[+0x8]` and `[+0x10]` from `main+0x5d501c0` whenever `GameRenderSettings.Enable` is 1, a constant of this build; and `BaseDisplaySettings.PresentInterval` is 2.
- **What the host does:** the simulation settings are found by name in `main`'s reflection data, on any build ([Frostbite's simulation rate, found by name](../../../docs/reference/frame-rate.md#frostbites-simulation-rate-found-by-name)); the regulator is a build-gated row of `hle_fpslock.c` (the game sets 30 again at some screen changes; the host writes 60 back); `present_interval display` ignores the interval. Only the simulation and the regulator at 60 together give 60 at the right speed: the regulator and present interval alone gave 60 frames a second with the match clock at half speed (3.65 game seconds a second); the simulation at 60 with the regulator at 30 (a build without the row) gives 30 fps at the right speed.
- **Not needed:** `GameplayFeatures.DeltaTicks` (4.0; it becomes the int at `main+0xd10b6d8` that sets the gameplay rate `60 / DeltaTicks` at `[regulator]+0x1e54c`) stays as the game sets it. Forcing that int to 1 instead crashed the match at kick-off (`main+0x4ccd66c`).
- **Open:** a future build needs the regulator row carried over (`nso_fnmap.py`, then check the setter and the regulator's global by disassembly): `main` has unwind entries for only 405 functions, so a function-matched cut cannot follow it. 1.8d.6523 was carried over this way (setter `main+0x5d66b70`, global `main+0xda450d8`, tick `main+0x9a0b690`); until a build has a row it runs at 30 fps at the right speed.

## Found on this game

- **Open, 2026-11-12, frame step:** at 4K / 120, pausing and moving to another monitor (the window covered: its display link fires about once a second) often leaves the game held at 60 after the return. The frame step controller (`nvn_fstep.h`) is not told the window is covered, so it keeps judging those frames, counts failed probes and learns its references from them; after the return it probes only when the CPU or GPU looks slowed or the scene's cost matches one that held 120, and one session made 2 probes, both failed, in the minute after. Not confirmed which reference blocks the probes; accepted for now (the frame step decides again at the next cap or scene change).
- **Open, 2026-11-12, performance:** after each of two Be A Pro matches at 4K / 60 the same scene ran for 30 s or more at GPU p50 21 ms (about 47 fps, 80 to 88 of each 300 frames dropped), against 10 to 11 ms in the match itself. Not yet profiled (`[gpuprof]` names the pass); the scene is not on the benchmark route.
- **Current, 2026-11-11, stability:** the 283.4 ms match-load frame spent 268.7 ms compiling three previously unseen pipelines; the preceding frame loaded shader `d99fcad487cc22c4_b`. Their four recorded rows are now in `pso_manifest.tsv`, so startup can prepare them. `b5aae7280a615617` lacked its dual-source entry; exhaustive prewarm collection also found `7fea71b3931b3a64`, `bb5a9abd45b6e603` and `f6f6e6e385786cb7`. These four keys are now in `dual_want.tsv`. Rebuilt libraries contain the required entries; gameplay confirmation remains pending.
- **Resolved attribution, 2026-11-11:** the 123.0 ms frame followed `window covered` and `display link silent for 121 ms`. A diagnostic reproduction recorded 118.4 ms with the render thread in `mtl_present_wait`, again immediately after the window became covered. macOS suppresses a covered window's display-link callbacks; this is not shader or scene-rendering work. No game-code workaround is applied. Keep the window visible for performance measurements; covered-window intervals do not establish gameplay stutter.

- **Current:** at 4K / 120 the heavier scenes hold 60 (the Frame rate table). For measuring the sustained rate without that hold, use `DM_FPS_TARGET=120 DM_FPS_HOLD=off`; the host now honors the hold setting at 120 too ([120 fps follows the frame step](../../../docs/reference/frame-rate.md#120-fps-follows-the-frame-step)). - **Current, 2026-11-11:** [A burst of pipeline misses compiled one after another](../../../docs/reference/shaders.md#a-burst-of-pipeline-misses-compiled-one-after-another): the match load's freezes on a cold start.

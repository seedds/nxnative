# Hyrule Warriors: Age of Imprisonment (`04003F40232DE000`)

A Switch 2 game: update v196608, SDK 20.5.15 built for the Switch 2 (`Ounce`). Koei Tecmo's KTGL engine on NVN2, modules `main`, `subsdk0` (NintendoSDK_movie: VP9 movies) and `sdk`. **Plays on the Mac** from a new save through the first-run settings, the opening movies and cutscenes into the first field, where Zelda walks; the frame time's median is 16.6 ms there, with long frames every few frames on a 16 GB Mac ([Performance](#performance)). The first battle (the village) plays at 1x and at 2x; the first outpost mission froze the GPU once in the Mac app ([GPU hang in a battle](#gpu-hang-in-a-battle-open)). A one-hit-kill cheat exists ([Cheats](#cheats)). No IPA has been built.

## Performance

- The first field, from boot: frame time p50 16.6 ms, p95 about 18 ms, p99 100–114 ms on an M6 Mac with 16 GB. Each frame takes 3–6 ms of GPU time; the long frames wait for Metal's submission queue.
- Resolved: about 10 fps (p50 100 ms) in the field. Each dedicated c1 constant block of the partial library was a Metal buffer of its own, and the residency set's 16,118 objects made every commit slow ([Dedicated c1 constants as slices of a bank](../../../docs/reference/frame-rate.md#dedicated-c1-constants-as-slices-of-a-bank)).
- Current (open): the Metal driver wires and unwires memory for each submission, 2.8 s of every 4 s in a Metal System Trace. The game's own GPU memory pool is a constant 4,655 MB (`main+0x19eb098`), with a second pool of 350 MB, and its GPU allocations total 7 GB; the 16 GB Mac had 9.7 GB wired system-wide and about 160 MB free. With fewer commits per frame (`DM_NVN_CUT=0`) p99 was 52–69 ms. A Mac with more memory has not been tried.

## Resolution upscaling

Measured 2026-11-04 in the first field (Zelda walking), `DM_UPSCALE=2` with `DM_NVN_PASSDUMP_ALL=1`, `DM_NVN_PASSDUMP` of three frames and `DM_CTL` `texlist 1`, before IMAGE-flagged textures could be scaled:

- KTGL makes every render target with `IMAGE | COMPRESSIBLE` (flags `0xc`), and the swap chain's three 3840x2160 textures with `DISPLAY | IMAGE | COMPRESSIBLE` (`0xd`), whether or not a shader ever writes them as images; `DM_NVN_TEXINFO=1920x1080` and `texlist` show no screen-sized target without `IMAGE`. So nothing was scaled.
- The 3D is drawn at a dynamic resolution, 1600x900 in this scene: depth (ser 802, format `0x36`), the G-buffer and lighting targets (863, 1337, 1341, 1348/1349, 3208, 1305) and the post-processed scene (3232), half-size 800x450 targets for effects, all written by draws (19 passes on the depth, 12 on 3208). A frame runs 9 dispatches, and only three of them bind written images.
- Written as compute images: two 1920x1080 targets. `b0fe425c26f12012` is an FSR-style upscale: it reads the 1600x900 scene (3232) with 48 `gather`s at normalized coordinates and writes ser 25094; `0ee13624ced0b38e`, a sharpening pass, reads 25094 with integer `read`s and writes 25095; a draw (`97b3b56827e33df2`) copies 25095 into the top-left quarter of the 3840x2160 swap chain. The third written image is a 4x1 texture (exposure). `2118ab534fac88c6` reads the lit scene 3208 in compute as a texture.
- The movies are drawn by `3aafef4169955790` into a 1920x1080 target (ser 44318); they have no 3D to scale.

So the scene targets only carry the flag, while the upscaler's output is written by compute with the game's thread-group counts and image coordinates. The host therefore scales IMAGE-flagged targets too and demotes a scaled texture to the game's size the first time a shader binds it as a written image (`ups_pick` and `image_prepare` in `nvn_mtl.m`); the swap chain stays at its size, as a target whose scaled size would pass 3840x2160 is not scaled.

Result at 2x (same day, first field): the 1600x900 depth, G-buffer (its two 4-layer 2D arrays included), lighting and scene targets are made at 3200x1800 and stay scaled (24 made, 3 demoted), the game's FSR-style upscale gathers from the 3200x1800 scene, and the field is clean (0 red lines). The three demotions: the upscaler's compute-written outputs 25094 / 25095 ("a shader writes it as an image") and the 1920x1080 depth ser 6, which the pass that copies into the 3840x2160 swap chain clears. The first version brought the 3D back to 1600x900 through one chain of mixed-pass demotions (the unscalable swap chain → ser 6 → the scene 3232 → depth 802 → every G-buffer target); two rules broke it. (1) A pass whose depth disagrees with its colours on the factor runs the depth lookahead (`pass_ds_need`) on the Mac too, and a depth no draw of the pass tests is neither attached nor part of the vote: KTGL draws the swap-chain copy and the scene composite with the depth test off and the depth write on, which writes nothing (as in GL; the host's depth-stencil state sets Metal's write only under the test), and the lookahead now counts a write only under the test. (2) Single-level 2D arrays of up to 8 layers scale (`nvn_ups_shape_ok`): the translator scales integer fetches on 2D arrays as on 2D textures, the host's copies run per layer, and a demotion draws every layer down. Cost on the 16 GB Mac: frame time p50 21.3 ms, GPU-bound (NVN submit + present p50 19.7 ms), against 16.8 ms with the chain demoted; 1.5x has not been measured.

## GPU hang in a battle (open)

On 2026-11-04 the Mac app froze in the first outpost mission while a special attack filled the screen, after 18 minutes at a locked 60 fps (host 48b9911e, `DM_UPSCALE=2` scaling nothing yet). The game kept running (its threads poll and wait) while the GPU showed 100 % utilization for minutes and the host's submit thread waited without a timeout for the oldest submission's fence (`mtl_wait_at`, site WS_ALLOC): the picture froze in silence. The evidence is in the work folder's `logs/freeze-20261104-1938/` (host log, a 5 s `sample`, the pipeline ledger) with a README.

- The four pipeline bases compiled at that instant are (`c13c00c6b467d521`, `1bcc1a39c37f54eb`), (`fd6f2ce7f7046571`, `8d7d98c7b654f6b3`), (`41671ebe006f5bd4`, `328b6d7aa0940939`) and (`4a2396e4f9fea11b`, `f07838d26866e16b`). Pixel shaders `1bcc1a39c37f54eb` and `328b6d7aa0940939` (both from `/b6e28c40/0x38f972af.fdata`, IDRK@0x2f394788) hold KTGL's clustered-lighting loops: the cluster index comes from `gl_FragCoord`, the scene depth (slot 3) and the constants `c3[15..18]` (row and slice strides, z mapping); texel `2i` of the list in slot 16 is the cluster's offset into the index list and texel `2i + 1` packs two counts (`>> 16` and `& 0xffff`); each count bounds a do-while loop that reads a light index from the list and the light's data from slots 17 to 21. A count read from the wrong place (a float's bits give 16,000 or more) runs the loop that often per pixel and the GPU never returns. The vertex shaders have no loops; the other two pixel shaders have none. The pipeline of `1bcc1a39c37f54eb` compiled at the freeze differs from the one its draws use in the first battle only in the blend state (src alpha ONE, dst alpha ONE_MINUS_SRC_ALPHA): the same shader in another material pass, as the special's effect would use.
- The list is a texture buffer of 1,012,000 R32 elements (NVN format `0xb`, serial 3013 in a headless run), zero copy over the pool, bound as 16,384-texel rows (`tbuf_as_2d`) and viewed as R32Float since the shader declares float ([Integer buffer textures read through float slots](../../../docs/reference/rendering.md#integer-buffer-textures-read-through-float-slots)). Checked on this Mac (M2 Pro): such a view returns every bit pattern unchanged, denormal and NaN ones included, and a read past the view's edge returns 0, so an index past the list cannot make a count. The slots 17 to 21 hold RGBA32Float buffers of 1,024 and 3,072 elements and R32 ones of 3,072 and 192; no compute dispatch writes the list (the game's CPU does), and all texture IDs the draws bind lie in the first of the game's two 33,024-entry descriptor pools.
- Not reproduced: the first battle (the village, reached with the route under [Driving it on the Mac](#driving-it-on-the-mac)) draws those pixel shaders at 1x and at 2x and never hangs, but its list is empty in every dump taken (count 0 in every cluster), so the loops never ran there; the special attack's gauge never filled in the scripted rounds, and the outpost mission was not reached headless. The texel the loop read at the freeze is therefore still unknown.
- The host now reports such a hang ([A GPU that never finishes: the hang watchdog](../../../docs/reference/rendering.md#a-gpu-that-never-finishes-the-hang-watchdog)): a `[RED] GPU watchdog` line names the pipelines of the submission the GPU is stuck on. To play on past a fragment shader it names, `DM_NVN_SKIP_FS=<key>` in `~/Library/Application Support/nxnative/04003F40232DE000/env.txt` drops its draws (the effect is missing, nothing else). Next: reach the outpost mission with the watchdog host, `DM_NVN_PASSDUMP_ALL=1` and `DM_NVN_CBDUMP` set, `passdump 3` and a `memdump` of the list right at the special (the scratch scripts `fight2.sh` / `lightlist.py` of the 2026-11-04 session do that), and compare the counts with the pixels' cluster indices.

## Saves

- The save is one file, `DATA.BIN` (8 MB). A new save creates it at boot with its defaults (operation 0 of the game's file request routine, `main+0x1325be0`); every boot reads its header and three areas (operations 1, 6, 7 and 8).
- The game writes it at its autosave points (operation 2; four of its nine write requests come from the state machine of the save manager, a sequence the game creates only when it saves, `main+0x15463d4`). The opening and the first field reach none, so until then every boot starts at the first-run settings again. Checked: in a 12-minute playtest the game asked for no write and called no file or SDK function to save.
- The autosave icon in the lower right corner after confirming the first-run settings is not a write: the game makes no request and no SDK call while it shows.
- A save written at an autosave point and loaded again has not been seen yet.

## Driving it on the Mac

Run headless: `DM_WINDOW` set to anything, `0` too, opens a window, and a covered window takes the focus away (`oe focus state → 2`), which slows the display link to about once a second and holds `DM_CTL` screenshots. Shots of the 3840x2160 swap chain hold the 1920x1080 picture in its top-left quarter. From a new save: about 40 s to the settings screen, `A` (Next), `A` (Yes), `A` at the autosave notice, then the movies and cutscenes, `A` every 25 s or so; two taps of `Plus` skip a movie (one tap does not), and in the field `Plus` opens the pause menu, which `B` closes. Zelda is in the field about 8 minutes after boot, and `LUp` walks. Presses during fades are lost. The work folder has `boot.sh`, `ctl.sh`, `see.sh`, `shaders.sh` and `to_field.sh`. From the field (pause menu open) to the first battle in about 4 minutes at 1x, each hold followed by a wait of its length: `B`; `LUp~6` eleven times (straight through the stone arch and past its right pillar, along the dirt path to the egg-shaped shrine stone and the crates; the companions walk off to the right, do not follow them); `LDown~2`, `LLeft~3`, `LUp~5`, `Minus`, `RRight~0.8` three times, `LUp~3` six times, `LUp~4` six times (the village); then the movies, each skipped with `Plus` twice, and `B`, `Plus`, `B`, `Plus`, `B` (a pause screen over the battle, closed with `B`). At 2x the game runs slower, so the holds move less: about nineteen `LUp~6` to the crates and seven more `LUp~4` before the village. In the battle `Y` attacks and `A` is the special attack once its gauge is full; the first battle ends after a few minutes.

## Cheats

[`HWAoI.cheats.toml`](HWAoI.cheats.toml) is the anchored source ([Cheats that survive game updates](../../../docs/development.md#cheats-that-survive-game-updates)) of two code patches; [`mkcheat.py`](mkcheat.py) assembles them with clang and writes the plain `659CB288B5C5B2B4.txt` of this build, from which the source was imported. No public cheat file exists for this Switch 2 title (GBAtemp, VGChartz, GameFAQs checked 2026-11-04).

- **One hit kill**: every unit hit by a playable character loses all its HP. **Infinite health**: a playable character never loses HP. Both tested in the first Depths mission ("Dove riposa l'antica saggezza") from a save past the first outpost mission: grunts, captains and the boss fall on the first hit, and enemy attacks still hurt without the second cheat.
- **The mechanism.** The game keeps its units in a table of 200 entries of 0x74 bytes at `[[[main+0x284e590]] + 0x1a24b18] + 0x374430`, indexed by unit id: HP `+0x4c` (float), the HP before the last change `+0x50`, max HP `+0x54`, flags `+0x5c` (bit 2 marks a playable unit: the KO credit and the invincibility mode key on it), the character id `+6`. The routine at `main+0x11c5ce0` applies every HP change: `w0` the victim's unit id, `s0` the delta (negative for damage), `w2` the attacker's unit id; at `0x11c5da0` it computes `new = old + delta` (`fadd s0, s1, s0`, with `s1` the old HP, `s2` the max HP, `s3` 1.0 and `w8` the victim's flags) and at `0x11c5dc0` clamps the result (`fcmp s0, s3`), stores it at `+0x4c` and clears flag bit 0 when it reached 0. `ApplyDamage` (`main+0x1153bf0`) calls it with `delta = -damage` and keeps a protected unit at 1 HP when its bit 0 argument is set (story units).
- **The patches.** Each replaces one word with a branch to a stub in the zero padding after the text (`cave`, 0x1ed71c0 in this build, 3.6 KB the rewriter leaves alone) that does the original work and branches back. One hit kill (`cave+0`, 18 words): when the attacker's entry has flag bit 2 and the delta is negative, the delta becomes `-max HP`, so the victim's HP clamps to 0; the stub reaches the table through `x22` (the global object, loaded by the routine's prologue) and redoes the `fcmp s1, s3` the next instruction expects. Infinite health (`cave+0x60`, 6 words): when the victim has bit 2 and the new HP is below the old, the old HP is kept. The stride, the field offsets and the table's offsets inside the global object are baked into the first stub: an update that moves them needs them re-read (the anchors carry only the code sites and the cave).
- **How it was found.** Static search was blind (`main` is stripped: 58 defined dynamic symbols, no RTTI, hashed gameplay strings), and whole-heap diffs between snapshots (`DM_CTL` `memdump` of the populated heap, 7 GB a shot) kept surfacing animation and UI data: the KO counter is drawn from a text mesh, and the enemy HP bars are gauge widgets (`main+0xced51c` stores value and max at `+0x14/+0x18`). What worked: a diff for adjacent `(HP, max HP)` float pairs with `HP == max` before the hit (Age of Calamity's layout) found the unit table; an lldb write watchpoint on the boss's HP word (an SB API script, attached with `EXC_BAD_ACCESS` ignored and `SIGSEGV` / `SIGBUS` passed through) caught the store in `main+0x11c5ce0` with `ApplyDamage` as its caller. The run was a game window (`DM_WINDOW=1`) on a copy of the save, with the user steering to the fights; `DM_PROBE` counters on `add w11, w10, #1` / `csinc` sites fired on nothing useful.

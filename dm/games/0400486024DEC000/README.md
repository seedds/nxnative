# The Legend of Zelda: Ocarina of Time

The combined Mac branch runs standalone update `v131072` through the opening movie, Link's house, its exit, Saria's dialogue and Kokiri Forest movement, with save/reload working. The missing terrain height data is fixed and the ground remains intact while walking through the village. This is early-game validation, not a complete playthrough. VideoToolbox decodes the 1920×1080 AV1 track; the movie library runs its NDVE compute shaders.

## Profile

SDK 22.2.8, NVN API 231.40, with Nintendo's sead, agl and gsys. The three loaded modules are `main`, `subsdk0` (NintendoSDK_movie), and `sdk`. The NPDM declares 48 MiB of system resources. Startup requests a 6.20 GiB heap, which fits in the profile's 12 GiB reservation with the stack and alias regions. The registered versions are `v0` and standalone update `v131072`, whose three module build IDs match. The shader tables are generated from `v131072`; other available versions can use derived profiles.

## Mac dry run

For the registered standalone update, set `WORK` to its `0400486024DEC000_build` folder. Build the host with `make -C dm/host GAME=0400486024DEC000` and use the [Mac shader build](../../../docs/development.md#build-by-hand-mac).

```sh
mkdir -p "$WORK/run/save" "$WORK/run/temp"
DM_ROOT="$WORK" DM_ROMFS="$WORK/extract/v131072/RomFS.img" DM_SAVE="$WORK/run/save" \
  DM_TEMP="$WORK/run/temp" DM_MSL_DIR="$WORK/shader/cache" DM_FONT_DIR="$WORK/font" \
  DM_NVN_SHMAP="$PWD/dm/games/0400486024DEC000/shader_map.tsv" \
  DM_PSO_BUNDLE="$WORK/pso/mac" \
  DM_WINDOW=1 DM_METAL_HUD=1 DM_FOCUS_KEEP=1 DM_AUDIO=1 \
  dm/host/dmhost "$WORK/patched_v131072"
```

`DM_FOCUS_KEEP=1` lets the title keep playing while another app has focus. The original profile prewarmed the 11 NDVE compute pipelines used by the title. The integration branch also records 1,397 render, compute and native mesh recipes from the opening, house and forest route; unseen later-game pipelines still compile on demand. On the Apple M5 that took 17.7 s on a cold run, with a progress screen, and 7 ms with the archive warm. Compiling the same pipelines during the first submission had blocked the first movie frame for tens of seconds. The larger scene shader set also triggers a separate graphics-pipeline prebuild. On the first run with that set, the startup screen took 86.9 s to hand out all pairs, and the remaining workers finished after 110.6 s total.

Start a new game to reproduce the opening scene transition. With the test save and title flow, `DM_KEYS=f2600:A,f2950:A` advances the menu automatically. `DM_NVN_SHDUMP` saves control sections and code for missing keys to the directory it names.

For a run past the opening, use your own saved checkpoint in the new run's `DM_SAVE` and load slot 00 from the menu. The checkpoint contains both `slot_00/progress.sav` and `slot_00/caption.sav`. The load screen identifies it as **Kokiri Forest Autosave**. A windowed reload reached the playable scene with the HUD and controls, so rendering can be tested without replaying the movie.

## Save format inspection (2026-11-06)

Read-only inspection of v131072 saves decodes all twelve copied files without changing the originals. The little-endian header has magic `0x01020304`, schema revision `2982123` and a record-table end at offset 8. Revision and per-file table boundaries match the game's `GameData/GameDataList.Product.110.byml.zs` metadata. Eight-byte records from `0x28` contain a field hash and an inline scalar or absolute payload offset, grouped by type markers. The schema resolves all 11,925 ordinary records per progress save and 46 per caption; binary caption data contains a JPEG. The remaining progress-save tail is a zero-terminated list of 64-bit keys matching `Bool64bitKey` definitions. The decoder bounds-checks its reads and accounts for every byte in the copied files.

Named, schema-confirmed fields include `PlayerStatus.SavePos` (three float32 coordinates), `Sequence_CurrentBanc` (String64 scene), `Sequence_IsChildhood`, health and rupees. Names use MurmurHash3 x86-32 with seed zero. Most field names remain unresolved even though their types and storage are decoded. **Open:** no edited save has been loaded, loader integrity checks are not established, and scene/position edits alone are not proof of valid late-game state. The performance campaign remains paused. Local evidence and the read-only decoder are in the build folder's `diagnostics/save-format-inspection/`; extracted schemas and saves remain outside the repository.

The installed `b0080664dbb1` Mac candidate loaded a copy of the Great Deku Tree manual save, defeated the Skulltula and collected its token with a running jump. Two runs advanced both dialogue pages and resumed movement; the reported sustained freeze was not reproduced. The first run, with attempted CPU sampling, recorded a 22.79 ms audio render maximum and 13 additional catch-up renders; the user heard corruption. A repeat without CPU sampling recorded zero catch-up renders and zero device underruns, with audio render maxima of 0.16–0.17 ms around pickup. Its 10-second PCM16 stereo capture had no clipped samples or all-zero 5 ms blocks; this does not exclude every audible artifact or problems after the PCM capture point. The largest logged frame in the eight-second pickup window was 25.5 ms, and pipeline creation was zero. ## Performance measurements (M4 Max)

The `kokiri-stand` route in `bench.tsv` reloads the same forest save, then measures seconds 70–130. Two runs with the game's upscaler averaged 48.4 and 52.0 FPS; frame p99 was 35.29 and 22.81 ms, with maxima of 76.66 and 52.59 ms. Two runs requesting MetalFX measured 51.6 and 51.7 FPS, but no replacement dispatch was observed in this scene, so that difference is not an established MetalFX improvement. No build ran during measurement. Other macOS background services remained active.

A diagnostic docked/handheld comparison measured 52.5/55.3 FPS, frame p99 22.28/21.66 ms and maxima 64.94/65.48 ms. Handheld reduced the main pass from 1536×864 to 1440×810 and the large shadow map from 1600² to 1000²; it still did not hold 60 FPS. Both screenshots show the same loaded scene. This quality tradeoff is not made the default.

A separate diagnostic run sampled GPU spans of 16.85–17.84 ms at frames 4,200–6,000. The 1536×864 main colour/depth passes consumed about 7.6 ms summed per frame, compute/copy about 5.5 ms, and attachment traffic was about 444 MB loaded / 411 MB stored. Encoder timestamps can overlap; their sum is not total frame time. The route also has CPU submission spikes without pipeline compilation. These results do not meet locked 60 FPS. Higher-rate game timing has not been validated; raising the host cap alone is insufficient.

The transient-descriptor expiry candidate passed the full graphics suite. Two camera-route pairs in opposite orders measured controls at 50.8 and 49.2 FPS, candidates at 49.4 and 51.6 FPS. CPU submission p99 was 24.60 → 25.85 ms in the first pair and 21.71 → 13.59 ms in the second. All four screenshots retain the forest scene, but camera angles differ, especially in the first pair. These results do not establish a consistent FPS gain or pixel equivalence. No resolution, effects or quality setting was reduced.

The preceding LDSM chain `79ea0bfc5308` built all 42,850 shaders. Against the prior integrated build, the full static regression reports 41 changed MSL sources, no changed reflections or variants, no new compilation failures and no mismatch across 33,190 checked shader interfaces. Only this locally available game was checked, and that run did not include boot smoke. The O3 compiler chain `e2b3f72646e1` subsequently built all 42,850 shaders with no losses. Its comparison against chain 79 found no changed MSL or reflection, no newly failing shaders, and 33,190 checked interfaces with no mismatch. This establishes build/interface coverage, not a gameplay speedup.

## Frame rate

Upstream measurements (not revalidated on this branch): measured on an M6 Mac with 16 GB, headless, on one walk with camera turns (`walk.sh` in the work folder).

- Current: the title and menu, a movie behind them, are a locked 60 fps (p50 16.67 ms, GPU span 15.6 ms).
- Current: walking the village at the game's top internal resolution, 1536x864: a locked 60 fps, mean 16.67 ms over each settled window. Per 2,700 frames: 0-8 frames over 25 ms and 0-2 over 33 ms. Frame p95 17.8-18.9 ms with no window, as the game's own loop moves around its fence wait; in a window p95 17.8 ms, 3 over 25 ms and 5-16 over 18 ms per 600. GPU span p50 16.5 ms, summed GPU 15.8 ms, CPU 6 ms, about 101 passes a frame. The heavy stretch where the village opens (about 1,560 draws) holds 16.65-16.8 ms by lowering its resolution, then returns to full. The main pass used to sit at 763x429 at the same GPU time: [marked shaders tested depth late](../../../docs/reference/frame-rate.md#a-hosts-own-store-in-a-fragment-shader-moves-its-depth-test).
- Before [pool shaders stopped counting as depth readers](../../../docs/reference/rendering.md#pool-shaders-taken-as-depth-readers): passes 118, 104, 219, 224 in a four-frame cycle, frame times 15, 15, 18, 18.5 ms, mean 16.9 ms. Half the frames rendered the reflection probe's faces with one draw a pass.
- The host's GPU figure adds up command buffers, which overlap, so it reads above the real span: 17.5 ms was never a frame's real time. The real span is `@gpu_end_ms − @gpu_beg_ms` in `DM_NVN_TSV`, or the `first start to last end` of `DM_NVN_GPUPROF`.
- The roughly 1 ms the [wind fix](../../../docs/reference/shaders.md#dead-code-removal-dropped-a-coordinate-of-a-multi-output-instruction) seemed to add: 0.66 ms of it is the upscaler, 416 → 1076 µs, because its variants then read what they had lost. It is doing its real work.
- Attachment traffic was not the cost it looked: 254 MB load and 277 MB store remain, and the cheapest passes move 20 MB in about 30 µs. The pass count was the cost.
- Resolved: 25-40 ms frames while the GPU sat idle with the next command buffer committed, 51-75 per 2,700 in a bad run: [the GPU idles with the next command buffer already committed](../../../docs/reference/frame-rate.md#the-gpu-idles-with-the-next-command-buffer-already-committed). What holds Metal's submission queue in the kernel is still unknown.
- The title movie's network took 14.8 ms of compute a frame here (median from frame 3,000), so the title held 60 fps with almost nothing to spare, and slower GPUs fell below it: [issue 1375](https://github.com/seedds/nxnative/issues/1375), 35 ms on an M1 Max. Since [HMMA chains keep their matrices in the SIMD-group](../../../docs/reference/shaders.md#hmma-chains-keep-their-matrices-in-the-simd-group), 11.4 ms, and the GPU span 11.9 ms instead of 15.6 (26.7 → 18.9 ms of compute on an M4 with 8 GPU cores). Not measured on an M1 Max since.

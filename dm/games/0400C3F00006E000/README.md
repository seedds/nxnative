# Mario Kart World (`0400C3F00006E000`)

A Switch 2 game: update 1.8.0 (v917504) over the base game, SDK 21.4.0 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive), modules `main` + `subsdk0` (NintendoSDK movie) + `subsdk1` (C library) + `sdk`. **Plays on the Mac** (Apple M3 Max, macOS 27.0.1), with open items ([Open](#open)): boot, the title, the main menu and the first race of the 150cc Mushroom Cup Grand Prix (Mario Bros. Circuit), all 3 laps, driven by hand (the user's run `user_check.log`, 2026-11-01, chain a8e15f3b482b); a later run to frame about 13,200 had no crash. A second run (`user_race2.log`, 2026-11-01, recorded to `user_race2.keys`) drove two races of the Shell Cup by hand in a row, to frame about 32,100 with no crash; the same 20 shaders failed to load (no new one on these courses) and `nvnCommandBufferDrawMeshTasks` was called 9,697 times. The user saw the water's textures and some ground textures missing (fixed: [Rendering](#rendering)); otherwise it played. The kart drives and takes items; the scripted run to the first race had a p50 frame time of 16.6 ms (about 60 fps). Some geometry is missing (task / mesh shaders) and the first use of each pipeline compiles it. iOS is not tested.

- Full Mac build (chain bf7b068a0b02; a9e0bbe888ad and b7cd656abd7c the same count, about 25 minutes from an empty cache): 11,524 of 11,604 translate (11,522 on chain 3c66991eb439; the two agl compute shaders with 0x593, SUATOM, translate since the chain decodes it). On chain a8e15f3b482b, with 0x2be (UBREV) decoded, 67 fail: 12 of the 25 0x2be shaders fail next on 0x927 (26 in all); of the 67, 25 load on the route to the first race. - Resolved: 168 compute shaders of `DrivePassShaderDefault.sharcb` declare 48 KB of shared memory (the control section's +0x64), past an Apple GPU's 32 KB; Metal refused their pipelines and the host skipped their dispatches. Seven run up to the first race (`04dedc705a7ef88b`, `2a89b6d4df731b8d`, `7caf175d0e2ada58`, `a8310cf7c7acd0fe`, `c37db932f3076403`, `c9347f7c454a68a4`, `e2a5bd13907993e3`): 64 threads, no shared atomics, three with a barrier. Since chain a9e0bbe888ad their shared memory is a slice of a device buffer ([Compute shared memory past 32 KB](../../../docs/reference/shaders.md#compute-shared-memory-past-32-kb)): their pipelines are made, and on the route to the first race every dispatch fit a 1 MB buffer. The picture showed no change.
- Resolved: no shader is missing from the map. A run to the first race with `DM_NVN_SHDUMP` dumped nothing and logged no `is not in the shader map` line; the 37 `failed to load shader` keys of that route are all in the map, and are the translation failures above, not runtime-only shaders.
- Resolved: the boot crash at `main+0xd1c6e4`. With the UBREV shaders skipped, compute shader `18dd278d143adfd4` appended its records past its storage buffer into heap objects beside it (main's BREV decode covers UBREV: [Texture handles of SDK 22's Ampere code](../../../docs/reference/shaders.md#texture-handles-of-sdk-22s-ampere-code)). With the UBREV shaders translated (chain a8e15f3b482b, an earlier decode of the same instruction) it wrote no record out of range. Probably resolved, not proven: the race crash at `main+0x1a43e4` (about frame 14,700 of race 1, 4 runs in 5). Its object lies in the page slack of a memory pool and a GPU write overwrote it, as at boot; one run through race 1 with driving to frame 15,900 on the new chain had no crash. The object was not watched after the fix.
- The translator warns `Attribute offset 0x5C is not valid.` in 2,838 shaders (Donkey Kong Bananza's build has none). Open: not analysed.

## Rendering

The scene renders into 2048x1152 targets (RGBA16F colour). The window textures are 3840x2160, and the game draws its picture into their top left 2048x1152 and crops the window to it (`nvnWindowSetCrop`, `WindowCrop 0,0 2048x1152` in the log; 2560x1440 at the first frames). The window shows the crop. A `DM_NVN_SHOT` or `DM_CTL` `shot` without `DM_NVN_SHOT_OUT` saves the whole window texture, so the picture fills only its top left: take screenshots with `DM_NVN_SHOT_OUT=1920x1080`.

On the way to the title:

1. Black 3D scene: only the 2D layout ("Press L + R to start", "Ver. 1.8.0") over black with a few specks. The clears under render conditions ran unconditionally (`render_cond`, [What it needs](#what-it-needs)).

On the way to the first race:

1. The Grand Prix's cup opening movie (`Movie/KinokoOp.webm`) did not show: the screen kept the last 3D frame for its 23 s while every picture was decoded and read. The YUV pass writes an `RGBA8` render target and the composite samples an `RGBA8_SRGB` texture over the same memory; the host made them two Metal textures ([Textures of an sRGB / linear pair over the same storage](../../../docs/reference/rendering.md#textures-of-an-srgb--linear-pair-over-the-same-storage)).
2. Vertical rainbow bands in the bright parts of the 3D scene (the sky near the horizon, the water, the lit floors; in the tunnel the floor turned white with cyan bands), a dark band with rainbow streaks and a grey column in the title's sky, and large pale shapes in the flyover's sky. The bloom's bright pass (`c44cb8e46dbcfd4f`) colours what it extracts by luminance and showed them most, but they came from the volumetric fog: its compute shader `fd413f04f59c161e` writes the 68x40x256 scattering volume (`RGBA16F`, with an `R8` volume beside it) after a reduction through shared memory, and in that volume each group of four texels along x held four values rotated by x % 4 (a `DM_NVN_TEXRAW` dump at frame 9480). The translator took the address register of `LDS.128 [Ra.X16 + imm]` unscaled; main's decoder scales it by the stride ([Scaled shared memory addresses](../../../docs/reference/shaders.md#scaled-shared-memory-addresses)). With the address scaled (chain bf7b068a0b02, an earlier decode of the same field) the scene showed none of them.

The title and the main menu match the game as it is known: the title drives Mario's kart through Mario Bros. Circuit (the canyon, the tunnel with the course's name) with "Press L + R to start" and "Ver. 1.8.0"; L + R opens the main menu over the same drive, with Single Player (selected, the 1P marker), Multiplayer, Online Play, Wireless Play, three round buttons and "Free Roam" on the + button. What differs is in [Open](#open).

The first race matches the game as it is known: after "Start Grand Prix?" the map of the cup's courses, the Mushroom Cup movie (Mario Bros. Circuit, Crown City, Whistlestop Summit, DK Spaceport, the cup's emblem), the course flyover, the grid at the Mario Kart arch with Lakitu's lights, 3, 2, 1, GO!, the HUD (coins, lap 1/3, place, the course map, the item box). The rainbow bands of the sky, the water and the lit floors are resolved (item 2 above).

In the open world:

1. The flat ground behind the title (one flat colour on a flat plane: the snow course, under Bowser's castle, over the water) and the ground and water textures missing in the Shell Cup run. The open-world terrain is drawn as patches whose uncompressed maps (a 260x260 R16 heightmap, RG8, RGBA8, R11G11B10F and a 68x68 RGBA16 map) the game writes from the CPU, without a flush, into a `CPU_CACHED | GPU_CACHED` pool the GPU never writes; the host made them textures of zeros, so every patch was a flat plane. Uncompressed textures now take their storage at first use in a pool with no GPU write ([Uncompressed storage the CPU wrote, in a pool the GPU does not write](../../../docs/reference/nvn-objects.md#uncompressed-storage-the-cpu-wrote-in-a-pool-the-gpu-does-not-write)). Checked 2026-11-02: the title run (`fx2_4250.png`) shows rolling grass hills with dirt paths, and the user's Shell Cup recording replayed to its first race (Koopa Troopa Beach, `fx1_10000/10500/11000.png`) shows textured sand and water.

## Boot (Mac)

Each step below stopped the boot before its fix:

1. A null memory block in `nnMain` (`CRASH sig=11 addr=0x10 pc=main+0x5dd3ac`): the game allocates a fixed 7.04 GB block from its heap, which the Switch 1 pool could not hold. The Switch 2 pool, 9 GB (`app_pool`, [What it needs](#what-it-needs)).
2. `nn::diag abort: Result 0xe15` in `hid::InitializeNmouse`, then in `chat::Initialize` (GameChat), then `CheckGraphicsSystemInitialized` before the camera context: Switch 2 services the host does not serve. Answered with nothing connected ([Switch 2 mouse, GameChat and camera with nothing connected](../../../docs/reference/services.md#switch-2-mouse-gamechat-and-camera-with-nothing-connected)). The chat camera storage needed NVN2 native images ([NVN2 native images](../../../docs/reference/nvn-objects.md#nvn2-native-images)); the camera session fails "open camera" with the result the game takes as "no camera".
3. `CRASH pc=0` after `vi::SetLayerNextHdrAdjustableBezierMetadata` (`main+0x959ae4`), in the first frames ([Switch 2 HDR metadata on a layer the host never made](../../../docs/reference/services.md#switch-2-hdr-metadata-on-a-layer-the-host-never-made)).
4. GPU out of memory after about 90 frames (`kIOGPUCommandBufferCallbackErrorOutOfMemory`, then the present watchdog; "GPU allocated" 21 to 24 GB): six sparse terrain arrays of 8192x8192x68 with 12 levels (two of 6.1 GB, format 0x50; four of 1.5 GB, ASTC 8x8) in virtual pools the game maps only in part, made as whole textures. Now Metal placement sparse textures, mapped and filled tile by tile from the page table ([Sparse textures in sparse virtual pools as Metal placement sparse textures](../../../docs/reference/nvn-objects.md#sparse-textures-in-sparse-virtual-pools-as-metal-placement-sparse-textures)): after 60 s 26,593 Metal tiles (1.7 GB) in 7 heaps, GPU allocated 14.2 GB, process footprint 12.6 GiB (with the 9 GB pool).

To the main menu (Mac): `DM_KEYS=f4000:L+R~0.5` from a fresh save. The title asks for L + R from about frame 3400 and the main menu shows by frame 4300 (with `DM_PRESENT_LINK=0`, so a window behind others still presents every frame). No movie started and no `nv::InitCheck` abort came in 3 minutes on the title without input (#834 saw one when the attract movie started).

5. `game called nn::diag abort: Result 0, call site sdk+0x32f998` when the Grand Prix's movie starts (after "Start Grand Prix?" OK, about frame 8900): the movie player (`subsdk0`, `movie::VideoDecoder::Configure`) calls SDK 21's `nn::codec::InitializeVp9DecoderByTransferMemory`, which the host did not take over then, and the SDK's own one aborted on the decoder service. Main's SDK 22 decoder forms take over the same names ([AV1 movies through SDK 22's decoder](../../../docs/reference/movies.md#av1-movies-through-sdk-22s-decoder)). The movie is VP9 2560x1440, 1,423 pictures, output mode 1, read as NV12.

To the first race (Mac): the steps of `keys_race.txt` in the work folder, from a fresh save: `f4000:L+R~0.5, f4800:A` (Single Player), `f5200:A` (Grand Prix), `f5600:A` (Mario), `f6000:A` (Standard Kart), `f6400:A` (Mushroom Cup), `f6800:Right~0.2, f6900:Right~0.2, f7100:A` (150cc), `f7500:A` ("Start Grand Prix?" OK), `f10350:A~20` (drive). The movie runs from about frame 7860 to 9240, the countdown's 3 at about frame 10050 and GO! at about 10230 (the countdown at the same frames in three runs). Race frames: p50 16.6 ms, GPU 10–14 ms; footprint 14.4 GiB.

Memory after 60 s (`run11.log`): GPU allocated 14.2 GB, footprint 12.6 GiB, 7 placement heaps of 256 MB.

## Open

- 20 shaders the route to the first race loads do not translate ([Shaders](#shaders)); their draws and dispatches are skipped. A run to frame 12,300 of race 1 on chain bcd4adc6f52c (`t7d_r1.log`) had no crash and no new kind of `[RED]` line against `user_check.log`; it logged 20 `failed to load shader` keys, 26 before.
  - 0x927 (26 shaders, 19 on the route) is ISBEWR, a write to the internal stage buffer entry (Mesa NAK `sm70_encode.rs` (main, read 2026-11-01) `OpIsbewr`, line 4334: offset register 24..32, data register 32..40, immediate offset 40..56, size 74..76, access 76..78 (map or attribute), skew 78, output 79). NAK's `from_nir.rs` emits it only from `nir_intrinsic_isbewr_nv`, the output path of task and mesh shaders (ISBERD is its read). Eden-NS2's `NX2_NOTES.md` (commit `b2cef0c`, rows 89 and 97) reports, for this game, task and mesh programs bound in stage slot 1 with a vertex-type SPH: the task program writes its payload with `ISBEWR.O.ATTR` and the mesh count with `ISBEWR [0x4]`; skipped, they give pop-in and low-quality LODs. Checked here: the split labels these 26 vertex (14) or domain (12), and only they have the SPH's word 4 bits 24..31 (Maxwell's StoreReqEnd) at 0xff; the 4 other vertex shaders the same build translated anew have 0 (the whole package not checked). Not checked: which draws bind them; the Task 7d run `t7d_r1.log` (to frame 12,300) calls `nvnCommandBufferDrawMeshTasks`, which the host does not implement, 2,849 times. Decoding ISBEWR alone would not draw them: they need a task / mesh pipeline.
  - 0x481 (compute shader `078997bf631992c5`) is not an instruction: the program starts with a 0x80-byte vertex-type SPH (word 0 `0x020c0481`), and its instructions from +0x80 are ALD, three FMUL, AST and EXIT. The split labels it compute (`cs_shader.bin` 162); its stage is not known.
  - 0x59f (compute shader `ab77eaee44cfef88`, on the route) is reached: `MOV R0, 1` then 0x59f with R4 and R0, before EXIT. Eden-NS2's notes (row 88) count one SURED among this game's programs that its lowering leaves; no source gives 0x59f's fields (Mesa NAK has no encoder for it, nor Eden-NS2's opcode table), so it is not decoded.
- Task / mesh draws are missing: `nvnCommandBufferDrawMeshTasks` is not implemented (4,031 calls in the user's race 1 run `user_7d2.log`, 2,849 in the Task 7d run `t7d_r1.log`; 302 in 60 s of the route's first minute), and the 26 task / mesh shaders (ISBEWR, 0x927) do not translate. The geometry they draw is missing (Eden-NS2's notes: pop-in, low-detail LODs). Mesa NVK describes the model: [Mesh Shading Notes](https://docs.mesa3d.org/drivers/nvk/mesh_shading_notes.html) and its [ISBE layout](https://docs.mesa3d.org/drivers/nvk/isbe_layout.html) page. The Ampere ISBEWR encoding is in the 0x927 item above.
- `nvnCommandBufferShadingRateImagePalette` and `BindShadingRateImage` are not implemented (about 2,800 calls a race): the game draws at the full pixel rate. Unknown names: `nvn*CooperativeVectorMatrix*`, `nvn*PoolWriteDescriptorTableData`.
- The 0x59f instruction of `ab77eaee44cfef88` is named SURED (immediate form) in Mel's nvdisasm opcode list, <https://gitlab.freedesktop.org/mhenning/re/-/tree/main/opclass>, `opclass86`); its fields are not known.
- Program `078997bf631992c5` (0x481 above) is labelled compute by the split but starts with a vertex-type SPH: the split's stage label is wrong for it.
- Under `DM_DETCLOCK` the game stops after frame 3 (`user_7d.log`; inferred from comparing logs, not proven): runs and recordings go without it.
- Not done: the prewarm seed list (`pso_manifest.tsv`), so each pipeline compiles at its first use.
- The display link stalled 7 times in the first 50 s (`display link recovered: stalled … ms`), with 253 dropped frames up to frame 600; after that 2 dropped in 300 frames.
- The camera's other commands (29 at the first frames) fail as "no camera"; their meaning is not known.
- `pad_layout` and `app_category` are judgement, not measured.

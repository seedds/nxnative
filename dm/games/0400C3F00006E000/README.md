# Mario Kart World (`0400C3F00006E000`)

A Switch 2 game: update 1.8.0 (v917504) over the base game, SDK 21.4.0 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive), modules `main` + `subsdk0` (NintendoSDK movie) + `subsdk1` (C library) + `sdk`. **Plays on the Mac** (Apple M3 Max, macOS 27.0.1), with open items ([Open](#open)): boot, the title, the main menu and the first race of the 150cc Mushroom Cup Grand Prix (Mario Bros. Circuit), all 3 laps, driven by hand (the user's run `user_check.log`, 2026-11-01, chain a8e15f3b482b); a later run to frame about 13,200 had no crash. A second run (`user_race2.log`, 2026-11-01, recorded to `user_race2.keys`) drove two races of the Shell Cup by hand in a row, to frame about 32,100 with no crash; the same 20 shaders failed to load (no new one on these courses) and `nvnCommandBufferDrawMeshTasks` was called 9,697 times. The user saw the water's textures and some ground textures missing; otherwise it played. The kart drives and takes items; the scripted run to the first race had a p50 frame time of 16.6 ms (about 60 fps). Those historical runs lacked task/mesh geometry. The native implementation and current verification are recorded below; first use of each pipeline still compiles it. The isolated iPhone Duo port reaches gameplay; its remaining memory, frame-time and rendering work is recorded below.

## Terrain data written without NVN flushes (2026-11-02)

The large ground holes have a reproduced cause independent of task/mesh support. In a frozen photo-mode camera near Sunshine Railway, the procedural terrain colour pair `e25dcda134601471` / `9d0114392f7493d9` draws 376 patches. Its depth shader is `7744ac8816e42afc`; captured positions of the first 289-vertex patch match the colour shader bit for bit. Both sample a 260x260 R16_UNORM height tile.

Two bound tiles (serials 674084 and 698938) were entirely zero in GPU readbacks, while their guest storage contained 135,015 and 134,857 nonzero bytes respectively out of 152,064. They had `MINIMAL_LAYOUT`, no packaged layout, and lived in the same `CPU_CACHED | GPU_CACHED` pool (flags 0x24). Neither storage range overlapped any recorded NVN flush. The host therefore made zero-filled private textures instead of uploading the game's heights. In the same frozen scene, diagnostically uploading the registered height tiles restored the foreground slope and filled the large holes beside the road; the checked GPU height tile then matched the nonzero guest data. No depth override was enabled for this comparison.

The profile now enables the existing `tex_flush_upload` and `tex_dirty_upload` path: track writes from texture creation, upload the CPU's content and refresh streamed tiles. This is the existing explicit classification for games that publish uncompressed texture data outside NVN's flush API; the host cannot safely infer CPU ownership from nonzero bytes in every render target. See [CPU writes with no flush](../../../docs/reference/nvn-objects.md#cpu-writes-with-no-flush-caught-by-page-protection-tex_dirty_upload). The profile alone improved a fresh boot, but left streamed holes: 81 registered height tiles still held nonzero CPU data without a dirty generation after registration. Those had been filled before initialization. The host now also seeds a new backing from this initial storage under `tex_dirty_upload`, after checking for existing GPU aliases. A second bug discarded late uncompressed uploads because every sampled uncompressed texture has Metal render-target capability; ownership now records actual GPU destinations. See [initial and late CPU tiles](../../../docs/reference/nvn-objects.md#uncompressed-cpu-tiles-before-initialization-and-after-first-use).

Validation with both fixes: `t_late_texture` passes 39 GPU checks covering both upload timings and preservation of real render targets, aliases and format-view upgrades. The complete graphics test target passes, as do focused LLVM 23 lint and the documentation checks. Fresh-boot screenshots show the desert ground, slopes and cactus vegetation present. Short driving and successive fast travel through Whistlestop Summit, DK Pass, Sky-High Sundae, Dandelion Depths and Wario Shipyard preserve the visible ground; the shipyard photo-mode view also has a continuous water surface. The rebuilt standalone macOS bundle was separately launched with its own bundled host and assets: Crown City's roadside slopes are filled, and cactus/brush remain visible during a short off-road turnaround near Mario Bros. Circuit. Both runs used isolated saves and Metal validation, without a depth or culling override. These are sampled route checks, not proof that every distant LOD or vegetation transition is correct. Extended driving remains open.

## Distance-dependent instance loss (2026-11-02)

A second, independent cause of disappearing vegetation is confirmed in the GPU instance-list producer. Normal rendering consumes a compact list rebuilt when an active position changes a 64-unit cell. Photo mode selects a different, full list and forces refreshes; it can restore objects, but is not a complete rendering reference and must not be used as the expected image.

For 1.8.0, `main+0xa1d270` produces the list, called by `main+0x277e4c`; the owner flag at +0x93c bit 7 controls refresh. Compute programs `2ce9071c2f22d74f` (captured live) and `5fea9b7ddb30e8a8` reset four counter/indirect words from global invocation zero, then other workgroups append visible records. Their workgroup barrier cannot order different workgroups. Apple scheduling can run an append before the reset and erase the count; because this list survives across frames, missing objects remain absent until another cell refresh. Shadows and the photo-mode path can still draw them. The existing first-store lowering recognized Splatoon Raiders' single literal block, but missed these split blocks and their conditional constant alias. It now recognizes both forms and moves all four resets before the dispatch; see [dispatch-first stores](../../../docs/reference/shaders.md#a-store-only-a-dispatchs-first-invocation-makes).

Evidence is retained under `analysis/perf-20261102/compact-replay` and `lod-probe`: a GPU-timeline snapshot of 59,456 input records, five active positions and 929 workgroups. A separate CPU distance-filter reference expects 307 records. Replaying the original compute program 30 times with identical input produces counts ranging from 0 to 307 (including mismatched zero counts and nonzero indirect group counts). With the reset moved before dispatch, all 30 runs produce 307 records and 5 downstream groups. The resulting multiset of full 96-byte records matches the CPU reference exactly, with no missing or extra record. The second program independently matches all 2,273 CPU-expected records in 30 consecutive GPU runs (36 downstream groups), again with no missing or extra 96-byte record. This proves the compact-list race, not that every terrain/LOD defect has the same cause.

Integrated validation: `t_first_store` exercises the production Metal path, including preceding GPU writes, all four reset words and alternating direct/GPU-written indirect dispatches (101 checks, no failures with Metal validation). The complete graphics suite and focused lint pass. Chain `96064c74793c` rebuilds all 11,601 programs; compared with `6b2aba5d4d48`, only these two MSL outputs change. The static regression against the original PR has no newly failing shader or new pipeline interface failure (MKW only; other games and iOS remain unchecked). Windowless captures of normal free-roam rendering after a fresh boot show the desert ground and vegetation; several nearby positions in Boo Cinema retain visible trees, and DK Pass has continuous visible ground at arrival. These limited sampled views do not prove every object or distant LOD is complete; photo mode was not used as their reference. The HDR bundle now contains the corrected host and shader chain. It was separately launched through its bundled launcher with an isolated save; the log confirms chain `96064c74793c`, its own modules/shader assets, PQ HDR conversion and an RGBA16F drawable, and it reaches normal free roam with visible scenery. This packaging check does not use the experiment-only cache-toggle host.

## Dirty-range lookup cost (2026-11-02)

The historical `analysis/perf-20261102/live-slow.sample.txt` (PID 18980, not the current live process) contains 451 top-of-stack samples in `nvn_dirty_since`, repeatedly called by `nvn_sparse_since` during submission. Each physical run searched the dirty tracker's pool table again. The host now caches eight descriptor lookups per thread; the [shared reference entry](../../../docs/reference/nvn-objects.md#cached-dirty-range-lookups-with-overlapping-pools) records the selection rules, regression tests and CPU measurements.

Review found a correctness bug in the first cache version: two adjacent pools can share a rounded host page, and selecting the cached neighbour instead of the first containing descriptor can miss its protected neighbour's write. The corrected cache preserves the original first-match order and invalidates selections across registration, retirement and slot reuse. The overlap and cross-thread slot-reuse fixtures fail six assertions with the first cache, and pass with both HEAD and the correction.

The isolated CPU benchmark compares HEAD `0a759de7864b8c22bc0d9f596bb6b9a6f1c45486` with the corrected tracker on an M5 Max: repeated late-slot lookups improve substantially when the working set fits the cache, while streaming and misses can regress. It uses no Metal and never reads guest storage. Artifacts, exact sources and commands are retained in `analysis/perf-20261102/dirty-range-benchmark`. This establishes a component-level benefit, not an FPS improvement. Earlier two-run gameplay comparisons of the first cache were mixed. The corrected cache has now been rebuilt into the HDR app. Separate-process free-roam entries were rejected as a performance comparison because their attract-sequence spawn positions differed; their screenshots and rejection note are retained. A same-process diagnostic binary alternates the exact old scan and the corrected cache with unchanged shaders and no camera movement. In the windowless run, two 30-second windows per mode reduced median submission CPU time from 7.96/7.93 ms to 5.69/5.79 ms, and mean submission instructions from 183/181 million to 72/74 million per frame; mean draw counts stayed within 2,117–2,146. This is CPU-path evidence, not an on-screen presentation measurement. The HDR/windowed repetition confirms lower submission instructions (186/185 million without the cache versus 76/80 million with it). The first pair had compositor discards and one new pipeline, so it is not evidence of smoother presentation. In the second pair, with no newly created pipeline and no discarded presentation, both modes deliver 60 FPS; median submission CPU time is 8.09 ms versus 6.86 ms and the host frame-time p99 is 24.88 ms versus 17.46 ms. Mean draws are 2,105 versus 2,112; camera position stays fixed, but world time and lighting continue. Both modes have a 16.67 ms p99 on-screen interval: this demonstrates less CPU work and more headroom, not elimination of all visible stutter. Commands, experiment-only source, phase ranges, input recording (empty physical input), screenshots and per-frame data are retained in `analysis/perf-20261102/cache-controlled`. The toggle is not in the production host. Its actual hit rate, longer driving and other games remain unchecked.

### Follow-up: fullscreen GPU clocks (2026-11-03)

The user reports that the earlier visible stutter stopped after the dirty-range lookup fix. A separate observation on Rainbow Road is reproducible: GPU time rises from roughly 7 to 14–15 ms while the game remains at 60 FPS, and switching Spaces temporarily restores the shorter GPU time. This is not evidence of duplicated rendering work or exhausted peak GPU throughput.

Live measurements of the packaged HDR app (PID 51916, chain `96064c74793c`, M5 Max, macOS 27.0) align per-frame submission timings with one-second IOReport GPU-state samples using the process creation timestamp. The local `sgx` performance-state table maps active P-states to clock frequencies. In a 105-second interval the active-state weighted clock has a 595 MHz median and GPU time a 14.13 ms median; the host frame interval has a 16.67 ms median. A later 17-second interval has 1,588 MHz and 7.39 ms medians. The following 36-second interval returns to 663 MHz and 13.97 ms, with a 16.67 ms p99 on-screen interval and no discarded presentations in that interval. These are successive moving scenes, not an identical-camera optimization benchmark. The latter two windows have similar attachment traffic (about 480 MB loads and 613 MB stores per frame). IOReport labels their dominant power-controller states `PERF` and `SE`, respectively; those private labels are recorded without assigning an undocumented meaning to `SE`. Thermal state is nominal and Low Power Mode is off.

This supports frequency management as the explanation for the changing busy-time percentage; it does not establish the OS policy responsible for each transition. No frequency-forcing workaround has been added. Raw data, scripts, exact timing windows, renderer-pass samples and a Metal performance trace are retained under `analysis/reflections-focus-20261103`. The percentage displayed by a GPU activity monitor is not a measurement of electrical watts or the fraction of peak shader throughput. Overall system activity also includes the compositor.

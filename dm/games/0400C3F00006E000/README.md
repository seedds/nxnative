# Mario Kart World (`0400C3F00006E000`)

A Switch 2 game. Brought up on the base game (v0), SDK 19.3.3 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2 API 231.16. Nintendo EPD's engine (sead / agl / gsys, Phive, Havok, Pia), modules `main`, `subsdk0` (a Mono runtime, `nn::ecli`) and `sdk`. **Reaches a race on the Mac** (M6, 16 GB): the title, the main menu, the Single Player and Grand Prix menus, character, kart, cup and class selection, the Mushroom Cup's opening and the first race of Mario Bros. Circuit at 50cc, driven with items, at 60 fps on that Mac (see [Frame rate](#frame-rate)). Update 1.8.0 is packed from a profile derived from this one and reaches the first race on a Mac with the host's frame step (see [1.8.0](#180)). iOS is not tested.

| `modules main subsdk0 subsdk1 sdk` | `game.tsv` | the base game has no `subsdk1`; each build row names its own modules ([A version without one of the profile's modules](../../../docs/reference/packing.md#a-version-without-one-of-the-profiles-modules-stops-the-host-at-boot)) |
| `romfs_marker Movie/StaffRoll_00.webm` | `game.tsv` | a file of both versions' RomFS |

Render conditions, which the host evaluates for every game ([Conditional rendering evaluated at replay](../../../docs/reference/rendering.md#conditional-rendering-evaluated-at-replay); until 2026-11-12 the profile key `render_cond`): agl wraps its clears in render conditions, as in Donkey Kong Bananza and Splatoon Raiders; not tried without it here.

## Files

- Packed from a dump folder (`base/` only) with [`scripts/pack_dump.py`](../../../scripts/pack_dump.py): 205,902 RomFS entries, 21.7 GB.
- Shaders: 11,560 in [`shader_map.tsv`](shader_map.tsv) (compute 726, domain 12, pixel 7,261, vertex 3,561), from `Shader/` (bfsha, `Drive.Nin_Ounce_NVN2.release.sarc.zs`), `Lib/` (agl, gsys), `Effect/`, `Layout/` and 40 in `main`.
- The rewriter (`dm/tools/patch_nso.py`) rewrites the three modules with no cut. The SDK-wide address region rules of `dm/tools/sdk_patches.py` match no function of this `sdk`.

## Shaders

The full Mac build translates all 11,561. Getting there took four things, all general:

- 25 are task and mesh shaders (7 task, 18 mesh), which the split used to file as vertex and domain: [NVN2 task and mesh shaders](../../../docs/reference/shaders.md#nvn2-task-and-mesh-shaders). They draw the bushes and grass tufts beside the track.
- 8 pixel shaders use UP2UR with masks 8 and 0x40, and one compute shader (`ab77eaee44cfef88`) SURED: [Ampere shader code](../../../docs/reference/shaders.md#ampere-shader-code-switch-2).
- The 168 compute shaders of `DrivePassShaderDefault` that declare 48 KB of shared memory build since [Compute shared memory past 32 KB](../../../docs/reference/shaders.md#compute-shared-memory-past-32-kb); before it, the 3D scene of the title had sky and clouds over black geometry. A probe on the base game (2026-11-09) counted their dispatches from the title to the first race: all direct, of 1 to 3 workgroups, 700 to 2,400 every 300 frames before the race and 6 a frame in it, so the slices indexed modulo 512 they had before never collided here (pull request #1242).
- `dcb0504c844f1ecc` copies a flat per-primitive attribute into an R8Uint target, so it needs the integer entry point `fs_uint` now gives such a shader.

## Rendering

The game draws into the top left 2048x1152 of a 3840x2160 window texture and crops the window to it, so screenshots are taken with `DM_NVN_SHOT_OUT=1920x1080` (`play.sh` in the work folder does).

On the way to the title:

1. Every command buffer failed with `kIOGPUCommandBufferCallbackErrorOutOfMemory` and no frame was presented: six terrain arrays of 8192x8192x68 (two BC6H of 5,803 MB, four ASTC 8x8 of 1,451 MB), made whole, took more than the Mac's memory ([Large sparse textures as Metal placement sparse textures](../../../docs/reference/nvn-objects.md#large-sparse-textures-as-metal-placement-sparse-textures)).
2. Black geometry under the sky: the 48 KB compute shaders' dispatches were skipped ([Shaders](#shaders)).
3. 611 pixel shaders refused at load: [Uniform references past the first kilobyte](../../../docs/reference/shaders.md#uniform-references-past-the-first-kilobyte).

To the race:

4. `CRASH pc=0` from `main+0x19e77a0` when the cup's opening movie starts: `nn::syncpt::sdk::TryWaitSyncPointEvent` went through the SDK's null table, as `CreateSyncPointEvent` did on Donkey Kong Bananza; the host answers it from the event's SystemEvent (`hle_codec_video.c`). The movie player is in `main` and takes SDK 19's decoder forms ([SDK 19's decoder forms](../../../docs/reference/movies.md#sdk-19s-decoder-forms)): VP9 at 2560x1440.

## Frame rate

The first race on the 16 GB M6, in order of the fixes:

| Host | Frame p50 | Frame p95 | Submit |
|---|---|---|---|
| First race | 96-117 ms | about 280 ms | |
| A placement sparse texture no longer copied whole on its first view (389 MB) | about 22 ms | 100-155 ms | 11 ms |
| The sparse pool's change log instead of a walk of the page table per lookup, a cached pool span in the dirty tracker | 16.5 ms | 33-85 ms | 4-6 ms |
| [Large pools wrapped in chunks](../../../docs/reference/nvn-objects.md#large-pools-wrapped-in-chunks) | 16.1-16.7 ms | 17-33 ms | 4-6 ms |
| The task and mesh draws, now that they run | 15.9-17.2 ms | 21-31 ms | 4-6.5 ms |
| Real terrain and the whole scenery lists | 15.5-16.5 ms | 21-33 ms | 3.7-5.2 ms |

GPU time is about 8.3 ms a frame without the mesh draws and 8.6 to 9.3 ms with them; the numbers after this are from before them. Over 3,900 frames of the race (frames 8100 to 12000) the worst frame of each 300 is usually 35 to 65 ms, with five of the fourteen stretches reaching 140 to 233 ms; pipelines that compile at first use account for some of them (one took 703 ms in an earlier run), and there is no prewarm list yet. No out-of-memory error came. The residency set is 7.1 GB (shared buffers 1,554 MB, textures 2,011 MB, placement heaps 3,328 MB, private 192 MB), wired memory steady at 9.6 to 9.8 GB, about 6.5 GB of swap in use with 130 MB free. Taking the terrain tiles from their storage costs about 8 ms at the 95th percentile on this Mac (rule off in the same build: 17-24 ms) and 0.24 GB of GPU memory, with resident memory the same at 12.8 GB. It is not a leak, but runs of one build vary a lot with the Mac's memory state: another run right after a regression reached 35-56 ms and 13.8 GB resident with 8.5 GB of swap. Not measured on a Mac with more memory, or on iOS, where the address space is far smaller.

On a 16 GB M1 Pro (2026-11-04) the same race kept its frame median at 25 to 28 ms, the GPU taking about 24 ms of it. Before [Physical pages mapped at several places of a placement sparse texture](../../../docs/reference/nvn-objects.md#physical-pages-mapped-at-several-places-of-a-placement-sparse-texture), the placement heaps reached 2.75 GB within three minutes, wired memory 8.7 GB, and the system swapped (frames to 50 ms). With it, the heaps stayed at 1 GB and wired memory at about 7 GB over five minutes, with no swap growth; two Grand Prix in one session (about 30 minutes) played at a race median of 25 to 27 ms, with single frames of 100 to 200 ms now and then.

On the 16 GB M6 (2026-11-04, a host on the older chain `475a55e74858`, the Mac also swapping for another session's game for part of the run), the first race with those shared tiles: 4 heaps (1,024 MB) where the run above had 12 (3,072 MB), resident memory 11.3 GB where it had 12.8 GB, the frame median 16.7 ms and the 95th percentile 17 to 20 ms over 2,400 frames, no out-of-memory line. The run was minutes long, so it does not show that [issue #1193](https://github.com/seedds/nxnative/issues/1193)'s crash after 16 minutes is gone.

Dynamic resolution reads the GPU time between the frame's timestamp reports, as on Donkey Kong Bananza (same engine), so it needs real report times: [GPU timestamps per submission segment](../../../docs/reference/frame-rate.md#gpu-timestamps-per-submission-segment), every game's since it moved from profiles into the host. With one time for the whole submission the difference read about 0 and the scene kept 2048x1152 however long the GPU took. On a 16 GB M1 Pro (2026-11-04, main `777a5f6c`, [PR #1229](https://github.com/seedds/nxnative/pull/1229)) segment times, the GPU's idle gaps then still counted, stepped the first race's scene down to 1328x748, and the race (frames from 160 to 196 s, two alternating runs each, `DM_NVN_GPU_TS=submission` for the old behaviour) went from 33.4–33.6 to 42.2–42.3 fps, the GPU p50 from 26.8–28.3 to 20.8–22.4 ms. With the gaps counted, distant mountains and bridges flickered on the title screen and in free roam on an M5 ([PR #1350](https://github.com/seedds/nxnative/pull/1350)): about 5–6 ms of a frame was the GPU waiting for the host, the controller read it as over budget, and the render size swung from frame to frame. Without the gaps (the default now) no M1 Pro run has been made: it should keep a higher render size than 1328x748, at a frame rate that may be below 42 fps. On the 16 GB M6 (2026-11-11, first race, host pinned to chain `cb2e91c138e3`, `DM_NVN_GPUPROF` every 200 or 600 frames for the scene size) the GPU's idle gaps inside a submission are under 0.5 ms a frame, so leaving them out changes nothing there, but real report times do: the game reads its GPU time of 9 to 11 ms and steps its scene below 2048x1152 in most race frames (mean width 1433–1760 over three runs, 2 of 50 profiled frames at full width), where one time per submission kept it at full width in 18 of 34 (mean 1710–1872). Every run held 60 fps at the median; frames over two vsyncs per 2,400 were 12 and 17 with one time per submission, 19, 229 and 50 with segment times, and the long frames have no upscaler or texture churn behind them, so whether segment times cost smoothness here is not settled.

Since the race resizes, its render targets change size nearly every frame (1480x832, 1544x868, 1548x868, 1488x836 and their halves and quarters, issue [#1823](https://github.com/seedds/nxnative/issues/1823), current): each new size was new Metal memory, 1,100–2,400 residency commits and 3–6.7 GB added every 300 frames on the 16 GB M6, against about 100 MB in a race at one size, with the replay's CPU time up by 1.5–2.5 ms a frame. [Render targets that move with the dynamic resolution](../../../docs/reference/rendering.md#render-targets-that-move-with-the-dynamic-resolution-get-new-metal-memory-each-time) now takes them, their family heaps and their feedback snapshots from recycled heaps: in one run with two outside GPU loads (so that the resolution moved), alternating old and new every 600 frames, 970 → 272 residency commits and 1.8 → 0.34 GB added per 300 frames, replay CPU 6.94 → 6.36 ms a frame, frame and GPU times unchanged (2026-11-11, main a77c0ee8). The rest of a resize's cost (a new texture, its fill and the takeover of the old size) and the M4 at 3.1 GHz, where the issue's drop to 30 fps was seen, are open. Whether the game resizes depends on its GPU time: with one outside load on the M6 it held 2044x1148 in some runs and moved in others.

Game speed: the framework picks each frame's interval, 1 or 2 vsyncs, which the game steps by (the function at `main+0x3a9e28` on v0, its mode at `[x19+0x210]`: 1 = 60 fps, 2 = the game's 30 fps mode, 0 = chosen from the frame's CPU time alone). Frames that waited on the GPU kept interval 1 and played in slow motion, as the user saw on a slower Mac. With `fps_target 60` the interval is the host's frame step, at most 2, and the game's own 30 fps mode stays its own ([A fixed frame step plays in slow motion on a slow Mac](../../../docs/reference/frame-rate.md#a-fixed-frame-step-plays-in-slow-motion-on-a-slow-mac)), a stub placed by its function's fingerprint ([`patches.py`](patches.py); 1.8.0's function has its own, see [1.8.0](#180)). Mac runs on the 16 GB M6 (2026-11-08, a test host on the libraries of chain `1d619d0f520b`): the user's session held 60 fps (game time 0.977 in the one window with 3-vsync holds, where the game steps 2, else 0.999); at `DM_FPS_TARGET=30` every frame was held 2 vsyncs, game time 0.996 of real time, into a Grand Prix race. Those figures are the stub's own count; the Grand Prix shows no race clock, and a check against Time Trials' clock has not been run.

The 0.977 window was the host holding frames 3 vsyncs while the stub stepped 2: the stub now declares its largest step, 2, and the host holds and pays back within it ([Frames held longer than the game's largest step](../../../docs/reference/frame-rate.md#frames-held-longer-than-the-games-largest-step)). On an M4 Max (issue [#1823](https://github.com/seedds/nxnative/issues/1823), 2026-11-11, the reporter's numbers) races ran at about 40 fps with the hold and 60 without it (`DM_FPS_HOLD=off`: 1,800 of 1,800 frames at hold 1 per window, 57.5–61 fps, game time 0.99–1.02, about 28% of frames late by a few ms), 6.6 ms of GPU time in the long frames: three near-miss frames in a row stepped to 30 about once a second. The hold now rises only when the frames also fall short of 60 on average ([Three late frames among frames on time raised the hold](../../../docs/reference/frame-rate.md#three-late-frames-among-frames-on-time-raised-the-hold)). The reporter's retest (2026-11-12, `8a5c5e7e`, 144 Hz screen) confirmed it: most windows at 1,800 / 0 / 0, game time 1.003–1.013. Five one-second dips to 30 were left, four of them just after a single long frame of 43–68 ms (693 first texture uploads; shader libraries and a hybrid pipeline; two with nothing listed). A stall now no longer counts toward that average ([A lone stall among near-misses raised the hold](../../../docs/reference/frame-rate.md#a-lone-stall-among-near-misses-raised-the-hold), resolved in `t_fstep` with the reporter's numbers; not retested on the M4 Max). Open: the stalls themselves. At two of the rises the logged cost was 0.42–0.48 vsyncs on the stall's own present, which suggests the time went to the acquire's wait rather than the game's work, if `[longframe]`'s frame numbers match the presents.

Where a race frame's time goes on an M3 Max (2026-11-16, uncapped, docked): about 10.5 ms of GPU work in a frame of about 13.5 ms. No CPU thread is saturated (the queue replay at about 73 % of a core, the game's threads under 20 %); the main thread waits on the fence of the frame before (`main+0x3a9fe8`, the framework's loop, about 4.5 ms a frame), and the GPU idles at each frame's start until the new frame's first commands are copied, translated and committed (`DM_NVN_SUBTL`). The copy of the frame's first submission was a millisecond of that: [A submission copied whole before its first commands could start](../../../docs/reference/frame-rate.md#a-submission-copied-whole-before-its-first-commands-could-start). Handheld mode (`DM_OPMODE=0`, 1920x1080 inside) took the frame from 13.5 to 10.8 ms (GPU 10.4 → 7.9 ms), where the copy and the replay then bound it. The profile's `enc_thread on` puts Metal encoding on its own thread on the Mac too (as on iOS): two alternated uncapped runs each, docked 77.4–77.7 → 80.0–80.7 fps, handheld 104.3 → 106.6 fps. The cube map filters drew each level's six faces in one thread per texel, which kept the GPU short of threads; drawn once per face they take a quarter of their GPU time ([A draw into the six faces of a cube level at once ran short of threads](../../../docs/reference/rendering.md#a-draw-into-the-six-faces-of-a-cube-level-at-once-ran-short-of-threads)).

What a race frame's 116 render passes cost on the CPU at the 60 fps cap (handheld, M3 Max, Instruments Time Profiler on the host): the encode thread spends about a quarter of its time making and ending render encoders (`renderCommandEncoderWithDescriptor`, the driver's framebuffer setup and the descriptor's validation, `endEncoding`), about 5-6 µs a pass, and the replay about 3.6 µs a pass opening it (`rp_begin_ex_`): about 1 ms of CPU a frame. Why they end (`DM_NVN_PASSDUMP`, frame 3000): 80 at the game's own target changes, 21 at the cube filter's face-split levels (`fsp_encode`, one pass a level), 9 landing waiting clears that a draw's bindless program may sample (five of them the layers 0-4 of one 128x128 texture, which one layered pass could clear), 4 split by `DM_NVN_PASS_SPLIT`, which happens only because `DM_NVN_PASSDUMP` slows the replay: in a normal run turning the splits off (in-run A/B) changed neither the pass count nor anything else. The replay's own time (`@sub_instr` about 45 million instructions a frame, 22,000 a draw at 0.40 cycles an instruction): argument blocks about 30 % inclusive, Objective-C reference counting about 12 % (`objc_retain` / `objc_release` around `draw_`, `rp_begin_ex_`, `encode_args_`, `pso_get_`), the per-submission cost reading (`nq_cost_begin` / `nq_cost_end`, a `thread_info` call each for the kernel time) about 2 %. Tried at the cap and not kept: every guest thread at QoS utility (`DM_QOS_MAP=1 DM_QOS_EDGES=0,0`): 89-93 % on performance cores instead of 97 %, the same energy a frame, more late frames; no time-constraint policies (`DM_RT=0`): the same energy, the replay still at 3.45 GHz. The memory pool index, about 5,000 entries in a race, is kept sorted as pools come and go ([Address to memory pool lookups by binary search](../../../docs/reference/frame-rate.md#address-to-memory-pool-lookups-by-binary-search)).

Where the docked frame goes since (M3 Max, uncapped, `DM_NVN_SUBTL`): the game submits the main scene about 3.6 ms after its fence wait returns, the replay translates its ~1,050 draws in about 3.2 ms, and about 5 ms of GPU work follows, so a GPU saving before that pass shows only where the GPU is the limit (handheld). The GPU idled about 1 ms before the scene pass while it was translated. Two changes aimed at that did not help, in-run A/B: learning that segments ran from a shared event instead of their commit feedback (the long pass split came about 0.9 ms sooner, but the encode thread then needed about 0.8 ms for the segment; frame p50 +0.08 ms), and splitting long passes while the GPU still had work (frame p50 −0.14 ms, GPU +0.18 ms, attachment loads +180 MB a frame). On a shared Mac, other processes keep the GPU about 30 % busy (`ioreg` with the game closed), which delayed committed segments by up to 2 ms. The replay's translation went from 5.7–6.0 to 5.2 ms a frame (p50) when the texture view cache kept enough views per texture ([Texture views cached by texture and view parameters](../../../docs/reference/rendering.md#texture-views-cached-by-texture-and-view-parameters)) and a Metal texture's class answer was kept (`is_mtl_tex`). The lock the replay shares with the game's command threads (`g_rmu`: about 100 texture registrations a frame, almost all of new textures) costs the replay about 3 % of its busy time in waits; letting waiters spin instead of park (`OS_UNFAIR_LOCK_FLAG_ADAPTIVE_SPIN`) changed neither the waits nor the frame (in-run A/B, pairs both ways). After the scene pass, same-pass feedback ends the scene's pass three or four times (draws that sample the colour or depth an earlier draw of the pass wrote: `fb_prepare`, `fb_depth_rule`), each split storing and loading about 50 MB of attachments, about 0.4 ms of GPU a frame.

Encoding on its own thread brought held submissions with it ([A frame's submissions queued behind its first one while the iPhone's GPU clock is low](../../../docs/reference/frame-rate.md#a-frames-submissions-queued-behind-its-first-one-while-the-iphones-gpu-clock-is-low)): a submission that ended while the GPU still ran was held until the GPU ran out, so each of the frame's batches began behind an idle GPU. They are now held on iOS only (`DM_NVN_SUB_MERGE=1` holds them on the Mac). In-run A/B on the M3 Max (uncapped, `DM_AB=300`, race phases): frame p50 0.65 ms shorter docked and 0.60 ms handheld without them, no frame over 20 ms either way. A whole handheld run (1,800 frames): 105.5 → 114.7 fps, frame p50 9.11 → 8.33 ms, p95 12.1 → 11.1 ms, GPU p50 7.1 ms. The encode thread still falls up to a millisecond behind the replay at each frame's start, where about 40 small passes (the reflection probe and its cube filters) each cost a render encoder (Metal's `renderCommandEncoderWithDescriptor:` is about 15 % of that thread's time, `endEncoding` 6 %).

Tried since, in-run A/B (M3 Max, uncapped, race phases of 300 frames), and not kept: a segment commit wherever a pass ends inside a target's draws while the GPU has run out, with pass splits waiting for 32 draws into their pass (frame p50 +0.3 ms docked); segments committed behind running work (`DM_NVN_CUT_BUSY=0`, now an A/B switch: p50 -0.17 ms better with the rule, and up to 8 frames over 20 ms a phase without it); pass splits every 128 draws, up to 4 a pass (+0.08 ms handheld: few are taken, as a split waits for an idle GPU); a first segment of 2 draws on an idle GPU instead of 8 (+0.29 ms handheld, 6 more passes a frame); and a depth write after reads of the depth attachment keeping its pass when every read was proven to be of the reading pixel's own texel (the fetch analysis's `fpos_proof` / `scr_proof`): the post-scene passes of one frame went from 7 to 4, but the common depth readers after the scene (`a71bb4947bf8f4e8`, `118f25c4c4de77bf`, `d02e3773ac786af4`, `92e698b033c4babe`) have no analysed samples (`nfc 0`), so a race frame kept 0.3 passes on average and the frame did not move. Those readers' samples would have to be analysed (`dmsh_fetch.py`) for the rule to matter here. They read the depth at a projective position written with factors of `gl_FragCoord.w` that cancel (`d02e3773ac786af4`'s slot 4: `in.m_55.xy / in.m_55.w`), which `_proj` does not match, and their vertex shaders have no screen varying (`screen` empty in the raster facts), so both sides of the analysis would need the new forms before a chain rebuild (about 6 minutes for this game's 11,560 shaders). Ordering draw passes by the game's barriers alone (`DM_NVN_BARRIER=game`, A/B with submissions no longer held): frame p50 -0.04 ms, no change. Kept, for the replay's CPU time: draws whose fragment shader names no attachment of the pass skip the three walks of its bindings that the feedback rules made (`fb_any_att`: about 3 % fewer instructions a frame, `fb_prepare` from 7.7 to 3.2 % of the thread); the address → pool cache missed about 9 % of its lookups, each a lock and a search of the 5,000 pools, and with 4096 pages and 32 recent pools misses 2.3 % (in-run A/B: the replay's CPU 5.28 → 5.07 ms a frame, frame p50 8.22 → 8.07 ms handheld); the fields a texture binding reads come first in a texture ID's 440-byte entry.

Docked, the GPU bounds the frame (about 9 ms of work at the game's full 2560x1440, which its dynamic resolution keeps since that fits its 60 Hz budget). `DM_NVN_GPU_TS_SCALE=<factor>`, off by default, makes the game read a frame's GPU work as that many times as long from the frame's first timestamp report, so its dynamic resolution aims at a frame of 1 / factor of its budget. On the M3 Max, uncapped, one run each (2026-11-16): off 95.4 fps, frame p50 10.15 ms, GPU 8.81 ms; 2: 117.8 fps, 8.03 ms, 6.70 ms, the scene at about 1664x932; 1.6: 112.1 fps, the scene moving between 2560x1440 and about 1690x950 (the game's steps between them are coarse). It is the player's choice, as the picture is smaller.

Its compute work waited on itself: of about 120 dispatches a race frame, about 94 have an image or a handle binding (no memory range), many of one workgroup, and the host ordered each after everything before it. The profile's `dispatch_rangeless game` orders them by the game's barriers, and against copies as a whole ([Compute dispatches that wait for each other](../../../docs/reference/frame-rate.md#compute-dispatches-that-wait-for-each-other)). In-run A/B (M3 Max, uncapped, `DM_AB=300 DM_NVN_DISPATCH_RANGELESS=ab` with `DM_NVN_GPUPROF=every:20`, five phase pairs each, 2026-11-16): compute / copy time a profiled frame docked 1.29-1.51 → 0.87-0.99 ms, handheld 1.11-1.32 → 0.69-0.76 ms, the render passes unchanged; frame p50 −0.36 ms docked and −0.33 ms handheld. Before it, a docked race frame was about 8.2 ms of GPU work (`DM_NVN_GPUPROF`): the scene's colour and depth passes 2.6 ms in 8.7 passes, compute 1.4 ms, 18 one-draw 128x128 passes 0.43 ms, the shadow map 0.3 ms, and about 70 small passes 2.4 ms. The six passes after the main scene pass (about 115 draws: particles that read the depth and objects that write it) cost about 0.9 ms, each a store and a reload of the 2560x1440 targets at about 370 GB/s: the write-after-read cuts among them could go only with a proof that each reader samples its own texel (above), the read-after-write ones must stay. Lossless compression for family textures (`DM_NVN_FAMILY_NOCOMPRESS=0`) left the scene passes as they were (298 against 295 µs each docked).

The slow frames of an uncapped race (the slowest quarter, 10-14 ms) do no more GPU work, draws or translation than the median ones: the GPU waits, 2-4 ms of one gap a frame (`DM_NVN_SUBTL`). Once a second the gap was the host's: at a submission's start the release of render targets drawn over (`tu_pass`) looked at each of the race's 130,000 texture IDs, 1.9-2.3 ms of the replay thread while the GPU waited; it now looks only at the IDs used since its last pass, spread over the submissions ([Render targets drawn over stayed while their texture objects lived](../../../docs/reference/rendering.md#render-targets-drawn-over-stayed-while-their-texture-objects-lived)), about 0.05 ms. The other gaps are a command buffer committed on an idle queue that starts 2-3 ms later: without the present's wait for its drawable (a test build, `waitForDrawable` left out) the slow frames stayed the same, and the Mac's GPU was 35-40 % busy before each run with other processes (WindowServer, the wallpaper, other apps' renderers), so they wait behind those.

When the resolution steps down, from 2560x1440 to 2134x1200 docked, every render target was made again in a new recycled heap, as the old ones were more than half as large again as the new targets: 529 MB added to the residency set in 89 textures, and frames of 60–110 ms while it was committed. A heap now takes a texture down to 40 % of its size ([Render targets that move with the dynamic resolution get new Metal memory each time](../../../docs/reference/rendering.md#render-targets-that-move-with-the-dynamic-resolution-get-new-metal-memory-each-time)): with the resolution moved every 300 frames (`DM_NVN_GPU_TS_SCALE=ab:2.5`), residency commits 400 → 278 ms over 2,700 frames and frames over 20 ms 16–18 → 11–12.

Its compute queue (queue 6) takes about 0.70 ms of GPU a frame docked and 0.56 ms handheld (`DM_NVN_SUBTL`, M3 Max, uncapped), and in 60 % of it main-queue work waits behind it on the one Metal queue. A second Metal queue would not let them overlap: every one of those main-queue submissions (732 of 732 docked, 707 of 707 handheld) comes right after a wait of the main queue on queue 6 (`replay takes queue 1 node E` after the queue 6 submission), so it depends on that work as NVN orders it. The full-screen 2560x1440 pass of two RGBA8 targets (0.45 ms, `635061c90d75a8d1`, one draw) is the deferred lighting: 10 textures, 13 samples a pixel, its own work.

Tried after that and not kept, in-run A/B (M3 Max, uncapped, phases of 300 frames, 2026-11-16): a submission's last command buffer held while the encode thread already has the next records and the GPU still runs (fewer of the 14-15 commits a frame reach the kernel's queue; nothing waits for the GPU to run out): handheld frame p50 +0.15 ms paired, docked no reading (other processes put the run in its slow state in both modes); a cut committed ahead when the only segment on the GPU is estimated to end within 0.05 ms (its draws and dispatches times the GPU time a unit took before): handheld +0.07 ms, docked +0.16 ms. The ten 128x128 one-layer passes on one five-layer array (`3cc35012`, `0d3f740b`) are tessellated draws, which the slice merge does not take.

Its depth-stencil target stays attached in about 15 race passes a frame whose draws never enable the stencil test, and some that never test depth, so those planes were loaded (and stored) for nothing: about 50 MB of stencil a docked frame. ## Terrain and movies

## Vanishing scenery

Whole groups of trees and bushes vanished or appeared in one frame while the camera barely moved, for hundreds of frames, in the title scenes and while driving. The culling shader (`e04783bda5a52269`) reads a list that `2ce9071c2f22d74f` rebuilds every few frames, and a race in that shader's reset lost entries: [A store only a dispatch's first invocation makes](../../../docs/reference/shaders.md#a-store-only-a-dispatchs-first-invocation-makes). Ruled out on the way: conditional rendering (only some clears), stale camera uniforms, and a depth pyramid in the culling shader (it reads no textures).

## Sky panels

[Issue #1186](https://github.com/seedds/nxnative/issues/1186): large flat panels in front of the sky on many courses, on the base game and 1.8.0. The vertex shader `90a9a728715fd08b` (`DriveRefreshUber.Procedural`) moves its vertices by a 128x128x5 RGBA16F array, whose `y` reached 1,064 in layer 4 and 1,085 in layer 3 here (14,416 in the report), and stayed under 1 elsewhere. It is not a simulation running away: `8f3581eb40d8ce71` adds to a second array that is cleared every frame, and the large values are drawn into that one. They come from the per-layer task and mesh draws, which read [the dummy buffer](../../../docs/reference/shaders.md#task-and-mesh-draws-reading-the-dummy-buffer) instead of the game's data.

Resolved on the base game, on chain `d5fe9ae8bfba` (M6, 16 GB, another session's game running at the same time): at Crown City the array's `y` stays at or below 0.9 and the sky shots show no panels, and desert scenes checked with an earlier host that remapped the slots show none either. The first race, on the route of `measure.sh`, keeps a frame median of 16.6 to 16.7 ms and a 95th percentile of 17 to 18 ms, with GPU time 7.2 to 7.7 ms and resident memory 11.4 GB. That matches runs from before the fix, so reading real data costs nothing measurable there. One run reached 14 to 15 ms of GPU time and did not repeat. 1.8.0 has not been run here.

## Open

- **Cube map filters on the Mac:** the two filter shaders (GearPassShader `4744589bb8f9f7dd`, DrivePassShaderDefault `765844f5609bb11b`) fill three chains of six levels a frame, each draw writing the six faces of a level with 32 cube samples per face. Split per face (found on below), the 18 passes take about 0.55 ms of encoder time a frame against 2.4 ms. They still run one after another behind their entry barriers, though each level reads only the source cube: before the split, a diagnostic build without those barriers overlapped them and saved 0.3 ms of GPU time a frame. Shipping that needs hazard tracking across passes and the alias flush the large pools ask for; not done.
- **Barriers between draw passes:** every draw pass begins with a barrier that waits for all earlier GPU work, and `DM_NVN_BARRIER=game` does not help here (no change on an M3 Max, 2026-11-16): the large pools' alias flush still makes each pass's fragments wait for everything before. A diagnostic build with no entry barrier at all (pictures not checked) bounds what any finer ordering could gain: race GPU p50 0.4–1.0 ms lower, frame p50 0.7 ms on average, alternated in one uncapped run. Point-to-point ordering (a fence per writing pass) would get part of that.
- **Attachment traffic:** a docked race frame on the Mac loads about 700 MB and stores about 860 MB of attachments. `tbdr_load_dead.py` finds 38 % of the loads behind a full-screen first draw, most of them the 6144x6144 chain whose render area the host already limits, about 80 MB a frame otherwise; `tbdr_store_dead.py` (frames 2400–2401, an upper bound) finds 75 MB of stores nothing reads before the next clear, the 3072x3072 shadow depth and the 2560x1440 scene depth. A few tenths of a millisecond on an M3 Max; more where memory bandwidth bounds the GPU, as on a phone.
- **A boot that starts the course's video can abort:** 3 of about 32 Mac runs that started the 640x360 VP9 decoder (2026-11-16, hosts before and after that day's changes) stopped right after it: `nn::diag abort: Result 0x1c286f` (`nn::codec` 3604, no picture in the buffer) from `GetVp9DecoderOutputBufferProperties` (the game's wrapper `main+0x19e8110`, aborting at `main+0x19e8190`), before any picture was decoded. A trace of the decoder calls (`cvt` runs) shows the player's order: for each of its four buffers, Register, Acquire (generation 0), then `RequestSyncPointEvent` on that handle (`main+0x19e7760`), which the host signals at once since `TryWaitNativeSync` reads a just-registered buffer as signalled; after the four, Release and Acquire again (generation 1) and a new request. The event's callback (`main+0x19e6f40`, under the player's lock at `+0x1e4c`) gives the buffer back to the decoder unless the player's state (`+0x1e50`) is 3, in which case it reads the picture's properties: so the abort is the callback for a generation-0 event running after the state became 3. Not signalling generation-0 events stops the abort but also the video: the player then never releases its buffers (12 packets decoded, no picture). Where state 3 is written was not found (stores at `+0x1e50` in the player's code write 1, 2 and 0). On the console the waiting thread probably wins by priority; here both threads run at once. **Open.**

- **Long frames:** first-use pipeline compiles (no `pso_manifest.tsv` yet).
- **Shading rate:** the calls are accepted and ignored ([Variable rate shading ignored](../../../docs/reference/rendering.md#variable-rate-shading-ignored)), so every pixel is shaded where the game meant to save GPU time.
- **Mesh draws:** `DrawMeshTasks3D` and the indirect forms are not implemented; no run reached them.
- `649e36162cad9e79`, a foliage shader with an 8x8 local size, keeps a first-invocation race: its setup loops over a uniform's count, so [the host cannot make it as stores](../../../docs/reference/shaders.md#a-store-only-a-dispatchs-first-invocation-makes). Its list's count read 0 in every one of 7,350 traced title frames, so the race had nothing to act on there; whether that list should be empty is not known.

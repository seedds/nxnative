# Standalone Metal probes

Small programs that test one Metal or translator behaviour without the game. Each is a single file and needs no game run, so it can't push the machine into a GPU reset or a wired-memory panic the way a 16 GB game run can. The worst one does is time out one command buffer (`task_hang` case B, about 22 ms of GPU time). Use them before a game run, to settle a question about Metal, or to check a translator change on its real output.

`make` builds the Objective-C probes, and `make run` runs the four that need no input. The others take translated shaders (`<key>_b.metal` and `<key>_b.json`, as `dmsh_build.py` writes them in its `b-<V>` folder) or a host log. They were written for Ocarina of Time (`0400486024DEC000`) and tested on an M3 under macOS 26. The results below are from that machine.

| Probe | Question | Input | Result on M3 |
|---|---|---|---|
| `heap_alias` | Which textures placed at the same offset of a placement heap read each other's bytes as a plain reinterpretation? | none | They share a layout only with the same width, height, bytes per pixel and compression. With those equal, the pixel format doesn't matter (RGBA8 ↔ R32Uint ↔ R32Float ↔ Depth32Float: 100%). Any size or bpp change, or a lossless-compressed (GPU-optimized) texture against an uncompressed one, gives scrambled data in at least one direction (0–3% of words match). |
| `rt_sizes [w h]` | What does Metal allocate for each dynamic-resolution step of a 16:9 target (0.333 to 0.75 of the final image)? | none | At 2048×1152: 855 steps give 21 distinct RGBA8 allocation sizes, from `heapTextureSizeAndAlign`'s rounding (for example 1530×861 to 1536×864 are all 5,570,560 bytes). So a free list keyed on the allocation size reuses textures across steps; one keyed on width and height almost never does. |
| `mesh_index_range <a\|b\|c> [groups]` | Does a mesh primitive index past the mesh's declared vertex count hang the GPU? | none | No. All in range, one index of 200 past 64 vertices, and every index 255 all complete in under 5 ms over 1,000 groups. |
| `mesh_archive` | Is a mesh render pipeline built through `MTL4Compiler` stored in a Metal 4 pipeline archive and found there again? | none | Yes: built in 36 ms, found in the flushed archive in 0.18 ms, and a different pipeline misses. The host builds mesh pipelines with `newRenderPipelineStateWithMeshDescriptor`, which no archive covers, so every mesh pipeline is compiled again on each run. |
| `mesh_sweep <dir> <key>` (driven by `mesh_sweep.sh`) | Does a translated mesh or task shader access memory out of bounds, or hang, on zeroed inputs? | translated mesh/task shaders | Ocarina's 500 meshes and 20 tasks. Before the mesh primitive-memory fix, 387 meshes wrote past their threadgroup stage array (every mesh with 126 primitives); after it, 0. 8 task shaders hang on zeroed inputs (see `task_hang`). |
| `mesh_guard.py <in.metal> <out.metal>` | The guard band `mesh_sweep.sh` adds | a `<key>_b.metal` | Metal shader validation checks device memory but not static threadgroup arrays: a deliberate one-past-the-end threadgroup write isn't reported. So this widens the stage array by 64 words, fills them with a marker, and counts the ones that changed after the shader body. |
| `task_hang <dir> <key> <A\|B\|C>` | Is the task-shader hang a raw pool-table miss? | a task shader built with bind-time pointers | Yes, for all 8. A: the pool is in the table, so it completes. B: the pool is left out of the table, so the range reads 0, the loop runs `uint(0 - 1) >> 5` = 134,217,727 times and the GPU times out. C: the pool is left out of the table but the bind-time site entry is filled, so it completes. |
| `raw_sites <shader.metal> <helper>` | Does a raw global load take the bind-time site entry when the pool table can't resolve the address? | a shader built with bind-time pointers, and its raw-load helper's name | 11 of 11 cases read from the buffer they should (the site entry, the table, or neither). |
| `rt_reclaim_sim.py <rt_events.tsv> [idle]` | How much render-target memory would reclaiming textures that are dead by overwrite save? | a log of render-target writes and releases | Ocarina, frames 0–4,000: render targets held drop from about 3.5 GB to about 1.2 GB. The log format is in the file's header. |

## Notes

- `mesh_sweep.sh` needs `timeout` (GNU coreutils: `brew install coreutils`). Shader validation of the largest shaders takes several minutes to compile. A shader whose validation compile passes `VTIMEOUT` seconds (default 60) is run again without validation, checked by the guard band only.
- Run task shaders one at a time (`mesh_sweep.sh` does). A GPU hang makes the GPU discard the work of every process running at the time, so the others would fail as its victims.
- `task_hang` and `raw_sites` need the bind-time pointer translator, which adds the `gptr` binding. With a shader built by `main`'s translator there is no site entry, so case C hangs like B.
- Zeroed inputs aren't the game's inputs. 122 shaders also give "Invalid device load at offset 0" under validation; those are loads through the zeroed pointers, not bugs.

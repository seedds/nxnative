# Audio

The audio renderer (`dm/host/hle_audren.c`), AudioOut, audio devices and codecs. Each entry: symptom, cause, fix, the games it was found on. The [symptom index](../agents/symptoms.md) lists every symptom.

## Audio renderer

### Running the SDK's own renderer on the CPU

Check whether the SDK carries the renderer: list the `sdk` module's exports for `nn::audio::server::` and `nn::audio::dsp::CommandListProcessor`. If they are there ([Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md), SDK 16), do not write a mixer:

- switch a copy of `AudioRendererParameter` to rendering device = CPU (+0x2c = 1) and execution mode = manual (+0x30 = 1) in `GetAudioRendererWorkBufferSize` and both `OpenAudioRenderer` overloads;
- call the SDK originals (`guest_sym` returns the module's own code even for a forced symbol);
- drive `ExecuteAudioRendererRendering` from a guest thread (`dm_guest_thread_spawn`).

The open then goes through `CreateAudioRendererManagerByDfc`; no IPC.
For a replaced DSP renderer the size query keeps the service's work-buffer contract; a larger local CPU representation is a backend cost. See [A sound engine's heap too small for its renderer and players](#a-sound-engines-heap-too-small-for-its-renderer-and-players).

### SDK 1: the renderer is the `audren:u` service

- **Symptom:** the host stops at boot with `[RED] sf: the game connects to service audren:u itself, which the host does not serve`, under `nn::audio::GetAudioRendererWorkBufferSize` or `OpenAudioRenderer`.
- **Cause:** SDK 1.3.1 carries only the renderer's client: no `nn::audio::server::`, no `ExecuteAudioRendererRendering`, no DFC manager. Its `nn::audio` connects to `audren:u` (`CreateAudioRendererManagerByHipc`, `sdk+0x1641dc`), as on Horizon, so [the CPU renderer above](#running-the-sdks-own-renderer-on-the-cpu) has nothing to run.
- **Fix:** the host serves `audren:u` (`hle_audren_sv.c`, registered with `SF_SERVICE` in [`hle_sf.c`'s host sessions](services.md#game-linked-hipc-clients-of-system-services)), and `hle_audren.c`'s work size, open and close hooks hand an SDK without `ExecuteAudioRendererRendering` straight to the SDK's own client. Every layout was read off SDK 1.3.1's client:
  - the manager: 0 `OpenAudioRenderer` (the 0x34-byte parameter, its revision at +0x30; the work buffer's transfer memory and the process as copied handles; the work size and applet resource user ID at +0x38 / +0x40; the process ID; the renderer comes back as a moved session), 1 `GetWorkBufferSize` (the service budget, `dm_audren_work_size`), 2 `GetAudioDeviceService` (zeroed answers; the device calls are taken over above the service).
  - the renderer: 0–3 sample rate, sample count, mix buffer count, state (0 started); 4 `RequestUpdate` (A: the update; B: the answer; B: performance frames); 5 / 6 start and stop; 7 `QuerySystemEvent` (a copied read end of the renderer's kernel event); 8 / 9 the rendering time limit.
  - the update, revision REV2: a 0x40-byte header with each section's size (behaviour +4, memory pools +8, voices +0xc, channel resources +0x10, effects +0x14, mixes +0x18, sinks +0x1c, performance +0x20, splitters +0x24, total +0x3c), then behaviour (0x10), memory pools (0x20), channel resources (0x70: ID, 24 volumes, in use at +0x64), voices (0x170: the client's `VoiceInfo` from +0x40), effects (0xc0), splitters, mixes (0x930: volume, buffer count +8, in use +0xc, ID +0x10 with the final mix 0, 24 × 24 volumes from +0x24, destination +0x924), sinks (0x140: type +0, in use +1, the device's from +0x20 with its input count at +0x120 and six inputs at +0x124), performance (0x10). The answer: memory pools (0x10: a requested attach, 4, answers attached, 5; a requested detach, 2, answers detached, 3), voices (0x10: samples played, wave buffers consumed), effects (0x10: 3 enabled, 4 disabled), sinks (0x20), performance (0x10), behaviour (0xb0). The client aborts unless the answer's total equals its buffer, and fails the update when a section's size differs from what it reads back.
  - the renderer: voices (PCM8, PCM16 and DSP ADPCM; four wave buffers in a ring, consumed at their end unless they loop, the played count restarting at an end of stream; a stop consumes what is queued) resampled linearly, through their channel resources' volumes into their mix; sub mixes deepest first; Aux effects (type 2) through the game's send and return rings, whose DSP offsets are at +0x40 / +0x44 of each info; buffer mixers; the final mix through the first device sink to stereo (5.1 down-mixed). Delay, reverb and biquad effects pass the dry signal and splitters are not followed, each with a red line. A guest thread renders one frame per output block and signals the renderer's event while it is started.
  - `svcCreateTransferMemory` gives the client a typed kernel handle for the work buffer. The audio service keeps using its own renderer buffer. [Transfer memory in the host](services.md#direct-irs-connection-and-status-memory)
  - `t_audren_sv` drives the service through `hle_sf.c` as SDK 1.3.1's client does.
- **Found on:** [Rayman Legends: Definitive Edition](../../dm/games/01005FF002E2A000/README.md) (SDK 1.3.1). The renderer in [PR #1540](https://github.com/seedds/nxnative/pull/1540) (from the patch in issue #960) read the client's own structures at SDK 1.3.1's offsets instead, and took effect type 3 (delay) for Aux.

### SDK 8's longer `AudioRendererParameter`

- **Symptom:** abort with Result 0x499 in `audio::GetAudioRendererWorkBufferSize`.
- **Cause:** SDK 8's `AudioRendererParameter` is one word longer than SDK 16's: its revision sits at +0x38. The host copies the game's parameter before switching it to CPU rendering with manual execution, and copied only 0x38 bytes, so `CheckValidRevision` read garbage.
- **Fix:** it copies 0x40 now.
- **Found on:** [The Legend of Zelda: Link's Awakening](../../dm/games/01006BB00C6F0000/README.md) (SDK 8.2.0).

### A renderer opened without an event

- **Symptom:** the game is silent; only the game's updates render (catch-up frames that nothing plays). The log has `audren: OpenAudioRenderer (no event)` and no `render thread started`.
- **Cause:** the game opens the renderer with `OpenAudioRenderer(handle, parameter, work, size)`, the form with no system event, and paces its own updates, but the renderer must still run every 5 ms. The host used to start its render thread only for the form with an event.
- **Fix:** both forms go through one open that starts the thread (`hle_audren.c` `ar_open`).
- **Found on:** [Balatro](../../dm/games/0100CD801CE5E000/README.md) (SDK 18.3.2, LÖVE's OpenAL Soft; one boot).

### A game with more than one renderer

- **Symptom:** `[RED] audren: a second renderer (the host drives only one)` with different parameters from the first open; later, `catch-up renders so far` in the thousands (7,625 in 6 minutes), about 10% of the first renderer's frames.
- **Cause:** a game may open several renderers, as on Horizon. The host kept one set of globals: the second renderer got no render thread, but `AudioRenderSystem::Update` is one hook for all of them, so each update of the second renderer found nothing rendered since the last, rendered a catch-up frame of the second renderer and queued it in the first one's output, in place of a frame of its own.
- **Fix:** `hle_audren.c` keeps each renderer's state in `ar_t`: its render thread, output, catch-up queue, counters and upsampler history. Two renderers play through two outputs, which the sound card mixes. An SDK call that names only the `AudioRenderSystem` finds its renderer by `ar_of_sys`. One lock still serializes all rendering, since the header layout is decided once, from the first list, by trying each layout in turn; a frame takes about 0.02 ms. Catch-up renders went from 7,625 to 0 or 1 in a run. `dm/host/tests/t_audren_layout.c` checks the lookup and the upsampler's separate history.
- **Found on:** [Mario & Luigi: Brothership](../../dm/games/01006D0017F7A000/README.md) (SDK 12.3.2): one renderer at 48 kHz, which sounds during the movie, and Unreal's mixer at 32 kHz.

### Two renderers overwriting each other's queued blocks

- **Symptom:** with two renderers open, one plays single 5 ms frames between silences and its sound effects are missing, while the other has an occasional all-zero 5 ms block; no underrun and no `[RED]` line, and the AudioOut `appended` and `released` counts stay balanced. Cross-correlating the outputs finds one renderer's waveform on the other.
- **Cause:** AudioOut queues a block's pointer and copies its samples when the sound card asks (`h_au_Append`, `pull` in `hle_audio.c`). `render_main` kept its four blocks in function-level statics, left out when the renderer state moved into `ar_t`, so every render thread filled the same four. A block queued for one output could be rewritten by the other renderer's thread before it played. A second renderer's start also set the size of the blocks to 0 under the first one's output, whose `b->size - a->pos` could then underflow on a part-played block.
- **Fix:** the blocks are in `ar_t`, one set per renderer. The slots are static and `CloseAudioRenderer` joins the render thread before a slot is reused, so a block outlives its output. `t_audren_layout` queues every block of one renderer, renders the other, and checks the first one's samples.
- **Found on:** title `01007ED02424E000` (not in the [games table](../../dm/games/README.md#games); [issue #1336](https://github.com/seedds/nxnative/issues/1336), on an iPad Pro M1). [Mario & Luigi: Brothership](../../dm/games/01006D0017F7A000/README.md) also opens two renderers; it has not been run with the fix.

### The SDK's open with an event calls the open without one (`t_in_open`)

- **Symptom:** `audren: OpenAudioRenderer` logged twice right after the first open, with the same work buffer and "original device 1 mode 1", and a second render thread (until 2026-11-04 the second log line was `[RED] audren: a second renderer`, which now means [more than one renderer](#a-game-with-more-than-one-renderer)).
- **Cause:** not a second renderer: SDK 17.5.3's `OpenAudioRenderer` with an event opens it by calling the form without one through the PLT (`sdk+0x1e489c`), which the loader binds to the host's hook since that form has one ([A renderer opened without an event](#a-renderer-opened-without-an-event)), so `ar_open` ran twice for one renderer. The inner call started the render thread before the outer one had created the event, and the outer call took the renderer for a second one.
- **Fix:** a thread-local flag (`t_in_open`) hands the inner call straight to the SDK with the host's CPU / manual copy of the parameter, and only the outer call starts the thread (`hle_audren.c`).
- **Found on:** [ROMANCE OF THE THREE KINGDOMS 8 REMAKE](../../dm/games/0100C2A01A730000/README.md) (SDK 17.5.3).

### Explicit CPU / manual renderer

- **Symptom:** choppy, crackling audio with thousands of catch-up renders (`catch-up renders so far` in the tens of thousands), heavy `AudioOut` underruns, and `[RED] audren: no DeviceSink (ID 0x14) in the command list`, alongside `audren: OpenAudioRenderer … (original device 1 mode 1 → CPU / manual)`.
- **Cause:** a game may open `nn::audio::AudioRenderer` explicitly in CPU + manual mode (`renderingDevice = 1`, `executionMode = 1`) with a `CircularBufferSink` and drive `ExecuteAudioRendererRendering` itself from its own audio thread, feeding a direct `AudioOut`. The host already kept the SDK's work buffer and event contract for `device != 0`, but still spawned `render_main` (opening a second unused `AudioOut` and rendering every 5 ms alongside the game's thread), ran `capture()` looking for a `DeviceSink` (consuming the one-shot sink discovery), and ran catch-up renders and 50 ms `cq_cv` waits inside `AudioRenderSystem::Update`.
- **Fix:** `hle_audren.c` records `manual = (device == 1 && mode == 1)` on `ar_t`: `h_ar_WorkSize` and `ar_open` keep the game's parameter unchanged and skip spawning `render_main`, `h_ars_Update` forwards straight to the SDK without catch-up frames, and `h_ar_ImplExec` / `h_ars_Exec` forward straight to the SDK originals (resolving unbound manual slots separately from host-driven DSP renderers so a manual and a DSP renderer can coexist cleanly). `t_audren_work` checks work size, event/buffer ownership, no thread spawn/join, direct SDK forwarding for update/exec and coexistence with an unbound DSP renderer.
- **Found on:** METAL GEAR SOLID: Peace Walker – Master Collection Version (`0100C6F01C4F8000` / program 1 `0100C6F01C4F8001`, 1.3.0, SDK 19.3.11, not in the [games table](../../dm/games/README.md#games); [issue #3212](https://github.com/seedds/nxnative/issues/3212)). Reported on M1 Max (no game files here).

### The renderer event as the service gives it: a kernel event

- **Symptom:** the frame loop stops for good as a level loads while audio keeps rendering. The main thread waits in `os::WaitSystemEvent` under `CAudioMemoryPool::Shutdown`, and a sound thread of higher priority waits on the same condition variable.
- **Cause:** with the DSP service (device 0, what the game asks for) `OpenAudioRenderer` attaches the service's renderer event, a kernel readable event (`AttachReadableHandleToSystemEvent`, auto-clear). With CPU rendering and manual execution, which the host switches to ([Running the SDK's own renderer on the CPU](#running-the-sdks-own-renderer-on-the-cpu)), it creates a local one instead (`CreateSystemEvent(event, AutoClear, false)`, SDK 4: `sdk+0x190b6c`). Signalling a local auto-clear event wakes one waiter, the one of highest priority. A kernel event wakes every waiter, and each one tries `ResetSignal`. Donkey Kong Country: Tropical Freeze waits on the event from two threads: its sound thread (priority 29, `main+0x971e8`) every frame, and the main thread while it detaches an audio memory pool (`main+0x6fa8c`: `RequestDetachMemoryPool`, then wait and update until `IsMemoryPoolAttached` is false). The sound thread took every wake, and the main thread never woke again.
- **Fix:** when the game opened the renderer for the service, the host replaces the SDK's local event with an inter-process auto-clear one (`DestroySystemEvent`, then `hle_bind_system_event(event, 1)` in `ar_open`), and the game's event waits on a copy of its read end. That event is the renderer's own, not the game's ([The renderer event belongs to the renderer, not the game](#the-renderer-event-belongs-to-the-renderer-not-the-game)). The SDK's renderer signals through `os::SignalSystemEvent`, which handles either kind. A game that opens a CPU renderer itself keeps the SDK's local event.
- **Found on:** [Donkey Kong Country: Tropical Freeze](../../dm/games/0100C1F0051B6000/README.md) (SDK 4.4.0): the first level's load after the intro cinematic.

### The renderer event belongs to the renderer, not the game

- **Symptom:** the game exits with 42 on its first rendered audio frame: `Break#1 reason=0` in `os::SignalSystemEvent`, called from the public `ExecuteAudioRendererRendering` on the host's render thread (`render_main`).
- **Cause:** with the DSP service (what the game asks for), no SDK's `OpenAudioRenderer` keeps a pointer to the game's `SystemEventType`. It stores NULL in the handle's event slot and attaches the service's readable handle to the object, so the game may destroy the object or reuse its memory once the open returns. The slot is `handle[1]` in SDKs 3, 5 and 12 (SDK 3 `sdk+0x17e004`, SDK 12 `sdk+0x4d2b4`) and `*handle[1]` in SDK 18. The CPU / manual open the host switches to ([Running the SDK's own renderer on the CPU](#running-the-sdks-own-renderer-on-the-cpu)) stores the object in that slot instead (SDK 3 `sdk+0x17dffc`, SDK 12 `sdk+0x4d274`), and `ExecuteAudioRendererRendering` signals it after every render. LEGO Star Wars: The Skywalker Saga passes an event on its stack, and Little Nightmares reuses the object's memory. The first render found a state byte (+0x28) that was no longer the event's, and the SDK aborted.
- **Fix:** `ar_open` gives the SDK's open an event of the renderer's own (`g_rev` in `hle_audren.c`, alive until `CloseAudioRenderer`, which destroys it), whatever slot the SDK keeps it in. The game's object gets a copy of that kernel event's read end (`hle_dup_readable_handle`), attached as managed and auto-clear, as the service's copied handle is. The renderer never touches the game's object again. The host's binding no longer sits at the game's address either, where a later service event at the same storage would have found it (`hle_bind_system_event` returns early for an address it already holds). Tests: `t_audren_work` (the game's event is overwritten after the open, including the SDK 3 to 12 slot) and `t_system_event` (the copied read end).
- **Found on:** LEGO Star Wars: The Skywalker Saga (`010042D00D900000`, 1.10.0, SDK 12.3.6; issue #632), Little Nightmares (`01002FC00412C000`, 1.0.4, SDK 3.5.1; PR #804), both from provisional profiles. DRAGON BALL FighterZ (`0100A250097F0000`, SDK 4.5.0; issue #771) aborts at the same place, and SDK 5.4's open and `ExecuteAudioRendererRendering` are the same code as SDK 3's and 12's. None of the three is here: the fix awaits their reporters' runs.

### The renderer's update lock (`update_lock`)

- **Symptom:** none of its own; command generation races the game's `Update` on SDKs whose lock is not at SDK 16's offset.
- **Cause:** `AudioRenderSystem::Update` holds a mutex in `AudioRenderSystem`; `GenerateCommand` does not take it, so the host does (the auto-mode system thread does the same in `SendCommandToDsp`). Which mutex depends on the SDK: `nn::os::LockMutex(MutexType *)` at +0x1d0 in SDK 4.4 and at +0x1d8 in 6.4–8.2, `SdkMutexType::Lock` at +0x1d8 in 10.4–11.4, +0x1f0 in 13.3–16.2, +0x1f8 in 17.5 and +0x208 in 18.3 (the `sdk` builds of the games on hand). From SDK 19 `Update` reads the system tick and calls `UpdateImpl`, which takes it ([The update lock read off `UpdateImpl`](#the-update-lock-read-off-updateimpl)). The host took SDK 16's for every SDK before 20, which wrote a lock word into another field and excluded nothing.
- **Fix:** `update_lock` in `hle_audren.c` reads it off the SDK's own `Update`: the register the prologue adds the offset to and moves into x0 before its first `bl`, whose PLT slot must hold `LockMutex` or `SdkMutexType::Lock`. A miss in `Update` goes on to `UpdateImpl`; a miss in both keeps the layout's offset and logs a red line. Test: `t_audren_layout`.
- **Found on:** [Mario Kart 8 Deluxe](../../dm/games/0100152000022000/README.md) (4.4), the first game it was plainly wrong for.
- **Check:** checked with sound on [Big Brain Academy: Brain vs. Brain](../../dm/games/0100620012D6E000/README.md) (11.4, +0x1d8), [DRAGON QUEST XI S](../../dm/games/01006C300E9F0000/README.md) (7.3, `MutexType` +0x1d8) and [Super Mario Odyssey](../../dm/games/0100000000010000/README.md) (7.3, which is silent for its first minute with either lock).

### No `SdkMutexType` in SDK 3

- **Symptom:** `FATAL audren: missing SDK symbol _ZN2nn2os12SdkMutexType4LockEv` right after the renderer's render thread starts.
- **Cause:** the render path looked up `SdkMutexType::Lock` / `Unlock` before reading which lock the SDK's `Update` takes ([The renderer's update lock](#the-renderers-update-lock-update_lock)); SDK 3.5.1's `sdk` has no `SdkMutexType` and takes `nn::os::LockMutex` at +0x1f8.
- **Fix:** `render_once` looks up the `SdkMutexType` functions only when `update_lock` does not find `LockMutex` (`hle_audren.c`).
- **Found on:** [OCTOPATH TRAVELER](../../dm/games/010057D006492000/README.md) (SDK 3.5.1), the first SDK 3 game through the audio renderer (Bayonetta 2's 3.6.0 plays through `AudioOut`).

### Where the `AudioRenderSystem` sits in `AudioRendererImpl`

- **Symptom:** the sound is choppy: about two of every three 5 ms blocks are silent (a `DM_AUDIO_DUMP`), with no underruns. The log's `catch-up renders so far` grows by one for each rendered frame (2000 of every 2000), and every update logs `no frame rendered before update N`.
- **Cause:** the host's takeover of `AudioRendererImpl::ExecuteAudioRendererRendering` found the `AudioRenderSystem` at a fixed `+0x60`, where SDK 16 and 20 keep it. SDK 3.4 keeps it at `+0x50` (`add x19, x0, #0x50` in the prologue, `sdk+0x188a10`). With the wrong pointer, the execution mode and rendering device came from other fields, so each render on the 5 ms render thread failed with 0x40299 and played a silent block. Only the game's updates rendered: one catch-up frame each, at 60 Hz instead of 200.
- **Fix:** `impl_sys_off` in `hle_audren.c` reads the offset from the SDK's own function: the first `add xd, x0, #imm` before the first branch. If it finds none, it keeps `+0x60`. Every other `sdk` build on hand (18 games, SDK 4.5 to 21) reads `+0x60`.
- **Found on:** [SteamWorld Dig](../../dm/games/01009320084A4000/README.md) and [SteamWorld Dig 2](../../dm/games/0100CA9002322000/README.md) (both ship the same SDK 3.4.0 `sdk` build).
- **Check:** after the fix, the log has `audren: AudioRenderSystem at +0x50 in AudioRendererImpl`, a few dozen catch-up renders per 2000 frames, and a dump with no silent blocks once the music starts.

### The render thread's route through the public `ExecuteAudioRendererRendering` (SDK 20)

- **Symptom:** `CommandListProcessor::Process` crashes now and then (SIGSEGV under `render_main`, once at 60 s and once at 134 s in the shrine); every `RequestUpdate` renders a catch-up frame.
- **Cause:** the public `ExecuteAudioRendererRendering` (`sdk+0x221e90`) reaches `AudioRendererImpl::ExecuteAudioRendererRendering` (`sdk+0x22ca88`, `x0 += 0x60` and a jump through the PLT) through the vtable, so the host's takeover of the `Impl` function was never called. The SDK's own `AudioRenderSystem::ExecuteAudioRendererRendering` ran instead (no update lock), every `RequestUpdate` rendered a catch-up frame because the host's render counter never moved, and the two threads wrote the same command buffer.
- **Fix:** the host also takes over `AudioRenderSystem::ExecuteAudioRendererRendering`, the PLT target (`hle_audren.c`); catch-ups fell from one per update to 3 per run.
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md) (SDK 20).
- **Note:** the same SDK's other `AudioRenderSystem` layout is in [SDK 20's `AudioRenderSystem` layout](#sdk-20s-audiorendersystem-layout).

### A renderer below 48 kHz with no upsampler on the CPU

- **Symptom:** SIGSEGV at address 0x18 in `UpsamplerManager::Allocate` on the render thread.
- **Cause:** a DeviceSink below 48 kHz is upsampled by the SDK's upsampler, and `AudioRenderSystem::SetUpRenderResourceSet` allocates the `UpsamplerManager` only for the DSP (`sdk+0x21eb6c`: rate 0x7d00 and rendering device +0x48 == 0); with the host's CPU rendering the manager pointer (`AudioRenderSystem+0x150`, the render context's +0x20) is null.
- **Fix:** the host answers `Allocate` on a null manager with no upsampler, so the generator skips the upsample command (`sdk+0x225b40`), and resamples the DeviceSink's stereo downmix 3:2 itself (a 16-tap windowed sinc in three phases, `up_3_2` in `hle_audren.c`), 240 samples per 5 ms frame for the 48 kHz output.
- **Found on:** [DRAGON QUEST VII Reimagined](../../dm/games/0100A9D01C446000/README.md): rate 32000, 160 samples per frame, `GenerateSinkCommands` `sdk+0x225a80`.
- **Note:** until then the output code assumed an upsampled buffer at 32 kHz that no game had produced.

### A sound engine's heap too small for its renderer and players

- **Symptom:** the main thread spins at start-up in a resource wait (a `YieldThread` loop, no crash), right after `OpenAudioRenderer`.
- **Cause:** the DSP service and an application's local SDK server use different command/state representations. The host forwarded the local CPU server's work-buffer requirement as the guest's DSP-service requirement. Larger local command structures could then exhaust a fixed sound heap that fits the service's budget. Changing only the device / execution fields in the local sizing routine does not reveal this difference: it still sizes the same compiled structures. The game note records the comparison against Horizon's actual sizing code and the resulting allocation failure.
- **Fix:** `ar_service_work_size` in `hle_audren.c` computes the Horizon service budget through renderer revision 15, with revision gates for graph/splitter storage, effect states, performance frames and command storage. A DSP caller receives that size. On open the host independently asks the SDK for its CPU/manual requirement and supplies a page-aligned, zeroed backend buffer if it exceeds the caller's capacity; a buffer below the declared service requirement is rejected. Both open forms share the allocation, including a nested no-event open. Failed opens free it; close joins the render thread, closes the SDK renderer, then frees it. Explicit CPU renderers keep their SDK contract. A sufficient caller buffer is reused; revisions beyond the verified service model retain the SDK size. No firmware is loaded or distributed at runtime, and no game's heap constants change.
- **Found on:** [Hyrule Warriors: Age of Calamity](../../dm/games/01002B00111A2000/README.md).
- **Check:** `make -C dm/host/tests GAME=<id> audren-work` checks independently obtained Horizon sizing fixtures, both public parameter layouts, uninitialized padding, unsupported revisions, nested opens, undersized buffers, failure cleanup, caller-owned storage and close lifetime. The sizing implementation also matched 360 seeded parameter sets executed through Horizon's original machine code across REV1–REV15. The game note records the original-heap reproduction and audio check.

## Command lists by SDK

### Incomplete startup lists must not select the command layout

- **Symptom:** no sound after boot; `audren: no DeviceSink (ID 0x13) in the command list` and a malformed-command error persist even when later command lists are valid.
- **Cause:** the host's render thread can generate commands before the game's first `RequestUpdate`. Mario Kart 8 Deluxe's first list ended in a zeroed third command, so none of the supported header layouts could walk it. `capture` nevertheless latched the default layout and consumed the one-time sink scan. Later SDK 6 headers were read as SDK 8–20 headers, and SDK 4's DeviceSink was never found. Retrying only header detection still leaves the sink scan consumed.
- **Fix:** select the header only when the whole list walks in a supported layout. Until then, return a silent frame before the sink scan; the first valid list can select both the header and its sink. `t_audren_layout` reproduces the failure and checks stereo PCM for SDK 4, 6, 16 and 21, with valid-first, empty and incomplete startup lists and SDK 21's short first list.
- **Found on:** [Mario Kart 8 Deluxe](../../dm/games/0100152000022000/README.md) (SDK 4.4.0; [PR #331](https://github.com/seedds/nxnative/pull/331)).

### Malformed later command lists and bounded histogram logging

- **Symptom:** ASan reports a stack-buffer-overflow in `capture` while logging the first full command histogram; a malformed list can also consume sink discovery or return PCM before its invalid tail is checked.
- **Cause:** a short valid list selected the header layout without running the histogram. A later malformed list entered the histogram scan, which stopped at its first invalid command but still logged an uninitialized string or adopted a sink from the valid prefix. Separately, accumulating `snprintf`'s untruncated return value advanced the next write past the 512-byte string.
- **Fix:** validate the entire command list on every capture before histogram, sink discovery or PCM output. Keep discovery pending for rejected lists, initialize the histogram string, and stop appending at the last complete entry that fits.
- **Check:** `t_audren_layout` covers malformed first, middle and trailing commands after layout selection, recovery to valid stereo PCM for SDK 4/5/6/16/21, and 64,000 synthetic commands whose histogram exceeds the log buffer. ASan reproduced both the uninitialized-string read and the truncated-append write before the fix.
- **Found on:** synthetic command lists from the [issue #313 static-analysis audit](https://github.com/seedds/nxnative/issues/313#issuecomment-6543080671); no gameplay failure was attributed to these logging defects.

### The final mix is taken from the DeviceSink's mix buffers

- **Symptom:** the CPU processor drops the final mix.
- **Cause:** `dsp::SendCommandBuffer`, `dsp::Wait` and `dsp::Signal` are stubs in the application build, and DeviceSink (command 0x13) is a no-op in `CommandListProcessor::Process`.
- **Fix:** take the output after `Process` from the mix buffers the DeviceSink command names (layout in `hle_audren.c`).

### SDK 4: DeviceSink is command 0xf of 0x130 bytes

- **Symptom:** no sound: `[RED] audren: no DeviceSink (ID 0x10) in the command list, 0 commands of 0x148 bytes`.
- **Cause:** SDK 4's command list has SDK 6's header, but its DeviceSink (`CommandBuffer::GenerateDeviceSinkCommand`, `sdk+0x19e690`) is ID 0xf and 0x130 bytes: device name +0x14, upsample buffer +0x118, input count +0x120, input indices as bytes from +0x124.
- **Fix:** `capture` takes the one 0x130-byte command with 1 to 6 inputs when there is no 0x148-byte one (`g_sink4` in `hle_audren.c`).
- **Found on:** [Mario Kart 8 Deluxe](../../dm/games/0100152000022000/README.md) (4.0.0, SDK 4.4.0; one boot).
- **Note:** its `AudioRenderSystem::Update` (`sdk+0x19b77c`) locks an `nn::os::MutexType` at +0x1d0, not SDK 16's `SdkMutexType` at +0x1f0; see [The renderer's update lock (`update_lock`)](#the-renderers-update-lock-update_lock).

### SDK 6: the DSP command header layout

- **Symptom:** no sound; red `audren: command 1 in the command list is malformed (magic 0 size 0)`.
- **Cause:** SDK 6's DSP command header is +0x04 size (s16), +0x06 command ID (s16), +0x10 enabled, where SDK 8–20 have +0x04 enabled, +0x05 ID, +0x06 size (`CommandListProcessor::Process`, `sdk+0xaaa00`); its DeviceSink is ID 0x10.
- **Fix:** `capture` in `hle_audren.c` takes the layout whose walk finds the 0xcafebabe magic on every command of the first valid list; [incomplete startup lists](#incomplete-startup-lists-must-not-select-the-command-layout) leave detection open.
- **Found on:** [Fire Emblem: Three Houses](../../dm/games/010055D009F78000/README.md) (SDK 6.5.0).

### SDK 5: a startup list that walks in two layouts, and a 0x138-byte DeviceSink

- **Symptom:** no sound: `[RED] audren: no DeviceSink (ID 0x13) in the command list, 0 commands of 0x148 bytes` and `[RED] audren: command 2 in the command list is malformed (offset 0x3e, …)`, with `first-frame commands 13, by command ID:  0×2`.
- **Cause:** SDK 5.4.0's command list has SDK 6's header. Its first list holds two commands, the first of ID 0x14 and 0x14 bytes, so it walks in the SDK 8–20 layout as well (the ID read as the size), and that layout was taken because it is tried first. Its DeviceSink (`CommandBuffer::GenerateDeviceSinkCommand`, `sdk+0x233890`) is SDK 4's (ID 0xf, device name +0x14, upsample buffer +0x118, input count +0x120) but 0x138 bytes, with the input indices as s16 from +0x124.
- **Fix:** `capture` in `hle_audren.c` takes a header layout only from a list that walks in exactly one; a list that walks in none or in several is a silent frame. The sink scan takes the one 0x130-byte (s8 indices) or 0x138-byte (s16 indices, `g_sink5`) command with 1 to 6 inputs. `t_audren_layout` covers SDK 5 and Bastion's first list.
- **Found on:** [Bastion](../../dm/games/010038600B27E000/README.md) (1.0.0, SDK 5.4.0).

### Unaligned command headers during layout probing

- **Symptom:** UBSan reports a misaligned `uint32_t` load in `cmd_ok` while `t_audren_layout` probes SDK 4/6 lists (issue #409).
- **Cause:** interpreting the command ID as another layout's size can advance the candidate pointer off word alignment. Typed header loads then have undefined C behavior even though arm64 supports the machine load. A wrong size could also take the next header outside the generated list.
- **Fix:** `cmd_size`, `cmd_id` and the magic check decode multibyte wire fields with `memcpy`. `cmd_ok` verifies that the complete header and command fit before consuming them; malformed-command diagnostics do not dereference a rejected header. All supported SDK layouts use the same readers, with no game gate.
- **Check:** `t_audren_layout` checks deliberately unaligned headers, every truncated header/body length, invalid signed sizes and stereo PCM for SDK 4/6/16/21, including recovery from incomplete startup lists. The shipped SDK 6 processor reads the enabled byte at +0x10 before dispatching any command, confirming the 0x11-byte minimum used by the parser. Its UBSan alignment suppression was removed.
- **Found on:** the sanitizer audit's SDK 4/6 fixtures, representing [Mario Kart 8 Deluxe](../../dm/games/0100152000022000/README.md) and [Fire Emblem: Three Houses](../../dm/games/010055D009F78000/README.md); no game crash was attributed to this undefined load.

### SDK 8: command IDs numbered differently

- **Symptom:** no music and no sound effects, only the movies' sound (the log repeats `audren: first-frame commands …` every frame and never prints `DeviceSink inputs`).
- **Cause:** SDK 8 numbers the DSP commands differently: its command list goes 4×6, 7×24, 11×2, 16×1, 21×1 where SDK 20's goes 7×6, 11×24, 15×2, 20×1, 25×1, and the output command (DeviceSink, the same 0x148-byte layout with device name `MainAudioOut`, six inputs) is 0x10, not SDK 16's 0x13. The host never found it and played silence.
- **Fix:** when the expected ID is missing from the first full command list, `capture` in `hle_audren.c` now takes the one 0x148-byte command with 1 to 6 inputs as the sink and logs the ID it adopted.
- **Found on:** [The Legend of Zelda: Link's Awakening](../../dm/games/01006BB00C6F0000/README.md) (SDK 8.2.0).

### SDK 20's `AudioRenderSystem` layout

- **Cause:** in SDK 20 the getters the host used (`GetExecutionMode`, `GetRenderingDevice`, `GetCommandBufferWorkBufferSize`) are inlined away, `GenerateCommand` takes and returns a `Span<std::byte>` (the generated list comes back in x0 / x1), the device and mode are words at +0x48 / +0x4c, the command buffer is at +0xf8 / +0x100, and `UpdateImpl` locks the mutex at +0x2d0 instead of +0x1f0. The DeviceSink command became ID 0x14 (SDK 20 inserted a command before it) with the same layout.
- **Fix:** `render_once` picks the layout by whether the Span version of `GenerateCommand` exists (`hle_audren.c`).
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md).
- **Note:** the render thread's call takes another route in this SDK too: see [The render thread's route through the public `ExecuteAudioRendererRendering` (SDK 20)](#the-render-threads-route-through-the-public-executeaudiorendererrendering-sdk-20); the update lock at +0x2d0 is in [The renderer's update lock (`update_lock`)](#the-renderers-update-lock-update_lock), and SDK 22 moved it ([The update lock read off `UpdateImpl`](#the-update-lock-read-off-updateimpl)).

### The update lock read off `UpdateImpl`

- **Symptom:** `CRASH sig=11 addr=0x20` at `nn::audio::server::AddressInfo::GetReference` (`sdk+0x249874`) on the render thread, under `CommandGenerator::GenerateDataSourceCommand` and `render_once`, minutes into a movie. The `AddressInfo` the crash register points at is all zeros, though the function had just read a non-null memory pool pointer from it. Or `[RED] audren: no update lock read off AudioRenderSystem::Update or UpdateImpl`, on an SDK whose code the scan does not recognize.
- **Cause:** the Span layout took the lock at a fixed +0x2d0, which holds for SDK 19.3 to 21.4. SDK 22 moved it: `UpdateImpl` in 22.2.8 (`sdk+0x238530`) and 22.2.5 locks the `SdkMutexType` at +0x2d8 (`add x19, x0, #0x2d8; …; mov x0, x19; bl SdkMutexType::Lock`), as `SendCommandToDsp`, `Start`, `Stop` and `FinalizeImpl` do. Locked at +0x2d0, the render excluded nothing, and the game's `RequestUpdate` rewrote a voice while its commands were being generated. From SDK 19 `Update` reads the system tick first and calls `UpdateImpl`, so a scan of `Update` finds no lock.
- **Fix:** `update_lock` (`hle_audren.c`) reads `Update`, then `UpdateImpl`, whatever the layout, and a miss in both is a red line. The start-up line names what it took: `update lock SdkMutexType at +0x2d8`. Test: `t_audren_layout`.
- **Found on:** The Legend of Zelda: Ocarina of Time (Switch 2, `0400486024DEC000`, update v131072; its profile is in pull request #1299): the second run through its opening movie crashed, and the run with the offset read off `UpdateImpl` played the opening through to Kokiri Forest with sound. Checked statically on the `sdk` builds on hand: SDK 19.3 to 21.4 read +0x2d0, as before. SDK 22.2.0 (Fortune's Weave, EA SPORTS FC 27) is not on hand.

### SDK 21 DSP command header without a magic

- **Symptom:** no sound; red `audren: command 0 in the command list is malformed (first word 0x181901 size 0)`.
- **Cause:** SDK 21's DSP command header has no magic: +0x00 enabled (bit 0), +0x01 command ID, +0x02 size (s16), +0x04 estimated time, +0x08 node ID (`CommandListProcessor::Process`, `sdk+0x24fd50`), and every command body moved 8 bytes forward. DeviceSink is still ID 0x14 but 0x140 bytes: input count +0x128, input indices +0x12c, upsample buffer +0x120 (written at `sdk+0x23a7b0`). `AudioRenderSystem` keeps SDK 20's offsets (update lock +0x2d0).
- **Fix:** `capture` (`hle_audren.c`) tries this layout when neither magic walk works, bounded by the generated list's length. Its first lists hold 4 commands or fewer, so the layout is now chosen on the first non-empty list.
- **Found on:** [Rhythm Heaven Groove](../../dm/games/0100D9F01D474000/README.md) (SDK 21.4.0, one boot).

## AudioOut and devices

### An AudioOut opened at a rate other than 48 kHz

- **Symptom:** the game quits before its first frame with `FATAL AudioOut sample rate 44100 not supported (48 kHz only)`, `CRASH sig=6` in `abort` under `au_open_at` / `h_au_OpenDef`, exit 134. Nothing is drawn.
- **Cause:** audout takes only 0 (the default) or 48000 in `AudioOutParameter.sampleRate` and refuses any other rate with `ResultInvalidSampleRate`, 0x699 (module 153, description 3; yuzu's `audio_out_system.cpp` and Ryujinx's `AudioOutputSystem.cs` agree). A game written for that asks for its own rate first and opens again with the defaults when refused, then reads the output's rate back. The host stopped the game instead of refusing the open.
- **Fix:** `au_open_at` refuses another rate as audout does: a `[RED]` line with the rate and the call site, and 0x699, before anything is allocated. The game then runs the path it runs on a console. Accepting the rate and converting it instead would run a path no console runs.
- **Found on:** [Mega Man Legacy Collection](../../dm/games/01002D4007AE0000/README.md) (SDK 3.7.0): `main+0x9a3c8` opens at 44.1 kHz, `main+0x9a3cc` tests the result and opens again with a zeroed parameter, then reads the output's properties for its buffer sizes; it plays at 48 kHz with 0 underruns. Reported in [PR #2723](https://github.com/seedds/nxnative/pull/2723), which accepted the rate.
- **Check:** `t_audio`'s `test_rate_refused`.

### Periodic diagnostics outside the AudioUnit callback

- **Symptom:** RealtimeSanitizer reports stdio locking in `au_render` at its 2,000-callback diagnostic boundary. A busy log writer can block that callback even when its PCM queue is full.
- **Cause:** `LOG` takes `stderr`'s stream lock and formats its message on the calling thread. The callback previously called it directly for its frame-count, queue-depth and underrun statistics.
- **Fix:** the callback publishes a bounded snapshot for the existing audio watchdog, which copies ready reports under the output-registry lock and writes them after unlocking. Its local copies own every log argument; a slow writer holds neither an output pointer nor the registry lock. The single-slot mailbox uses release/acquire ownership; a busy writer leaves the callback accumulating later windows instead of waiting or overwriting unread data. Reports retain the output ID, total callbacks, frame range, average queue depth and underrun/zero-padding counts, with the actual window length when several windows merge. The release-event notifier remains independent of diagnostics, so an event-driven game can keep refilling PCM while logging is blocked. Close stops the producer and takes any remaining snapshot under the same registry lock before freeing the output.
- **Found on:** the [synthetic real-time audio audit in issue #313](https://github.com/seedds/nxnative/issues/313#issuecomment-6523656102). No particular game's audible failure is attributed to this finding.
- **Check:** `t_audio_stats` calls the real callback with synthetic PCM and traps callback-thread stdio, including its stream lock. With the watchdog's writer deliberately blocked, each PCM buffer still triggers its guest release event and is refilled correctly; queued and merged reports preserve their fields. Close drains a second pending snapshot while the watchdog holds only a local copy, which it logs after the output was freed. Statistics alone cause no guest event. The fixture needs no sound device or game files.

### AudioOut release notification can sleep with pending work

- **Symptom:** PCM is consumed correctly and its buffer reaches the released queue, but the guest release event never arrives. The notifier is asleep with `notify_pending=1` and `notify_armed=0`.
- **Cause:** the notifier cleared `notify_armed` with a release-only store before checking `notify_pending`. A producer could publish pending work and see the old armed value, leaving the notifier to wake itself; without acquiring that producer's exchange, the notifier could read stale pending state and sleep. Apple-silicon code generated a store-release followed by acquire-PC loads, which permit this ordering.
- **Fix:** disarm with an acquire-release exchange. If the producer's armed exchange precedes it, the notifier acquires the pending publication. Otherwise the producer sees zero and posts, or finds the notifier already re-armed with its own semaphore post. No timeout, polling, callback logging or audio pacing changes are needed.
- **Found on:** shared CI's `t_audio_stats` ASan/UBSan fixture, reproduced locally without a sound device or game. This is a general AudioOut mechanism; no gameplay reproduction is claimed.
- **Check:** the existing blocked-diagnostics cases remain intact. The fixture also renders and individually reclaims 100,000 event-driven PCM buffers, so releases cannot be hidden by bulk notification coalescing. The old notifier naturally strands a release in this case; diagnostics distinguish event delivery, PCM contents and returned-buffer identity without retrying the failed wait.

### Stopping an AudioOut releases its pending buffers

- **Symptom:** FMOD waits for buffer release after stopping an AudioOut, hanging the game during a scene transition.
- **Cause:** the host stopped its backend but left unplayed and partially played buffers in the pending queue, so no callback could release them.
- **Fix:** after stopping a started backend, `au_release_pending` moves the pending buffers to the released queue in order, resets the partial-buffer position and signals the client's release event and the host waiter. Calling Stop on an already stopped output preserves buffers queued for its next Start.
- **Found on:** [Pokémon Brilliant Diamond](../../dm/games/0100000011D90000/README.md): reported on 1.0.0 in [PR #190](https://github.com/seedds/nxnative/pull/190); the 1.3.0 bring-up passed that transition before this fix.
- **Check:** `t_audio_spsc` covers a partially consumed buffer, queue wraparound, release notification, repeated Stop and buffers queued before Start, then runs its 100,000-buffer producer/consumer stress test.

### Flushing an AudioOut at the end of a movie

- **Symptom:** a null read in `nn::audio::FlushAudioOutBuffers` at `sdk+0x9a3e4` after the title movie stops its audio output.
- **Cause:** the host opens and owns the AudioOut. The unhooked SDK function looks it up in the SDK's own service-session table and dereferences the null result.
- **Fix:** implement `FlushAudioOutBuffers` on the host output. A started output with pending PCM pauses its consumer, returns the queued buffers in order, drops any staged PCM and resumes playback in the same state. It returns whether PCM was flushed and signals the release event when descriptors are returned. A stopped output keeps its buffers for the next Start.
- **Found on:** [Devil May Cry 3 Special Edition 1.0.1](../../dm/games/01007B600D5BC000/README.md), SDK 8.2.0. The movie teardown calls Stop, Flush, then Close.
- **Check:** `t_audio_spsc` verifies the return value, release order and signal, staged PCM, and the playback state. The Mac build reaches the title menu with the fix.

### RemoteIO's default I/O buffer duration

- **Symptom:** crackling on iOS only.
- **Cause:** RemoteIO asks for as many frames per callback as the audio session's I/O buffer duration, about 21 ms by default (1024 frames at 48 kHz), while the renderer keeps 4 blocks × 5 ms = 20 ms in flight. Every callback came up 1.3 ms short and was padded with zeros, about 47 gaps per second. Reproduced on the Mac by forcing 1024-frame callbacks (`DM_DBG_AU_FRAMES=1024` with `DM_AUDIO=1`: 1999 underruns in 2000 callbacks).
- **Fix:** `AVAudioSession` `setPreferredIOBufferDuration:0.005` (and 48 kHz) before the game opens audio and again on return to the foreground (`front_ios_audio_session` in `front_ios.m`); the device then calls back with 240 frames and nothing underruns.
- **Check:** when checking a new device, read the host's `audio #N device callbacks` line, normally reported every 2000 callbacks: frames per callback, queued blocks, underruns. A busy diagnostic writer can merge windows; the line states their actual callback count.

### AudioOut crackle on a Bluetooth route

- **Symptom:** regular clicks in menus and races over Bluetooth on an iPhone. Built-in speakers play normally. In matched windows of 8,000 callbacks, the speaker route had 4 underruns at 240 frames per callback. The Bluetooth route had 669 at 278–279 frames.
- **Cause:** RemoteIO can grant a different duration from the requested 5 ms. On the tested route, 256 frames at 44.1 kHz become 278–279 at the host's 48 kHz. A guest with two short buffers in flight can enter a callback with one partial block and one full block. If their combined length is too short, the callback fills the gap with zeros before the guest can refill a released buffer.
- **Fix:** When a guest AudioOut callback requests more than 5 ms, copy the tail of its last guest block before releasing the descriptor, provided the tail is at most 480 frames (10 ms at 48 kHz) and fits the host buffer. The guest can refill between callbacks. The next consumer, including the silent sink, plays that copy first. The buffer count includes the staged block until it drains. Stop discards it along with queued audio.
- **Found on:** [Need for Speed: Hot Pursuit Remastered](../../dm/games/010029B0118E8000/README.md), update 1.0.3 on iPhone with Nothing Ear earbuds.
- **Check:** `t_audio_stats` replays both callback sizes against two recycled 256-frame buffers through the real render callback. The Bluetooth replay goes from 666 underruns to zero in 8,000 callbacks and checks PCM order, the queue count and Stop/restart. Mono and stereo tests check that a 480-frame tail stages and still counts across a queue index wrap, and that a 481-frame tail stays in the guest queue. Playback on an iPhone with the upstream patch remains to be checked.

### The Mac's default I/O buffer

- **Symptom:** clicks and dropouts on the Mac, heard as clipping; the log's `audio #N device callbacks` lines show hundreds of underruns per 2000 callbacks. Closing an output can also log `[RED] audio device buffer: ... (status 560947818)` (`!obj`).
- **Cause:** the Mac's default output asks for 512 device frames per callback (10.7 ms at 48 kHz; 557 frames of the 48 kHz stream when the device runs at 44.1 kHz), more than a game that keeps only a few small blocks queued has ready every time. Unicorn Overlord on a MacBook Pro's speakers: 250–290 underruns in every 2000 callbacks at 48 kHz (0.1–0.2 s of zeros), about 1,000 at 44.1 kHz. Whether a game underruns depends on how much it queues: 13 Sentinels (2.8 blocks queued, like Unicorn Overlord's 3.0, but larger ones) had none at 512 frames.
- **Fix:** like iOS's session buffer, the Mac sets its output unit's device buffer to about 5 ms of device frames (`kAudioDevicePropertyBufferFrameSize`, 240 at 48 kHz, 221 at 44.1 kHz), within the device's supported range (`au_buffer` in `hle_audio.c`). It reapplies this when the default output changes and when the same device's output sample rate changes; `CurrentDevice` alone does not notify a rate change. An unchanged buffer is not written again, since a write can itself notify the format listener. Both listeners are removed before uninitializing or disposing the unit, including a failed open: disposal otherwise calls the listener after the device has gone (`!obj`). The log reads back the actual frame count. `DM_DBG_AU_FRAMES=N` asks N frames instead.
- **Found on:** [Unicorn Overlord](../../dm/games/010069401ADB8000/README.md) (Asian release 1.05 on the Mac).
- **Check:** [PR #262](https://github.com/seedds/nxnative/pull/262) reports Unicorn Overlord at 240 frames: 0 underruns in 10,000 callbacks; 13 Sentinels stays at 0. A silent Core Audio probe on a Mac mini reproduced the disposal error and the stale buffer after a rate change, then verified the fixes: default output switched between USB at 48 kHz and speakers at 44.1 kHz with callbacks continuing, and the same speakers at 44.1 / 96 / 48 kHz used 221 / 480 / 240 frames. The original default output and device rates were restored. `make -C dm/host/tests GAME=<id> audio-device` checks setup, device and rate notifications, scope filtering, buffer limits, synchronous notifications, the diagnostic override, absent devices, close and failed-open listener cleanup without audio hardware.
- **Open:** the listed HDMI output was not retained as the system default during the probe, so switching to it remains unvalidated. The probe verifies silent host playback; gameplay listening after these listener changes has not been repeated.

### Underruns in a run without a window

- **Symptom:** a windowless Mac run logs intermittent audio underruns. A long frame can occur around the same time.
- **Cause:** macOS normally starts a shell-launched host with an unspecified task role. XNU caps interactive QoS at the legacy level for that role, even when the host requests interactive QoS for guest threads. Under CPU contention the thread that feeds AudioOut can miss the time it has to refill the game's queue. [XNU task policy](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task_policy.c#L770-L821).
- **Fix:** when `DM_WINDOW` is unset, the Mac front end requests `TASK_DEFAULT_APPLICATION` to lift the QoS ceiling. Set `DM_WINDOWLESS_ROLE=0` to keep the existing role for an A/B run. If macOS refuses the request, the host logs the Mach error and starts the guest.
- **Check:** `t_front_role` always checks the opt-out and the installed role. The `xcode-27` runner on macOS 27.0.1 set the role but kept interactive priority at 20. `taskpolicy -c utility` reproduced that result on an Apple M6 with macOS 27.2.1, where an ordinary launch went from 31 to 46. The test skips the priority increase assertion when both readings agree below the legacy ceiling. [GitHub sanitizer job](https://github.com/seedds/nxnative/actions/runs/44516888710/job/135542380500), [NieR role comparison](../../dm/games/010056B015FE8000/README.md#windowless-mac-audio).
- **Found on:** [NieR:Automata The End of YoRHa Edition](../../dm/games/010056B015FE8000/README.md).

### The ring / silent switch muted the game on iOS

- **Symptom:** a game is silent on an iPhone whose ring / silent switch is set to silent, though the volume is up; a game or video app plays through the switch.
- **Cause:** the audio session's category was `AVAudioSessionCategorySoloAmbient`, which iOS silences with the switch.
- **Fix:** `front_ios_audio_session` in `front_ios.m` sets `AVAudioSessionCategoryPlayback`: the switch no longer mutes the game, and it still interrupts other apps' audio, as `SoloAmbient` did. The host still suspends its output when the app goes to the background (no background audio mode is declared).
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md) (iPhone: reported by the player); also [issue #155](https://github.com/seedds/nxnative/issues/155), whose commenter has to toggle the switch to hear any game.
- **Check:** open question, not run on a device: with the switch on silent, the game's sound should play; the log's `audio session:` line shows the session came up.

### Interruptions that stop RemoteIO callbacks

- **Symptom:** sound stays silent after Siri, an alarm, a call or another app's audio; a game whose audio thread waits for its buffers back (Wwise's poll-only output, FMOD) then waits forever.
- **Cause:** iOS stops calling the RemoteIO unit back without stopping it, so the host still thinks the output plays.
- **Fix:** three layers handle it:
  - `front_ios.m` observes `AVAudioSessionInterruptionNotification` (began → the silent sink stands in, ended → session up again and resume; becoming active also ends an interruption whose "ended" never came);
  - `front_ios.m` also observes `AVAudioSessionMediaServicesWereResetNotification` (`dm_audio_reset` recreates every AudioUnit);
  - a watchdog in `hle_audio.c` switches any started output whose device has not called back for 200 ms in focus to the silent sink, retrying the AudioUnit after 1, 2, 4, 8 s. A start that fails (session still held by a call) falls back the same way instead of aborting.
- **Check:** the log shows `audio session: interrupted`, `the device has not called back for N ms` and `AudioUnit restarted`. `tests/t_audio.c` (in `dm/host`) scenario 3 stops a playing AudioUnit behind the host's back.

### Audio gap after switching stereo outputs

- **Symptom:** up to about a second of game audio is lost when switching between stereo output devices. On iPhone, PR #2863 reports a gap when AirPods connect during play.
- **Cause:** Core Audio can pause render callbacks while switching devices. The host checked the channel count on a route change, so a stereo-to-stereo move used the same 200 ms stall check as an output that failed on an unchanged route. On a Mac mini M6 with macOS 27.2.1, a switch from USB to HDMI that then reverted to USB hit the stall check at 212 ms. The watchdog stopped the AudioUnit and waited another second to retry. Callbacks resumed 1.31 s after the switch request on main `d2fd78b4`.
- **Fix:** the existing route handler tells the watchdog when the output moves. It lets Core Audio finish the handoff and keeps the queued PCM available while the unit is running. A callback gap of over 200 ms on a new route triggers an immediate restart once the route has had 250 ms to settle. Repeated changes can extend that wait to 500 ms of callback inactivity. If the silent sink has already taken over, the new route brings the next attempt forward. Failed attempts use the usual backoff and keep the game paced. On iOS the same session observer detects output changes by port type and UID and reapplies the channel preference. The channel-count path still replaces a unit when its input layout has to change.
- **Check:** `t_audio_device` advances the watchdog clock explicitly. It covers a callback gap longer than the usual stall interval that resolves with its PCM intact, a route that stays stalled, a second switch during a blocked start, and backoff after the prompt retry fails.
- **Live Mac check:** on a Mac mini M6, macOS 27.2.1 and Xcode 27.2, the stereo USB output and built-in speakers switched in both directions and the AudioUnit followed without a host restart. With callbacks deliberately suppressed until the next AudioUnit start during those same hardware switches, callbacks resumed after 332–344 ms with this change, compared with 1,295–1,302 ms on main `d2fd78b4`. Each run confirmed that the unit was on the requested device.
- **Found on:** [Persona 4 Golden](../../dm/games/010062B01525C000/README.md), as reported from the NX18 fork in [PR #2863](https://github.com/seedds/nxnative/pull/2863). Physical iPhone and AirPods verification on the host revision is open.

### A blocked audio device start freezes the game

- **Symptom:** a game stops advancing while the Mac's selected output refuses to play. A process sample shows `AudioOutputUnitStart` waiting in the HAL, with the game's audio renderer waiting for a released PCM buffer.
- **Cause:** Start and the watchdog's retries stopped the silent sink and waited for the device while holding the output registry lock. A driver could block there for seconds or return success without delivering any callbacks.
- **Fix:** the silent sink paces the guest at 48 kHz while a host worker starts the device. Until the watchdog sees a callback after startup and joins the silent sink, the device returns silence. A device that fails to deliver its first callback within one second is stopped and retried with backoff. Each output can start independently. A Close during a start that the driver still holds returns at once: it unregisters the output, and the start's worker stops and disposes the unit and frees the output when the driver returns (waiting for it in Close held the game's thread as long as the driver blocked).
- **Check:** `tests/t_audio_device.c` (in `dm/host`) blocks the mock driver's `AudioOutputUnitStart`: Start returns and the queued buffer is released, callbacks play silence until the handoff, and Stop / suspend / reset / Close each run while the start is still blocked.
- **Open:** `AudioOutputUnitStop` still runs under `g_aos_lock` (Stop, suspend, the media services reset, the watchdog's stall path). A driver that blocked there as it does in Start would hold the lock; not seen so far.
- **Found on:** [Splatoon Raiders](../../dm/games/0400380020056000/README.md), with an unavailable HDMI audio output on the Mac ([issue #1030](https://github.com/seedds/nxnative/issues/1030)).

### AudioUnit construction before output publication

- **Symptom:** TSan reports `au_create` writing `a->au` while `au_watchdog` reads it under `g_aos_lock` when a second real output opens (issue #410).
- **Cause:** `au_open_at` put the output into the lifecycle/watchdog registry before joining its AudioUnit construction helper. The registry lock did not order the helper's writes.
- **Fix:** construct and join while the output is private, then publish it under `g_aos_lock`. Suspend, resume, reset and watchdog readers only discover the completed output. Construction remains outside that lock because joining the helper can yield the guest core.
- **Check:** `t_audio_device` asserts from inside AudioUnit creation that the pending output is absent from the registry; it failed before the fix. `t_audio` exercises real output lifetimes and watchdog recovery under TSan with the `au_create` suppression removed.
- **Found on:** host unit tests; no particular game's failure was attributed to this race.

### Audio across a background round trip on the Mac

`DM_AUDIO=1 DM_AUDIO_MUTE=1` takes the real Core Audio path with the output silenced, and `DM_OE_SCRIPT="bg=1@60,bg=0@66"` runs the same sequence as the iOS lifecycle callbacks (focus, audio take-over, guest clock freeze, graphics suspend). Send `dmhost` `SIGSTOP` / `SIGCONT` between the two to imitate iOS suspending the process. The silent sink that stands in while in the background does not make up the time the process was suspended (it used to pull seconds' worth at once and log hundreds of underruns).

### Several outputs at once (`audio #N`)

- **Symptom:** combined numbers mislead: one fully fed output plus one fed by nobody look like "every other callback underruns, 2.0 blocks queued".
- **Cause:** a game may open several outputs. Engage opens one AudioOut from Wwise (`main+0x177d924`, no release event, the game polls); on the phone it opened a second one later, and the Mac runs never did. Unity's FMOD also has an output (`main+0x4aec0c` / `0x4aec4c`).
- **Fix:** the host logs each output as `audio #N`: the open with its call site, Start / Stop / Close (the first 32 per output), and the callback statistics normally every 2000 of that output's callbacks, through the [watchdog](#periodic-diagnostics-outside-the-audiounit-callback).
- **Found on:** [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md).

### Checking audio without listening

`DM_AUDIO_DUMP=file` writes the PCM the host plays (16-bit, 48 kHz, stereo). RMS per second, clipping share, spectral flatness (music ≈ 0.1–0.5, white noise ≈ 0.85) and the strongest FFT peaks (they should land on musical notes) tell real music from noise or silence.

### AudioOut volume kept per output

- **Symptom:** a null read at `sdk+0x1f2314` as the first movie starts (the title menu's background, right after the first press), in `nn::audio::SetAudioOutVolume`, called from `main+0x1c4fbc`.

### The output device notification under its SDK 21 and 22 name

- **Symptom:** an `nn::diag` abort with Result 0xe15 on an audio thread at start, in `audio::CreateUserClientSessionByHipc` under `audio::AcquireAudioOutputDeviceNotification`, after the line `sf: the game connects to service aud:u itself`.
- **Cause:** SDK 21 and 22 name the output device notification `AcquireAudioOutputDeviceNotification` (older SDKs: `AcquireAudioDeviceNotificationForOutput`, and SDK 7's `AcquireAudioDeviceSwitchNotification`). SDK 22.2.0's version (`sdk+0x1f1e00`) opens a user session with `aud:u`, which the host does not serve, asks it for a read end and attaches it AutoClear. It keeps no per-process flag (the service keys each acquire by its event) and returns a Result.
- **Fix:** `hle_audren.c` takes the name over, first for SDK 21 (Splatoon Raiders); the same takeover serves SDK 22. The event is bound, signaled on a host output-route change, and the Result is 0. Signals use its binding lifetime, so destroying and reusing the same event storage cannot redirect an old audio subscription. The takeover keeps the older names' once-per-process flag, so a second acquire returns 0x499 where SDK 22.2.0's code would bind again. No game has been seen to acquire twice.
- **The release:** `ReleaseAudioOutputDeviceNotification` (`sdk+0x1f2ac0` in Nintendo Switch Sports Resort's sdk) asks `aud:u` through the device session coordinator, then destroys the event. The game destroys the event itself only if it is still initialized afterwards (`main+0x3af11a0`). `hle_audren.c` takes it over: it destroys the event it bound (which drops the binding) and clears the flag, so a later acquire binds again. With nothing acquired it does nothing. `t_audren_work` covers acquire, the refused second acquire, release and acquire again.
- **Found on:** [Fire Emblem Fortune's Weave](../../dm/games/04007EF01F8AE000/README.md) (Switch 2, SDK 22.2.0, `main+0xe7b9c`); [Nintendo Switch Sports Resort](../../dm/games/04008E001F098000/README.md) (`04008E001F098000`: the release, `main+0x3af119c`).

### No audio input devices

- **Symptom:** SDL3's audio driver lists the input devices (AudioIn) when its audio starts. `[RED] sf: the game connects to service audren:u itself`, then `nn::diag abort: Result 0xe15` under `audio::AcquireAudioDeviceNotificationForInput` (`sdk+0x5633c`).

- **Found on:** [Absolum](../../dm/games/0100A83022A22000/README.md) (SDK 18.3.2, FNA on .NET NativeAOT with SDL3; one boot each); [Portal 2](../../dm/games/0100ABD01785C000/README.md) (SDK 13.3.0: its audio thread at start, `main+0x19f37c`).

### Virtual audio input streams (SDK 21/22)

- **Symptom:** `[RED] sf: the game connects to service auddmg:u itself, which the host does not serve`, then `game called nn::diag abort: Result 0xa99` at `sdk+0x1f61ac` under `audio::ListVirtualInputDevices`. On main before real input support, the safe empty list also kept the game from hearing a microphone.
- **Cause:** the game lists virtual input devices when its audio starts (`main+0xf48124`) and opens the first with `audio::OpenInputStream` if there is one. The host intercepts those SDK symbols because it has no `auddmg:u` service.
- **Fix:** the Mac app offers an off-by-default microphone setting when a packed module imports the supported polling open. If enabled, the app requests macOS consent before it starts the host, including when the settings window is hidden. When enabled and authorized, one AUHAL unit feeds bounded queues for the polling streams. The callback uses preallocated buffers (resetting `mData` and `mDataByteSize` before `AudioUnitRender` and reading the rendered buffer pointers), downmixes and resamples the device to 48 kHz mono PCM16, and applies `DM_MIC_GAIN` (default `1`, unity, range `1..8`) and a soft limiter. A full queue drops incoming frames. Device changes rebuild capture off the callback thread, including returning from a missing device while streams stay open. If disabled, denied, or on iOS, the list is empty and opens fail. Legacy AudioIn, event-based streams, and guest stream statistics remain open. [#2796](https://github.com/seedds/nxnative/issues/2796)
- **Default gain:** `DM_MIC_GAIN` originally defaulted to `4` (+12 dB), which raised realistic laptop room noise (`-40 dBFS` peak / `-44.8 dBFS` RMS → `-28.0 / -32.7 dBFS`) above Ocarina of Time Humming mode's end-of-phrase silence floor so learned songs matched in DTW (23 hits) but never finalized or triggered in-game. At unity (`DM_MIC_GAIN=1`), the same `-40 dBFS`-noise phrase finalized (`dtw=0.135`) and triggered in-game playback, and quiet `-36 dBFS` singing also passed (`dtw=2.30`), as the game runs its own AGC and adaptive floor tracking. End-to-end synthetic-backend checks inside Ocarina of Time on an M6 (macOS 27.2.1) verified `48 kHz` mono, resampled `44.1 kHz` mono, and stereo downmix with zero underruns or drops. Hardware retest on a MacBook built-in microphone and physical USB unplug/replug remain open.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) (SDK 22.2.8). [PR #1822](https://github.com/seedds/nxnative/pull/1822) reports Mac gameplay with built-in and USB inputs, including resampling from 44.1 kHz. Star Fox imports the same calls.

### A DualSense's microphone over Bluetooth

- **Symptom:** with a DualSense connected over Bluetooth and its microphone asked to stream, the game reads buttons and sticks no one touched. With the controller lying still, GameController reported about 1,300 button presses and 300 sticks past half in 5 s. Over Bluetooth the controller is in no input-device list (macOS's Sound settings, the launcher's picker). Over USB it is an input device, but its mic may stay silent: muted, or in power saving.
- **Cause:** over Bluetooth the DualSense carries its microphone in its own HID input reports. After output report `0x32` asks for it (an audio-control packet `0x11` with bit 7 set, mask bit 0), input report `0x31` with byte 1 bit 1 set holds a mic frame in place of the pad's state: a frame counter at byte 2, then 71 bytes of Opus (10 ms). Two things make that unusable on a Mac:
  - GameController does not tell those reports from the state reports, and reads every mic frame as the pad's state.
  - macOS polls the controller every 15 ms, 66 reports a second in all, while the mic alone makes 100 frames a second. With the mic on, 43 mic frames and 22 state reports arrived each second, every report in sequence: the controller drops the other frames itself (its frame counter steps by 1 to 3).
- **Fix:** none over Bluetooth; the host never asks for the mic there. Over USB the controller is a USB audio device that the AUHAL capture records like any microphone. The launcher identifies a DualSense or DualSense Edge on USB from CoreAudio's `kAudioDevicePropertyModelUID` (`054C:0CE6` / `054C:0DF2`) and labels it "(USB)". When capture opens one, the host correlates the audio device to its own USB HID controller by USB VID:PID and `locationID` (from its `AudioBox`'s `BoxUID` or `AppleUSBAudioEngine` `DeviceUID`) or unique serial—failing closed on mismatch or ambiguity—and sends output report `0x02` (SetState), selecting the built-in mic, unmuted, without power saving (`dualsense_mic_mac.c`, `audio_input_dualsense_mac.m`). The formats come from the controllers wiki's DualSense data structures and awalol/DS5Dongle (MIT).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md)'s Ocarina Mic Input, on an M5 Pro Mac with macOS 27.2. A probe sent the same `0x32` report and counted what arrived: 5 s with the controller lying still, then 12 s moved and hummed into (the hum decoded at about 120 Hz, from 43% of the frames). After the stop report, the phantom input ended. Over USB, on a USB-C cable: the log's `built-in mic selected and unmuted`, captures at 48 kHz stereo with no underruns, zero fill or drops, and a live hum taken for Zelda's Lullaby at gain 2. The input is hot: at macOS's input volume for it (0.10), a hum at the controller clips before the gain, so a low gain suits it. DualSense Edge and multi-DualSense hardware checks remain open.
- **Check:** `make -C dm/host/tests GAME=<id> dualsense-mic` checks the USB report byte for byte and the CoreAudio-to-HID USB matcher. When capture opens a DualSense's USB audio, the log shows `audio input: DualSense over USB ("…", loc=0x…): built-in mic selected and unmuted`.

### `OpenAudioOut` without a release event (SDK 22)

- **Symptom:** `game called nn::diag abort: Result 0xe15, call site sdk+0x1f8704`, i.e. inside `nn::audio::CreateAudioOutManagerByHipc+0xb4`, before any audio device opened.
- **Cause:** SDK 22 calls **`nn::audio::OpenAudioOut(AudioOut*, const char*, const AudioOutParameter&)`** (`sdk+0x1f7914`, `nn::audio::OpenAudioOut(AudioOut*, const char*, const AudioOutParameter&)`'s failure path) — the overload without the `SystemEvent` the host implemented (`_ZN2nn5audio12OpenAudioOutEPNS0_8AudioOutEPKcRKNS0_17AudioOutParameterEPNS_2os11SystemEventE`). With no hook the SDK's own IPC path ran and the audout service is not there.
- **Fix:** `hle_audio.c` gained the 4-argument hook, which opens through the same `au_open_at` and leaves the release event NULL (`au_open_at(g, NULL, name, param, __builtin_return_address(0))`), so the output polls its released buffers. The log then reads `OpenAudioOut … , no release event (the game polls)`.
- **Found on:** [Well Dweller](../../dm/games/0100217023F6C000/README.md) (SDK 22.2.0); the game's first `AudioOut` is the "DeviceOut" form, the second its 48 kHz music output.

### SDK 21's OutputStream on a virtual output device

- **Symptom:** `[RED] sf: the game connects to service auddmg:u itself, which the host does not serve`, then `game called nn::diag abort: Result 0xa99` under `nn::audio::GetDefaultVirtualOutputDevice` (`sdk+0x221520`, `audio::detail::GetVirtualOutputDeviceProperties`).
- **Cause:** SDK 21 has a second output interface beside AudioOut: `GetDefaultVirtualOutputDevice` names a virtual device, `OpenOutputStream` opens a stream on it with a `StreamFormat` {sample format, channels, sample rate} (5, float), a capacity in frames and, in one overload, a system event; the game writes a period at a time with `WriteOutputStream` once `GetOutputStreamFreeFrameCount` covers it, waiting on the event with a short timeout between writes. States as games read them: 0 not open (the SDK's own answer for a null stream), 1 stopped, 2 started: a game's close path stops a stream in state 2 and purges and closes one in state 1, so a wrong answer leaves it open for good. `GetOutputStreamStatistics` returns a 24-byte struct through x8. Every call reaches the service.
- **Fix:** `hle_audio.c` opens one AudioOut per stream, its release event the stream's: each write becomes a 16-bit interleaved block (float clamped and scaled), the free count is the capacity less the frames still queued, `Purge` drops the queued blocks, `SetOutputStreamGain` is the AudioOut's volume (no fade), `StartOutputStreams` starts several, and the statistics report nothing. Input streams have their own [capture path](#virtual-audio-input-streams-sdk-2122). The default virtual device is `AudioVirtualOutput`, a name of the host's.
- **The frames are interleaved:** `WriteOutputStream` takes L, R, L, R, although the game's code that zeroes an unfilled tail (`main+0xad1684`) steps by a period per channel. Read as planar, each 10 ms block's first half played as left and its second half as right, each at half speed: all sound an octave low (voices very deep) with a jump at every block (crackling). In `DM_AUDIO_DUMP` that shows as a spectrum mirrored about 12 kHz (33-39 % of the energy above 20 kHz where 0.00 % belongs) and channels whose samples alternate between two signals (lag-1 autocorrelation 0.18, lag-2 0.99). `t_output_stream` checks the order.
- **A larger statistics result ends the game:** Star Fox keeps its 24 bytes at `sp` with its stack canary right behind them (`main+0xbce9b90`), so a 32-byte result ended in `__stack_chk_fail` on the audio thread (`CRASH sig=4`, `lr=main+0xbce9f98`).
- **Focus:** Star Fox closes its stream when its window loses focus and opens a new one when it regains it; 14 rounds went by with the sound intact.
- **Found on:** Xenoblade Chronicles 2, Nintendo Switch 2 Edition (`0400E95004038001`) (SDK 21.4.4, one or two 2-channel streams at 48 kHz, 10 ms periods, 40 ms capacity; the second when the active device is `AudioExternalOutput`); [Star Fox](../../dm/games/0400E88025B1A000/README.md) (Wwise 2024.1, SDK 21.4.4).

### The virtual output device's properties, and the OutputStream open without flags

- **Symptom:** `[RED] sf: the game connects to service auddmg:u itself, which the host does not serve`, then `game called nn::diag abort: Result 0xa99, call site sdk+0x224d1c` (`audio::detail::GetVirtualOutputDeviceProperties`), right after `GetDefaultVirtualOutputDevice`.
- **Cause:** before each OutputStream open the game asks for the default virtual output device's properties with `nn::audio::GetVirtualOutputDeviceProperties` (`main+0x5eda90`, `main+0x7a0414`); the SDK's version asks the device manager service for the device's 0x228-byte profile. It then opens the stream with the `OpenOutputStream` overload that takes no flags (`main+0x5edb34`), which the host did not take over either.
- **The properties:** `VirtualDeviceProperties` is 0x110 bytes, filled from the profile at `sdk+0x224cd4`: the name asked about (+0x00, 0x100 bytes); the profile's +0x218 at +0x100, the device's shortest stream as a duration in ns (`OutputStreamImpl::Open` refuses a capacity under ceil(duration x rate / 1e9) frames with 0x899, `sdk+0x225a94`; the input stream open the same); and the profile's +0x108 at +0x108, a 32-bit word nothing in the sdk reads. Both of the game's callers, and Donkey Kong Bananza's two (`main+0x57cadc`, `main+0x187cee4`), only test the Result.
- **Fix:** `hle_audio.c` answers for its one device, `AudioVirtualOutput`: the name, a shortest stream of 10 ms (one period as Xenoblade Chronicles 2 and Star Fox write it; the host's own open sets no minimum) and 0 in the unidentified word. Any other name gets a red line and a failure. The overload without flags opens like the others. `t_output_stream` covers both.
- **Open:** what the +0x108 word means; no caller seen reads it.
- **Found on:** [Nintendo Switch Sports Resort](../../dm/games/04008E001F098000/README.md) (`04008E001F098000`; SDK 20+).

### The AudioOutBuffer handed to the SDK is its own 40-byte object

- **Symptom:** a game that resamples its own audio plays, in one block of every four, the sound of four blocks earlier: Metro 2033 Redux (44.1 kHz to 48 kHz in the game's own resampler) re-appended 518 of its 2,095 loud 8192-byte blocks (24.7 %) still holding the contents of the block 4 appends back, so that audio left 170.6 ms behind; after the fix 0 of 1,989, with no block appended twice or lost and no underruns.
- **Cause:** the host declared `nn::audio::AudioOutBuffer` as 24 bytes, data at +0x00, capacity at +0x08, data size at +0x10. The SDK's object is 40 bytes, `{next, buffer, buffer_size, data_size, data_offset}`, the audout service's own buffer format: data at +0x08, capacity at +0x10, data size at +0x18 (`SetAudioOutBufferInfo`, `sdk+0x80f80`; the same in Hades's SDK, `sdk+0x142ab0`). The SDK's `AudioBufferList` links buffers through `next` at +0x00, where the old layout wrote the data pointer. The host does not take `GetAudioOutBufferBufferSize` over, so the SDK's own (`sdk+0x80fb0`) read the host's data-size field as the capacity and answered with the previous block's: 2047 frames of the 2048 the resampler had room for. On every fourth block the resampler then wrote nothing, and the game appended that block at full length holding the earlier contents.
- **Fix:** the host's buffer description is the SDK's object: one definition, `aout_buf` in `dm/host/hle.h`, five fields at the SDK's offsets with a `_Static_assert` on them, which `hle_audio.c`'s AudioOut and the blocks `hle_audren.c` appends to it both use. The descriptor functions (`SetAudioOutBufferInfo` in both overloads, `GetAudioOutBufferDataPointer`, `GetAudioOutBufferBufferSize`, `GetAudioOutBufferDataSize`) run in the sdk, as AudioIn's do, so no accessor can read a layout of the host's; they are the same plain stores and loads in the SDKs of Metro 2033 Redux (SDK 8.2.0), Hades, Fire Emblem: Three Houses (which also has the overload without a buffer size, storing only +0x08 and +0x18) and PRAGMATA (Switch 2). `GetAudioOutBufferBufferSize` answers 8192 on every block.
- **Found on:** [Metro 2033 Redux](../../dm/games/0100D4900E82C000/README.md) (SDK 8.2.0, 4A Engine).
- **Check:** `t_audio`'s buffer-layout case hands the device callback an object written at the SDK's own offsets, its `next` linked and its data size 4 bytes short of its capacity: the callback must play exactly the data size from the data pointer, release the buffer and leave `next` alone. Under the 24-byte layout it would read `next` as the data.

## Output channels

The output route decides how many channels the device takes: on the Mac, six when Core Audio maps 5.1's front pair, center and surround pair onto the device's outputs via its preferred speaker layout (`dm_audio_output_channels`, `hle_audio.c`); on iOS, six when the audio session has six output channels (`front_ios.m`); otherwise stereo. Games read it from `GetActiveAudioDeviceChannelCountForOutput` and the SDK 7 name, and each output AudioUnit follows it. The in-process renderer queues both its six channels and its original stereo fold (`hle_audren.c`).

### Stereo only on a 5.1 system

- **Symptom:** on a Mac connected over HDMI to a 5.1 TV, receiver or soundbar, or an iPhone on such a route, a game that writes six channels plays in stereo: its center, LFE and back channels come out of the front pair as a downmix. The game is told the device has two channels.
- **Cause:** `GetActiveAudioDeviceChannelCountForOutput` reported two channels on every route, and every six-channel output was downmixed to stereo before it reached Core Audio.
- **Fix:** the host reports the route's count, and a six-channel output on a six-channel route goes to the unit as it is, with the unit's input layout set to `MPEG_5_1_A` (front-left, front-right, center, LFE, back-left, back-right). Core Audio then maps each channel to its speaker in the device's own layout. On HDMI that order puts the LFE before the center (`L R LFE C Ls Rs …`), so six channels sent without a layout would play the center on the LFE. On a stereo route the host downmixes a six-channel output with the renderer's default coefficients; Core Audio's own 6 → 2 would keep only the front pair. Outputs with another channel count go as the guest writes them, and an output opened with a channel count of 0 is stereo.
  - `dm_audio_route` reads a cache initialized on the calling host stack (all HLE takeovers already switch to it). The Mac listens to the system default output and that device's stream format and speaker layout, including when no AudioUnit is open; opens and resume also refresh it. A changed channel count or Mac device identity publishes the cache before scheduling the guest's output-device notification off the audio registry lock.
  - The Mac's route is the device's stream format and preferred speaker layout: a device whose layout maps surround (5.0 / 5.1+) onto its outputs is a six-channel route ([Center and back channels silent on an audio interface](#center-and-back-channels-silent-on-an-audio-interface)). The host does not change a device's format or layout.
  - On iOS the session asks for `maximumOutputNumberOfChannels` (up to six) at boot, on return to the foreground and on each route change. Headphones, AirPods included, are expected to report two channels and stay stereo (not yet seen on a device).
  - A route change while an output plays queues a check off the notifying thread. Each six-channel guest output, or host DeviceSink output, whose unit no longer fits the route gets a replacement through the same lifecycle path as an iOS media-services reset (`au_reopen`). The silent sink paces queued audio meanwhile; a start still held by the driver retains its old unit until it returns. A failed replacement is tried again on the next route change or resume. iOS asks for the new route's channels before checking, and resume checks changes made during suspension.
  - The in-process renderer never freezes its format to the opening route. Each queued sample contains six channels followed by a stereo fold computed from the original int32 mix before resampling and clamping. The device callback selects six or two, even halfway through a queued block. This preserves current main's stereo PCM at both 48 kHz and 32 kHz: folding already clamped surround can destroy cancellation (front-left -30000 plus center 60000 gave -6834 instead of 12420). Guest AudioOuts retain the count the game opened; their device-change event lets the game query the new count and reopen when needed.
  - `DM_AUDIO_DEVICE` pins the Mac's output to a device by name, for tests. BlackHole 2ch reads as stereo; a six-channel virtual device needs BlackHole 16ch set to 5.1 under Configure Speakers in Audio MIDI Setup (its first six channels carry the 5.1 signal).
- **Open:** switching between BlackHole devices can pause callbacks about 230 ms before the route notification. See [Audio gap after switching stereo outputs](#audio-gap-after-switching-stereo-outputs) for the watchdog's recovery once the host sees the change. The system's binaural rendering of six-channel PCM over AirPods Pro 2 (`setSupportsMultichannelContent`, `isSpatialAudioEnabled` on the route) remains untested. The route is the device's first output stream; a device whose first stream is stereo stays stereo.
- **Checked:** the current-main rework adds route changes without an open unit, selecting both representations mid-block, and destroyed/rebound notification lifetimes. Stereo PCM hashes match the pre-surround output at 48 kHz and 32 kHz over three frames including clipping and resampler history. `t_audio_device` (mock units: six channels reach the device unchanged with the layout set, the downmix values and its clamp, the route's count, a route change both ways, a failed new unit made again at the next change, stereo and mono outputs left as they are) and `t_audren_layout` (the six-channel resampler, the sink's six inputs in order, a mono sink on the front pair). `dm/tools/audio_channel_check.py` plays test tones (440, 660, 880, 60, 1320, 1760 Hz for front-left, front-right, center, LFE, back-left, back-right) through the host on a named device and captures that device's input in-process (`DM_AUDIO_CAPTURE`): the check asks for each channel's own tone 12 dB above the others, and for the downmix within 1.5 dB of the host's coefficients (`--stereo`). - **Current-main rework validation:** MacBook Pro M4 Pro, macOS 27.2.1, Xcode 27.2: audio/output-stream/SPSC/statistics/device/renderer fixtures pass, including ASan/UBSan on the changed frame and route boundaries. The four renderer slots and capture scratch reserve 566,688 more bytes (0.54 MiB); active resident memory depends on the renderers opened. - **Found on:** PR #2234's host probe on a Mac over HDMI to an LG TV, passed over eARC to a Sonos system (the TV reads as 8-channel 48 kHz PCM in HDMI's order): `t_audio_live` with `DM_AUDIO_LIVE_PCM` (a spoken name on each channel and a 45 Hz tone on the LFE) played each from its own speaker. Not yet checked in a game, or on an iPhone.

### Center and back channels silent on an audio interface

- **Symptom:** on a Mac with a multi-output audio interface, sounds placed at the player are almost silent while music plays normally. The log reads `audio output route: "<device>" has 22 channels, the host plays six (5.1)`.
- **Cause:** the route treated six or more channels as 5.1. An interface's outputs are discrete, usually with stereo monitors on the first two, so the center, LFE and back channels went to outputs with nothing connected.
- **Fix:** the Mac route is six channels only when Core Audio's own `kAudioFormatProperty_ChannelMap` from `MPEG_5_1_A` to the device's preferred speaker layout (`kAudioDevicePropertyPreferredChannelLayout`, covering descriptions, standard tags and bitmaps) routes left, right, center and both surrounds within the stream's output channels. The LFE is optional, so a 5.0 system (five or more outputs) stays surround, and any layout whose surround labels Core Audio leaves unmapped falls back to stereo. Any other device, including one with unlabelled channels or no readable layout, gets the stereo downmix, which keeps every channel audible. A real surround system connected through an interface is enabled under Configure Speakers in Audio MIDI Setup, and the host follows that change live.
- **Open:** not yet run on a physical multi-output interface or an HDMI surround sink. An HDMI sink that reports no speaker labels would now play stereo until it is set under Configure Speakers.
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md) on a MOTU UltraLite-mk5 (22 outputs; issue #3263).

## Codecs

### Hardware Opus decoders built on the SDK's software decoders

- **Symptom:** an abort in `sm::Initialize` under the hardware Opus decoder's C interface; for the multi-stream one, under `nn::codec::GetHardwareOpusMultiStreamDecoderWorkBufferSize(int, int, int, int, int)` (at `nnMain`, CRI's Opus streams). An abort in `sf::hipc::InitializeHipcServiceResolution` under `codec::GetHardwareOpusDecoderWorkBufferSize(int, int)` (`main+0x31f8e8`, early in `nnMain`). A game that builds `HardwareOpusMultiStreamDecoder` with the imported constructor and then calls it through its vtable.
- **Cause:** the hardware decoders are a service. The `HardwareOpusMultiStreamDecoder` class's 12 vtable slots match the SDK's software `OpusMultiStreamDecoder` one by one. SDK 11 has a work buffer size form without the option argument; the host had only the three-argument one.
- **Fix** (`hle_codec.c`):
  - the classes: the constructor binds to the software class's, which builds the software decoder in place (0x38 of the 0x48 bytes), as for the single-stream `HardwareOpusDecoder`, and so do the members ([A hardware Opus class's members called directly](#a-hardware-opus-classs-members-called-directly)); `GetHardwareOpusMultiStreamDecoderWorkBufferSize` returns the software size. Both destructors are a bare `ret`.
  - the single-stream C interface (`GetHardwareOpusDecoderWorkBufferSize`, `InitializeHardwareOpusDecoder`, `DecodeOpusInterleavedWithHardware`, …) is forwarded to the `sdk`'s software `OpusDecoder` C interface with a host-held decoder state per game object.
  - the multi-stream C interface, including the SDK 12+ overload with an option argument, goes to the `sdk`'s software `OpusMultiStreamDecoder` C interface, with a host-held state per game object as for the single-stream decoder. `GetHardwareOpusMultiStreamDecoderProcessingTime` reports 0.
  - the two-argument `GetHardwareOpusDecoderWorkBufferSize` is hooked beside the three-argument one.
- **Found on:** [Hyrule Warriors: Age of Calamity](../../dm/games/01002B00111A2000/README.md) (SDK 9.6: only the `HardwareOpusMultiStreamDecoder` class and the four-argument size); [The Legend of Zelda: Tears of the Kingdom](../../dm/games/0100F2C0115B6000/README.md) (1.4.3, the single-stream C interface); [Big Brain Academy: Brain vs. Brain](../../dm/games/0100620012D6E000/README.md) (SDK 11.4.3, the two-argument size); [Unicorn Overlord](../../dm/games/010069401ADB8000/README.md) (SDK 16.2.4, the multi-stream C interface; one boot).

### A hardware Opus class's members called directly

- **Symptom:** an abort under `hwopus` (or a second, uninitialized decoder) in movie or audio setup, from a game that calls `nn::codec::HardwareOpusDecoder`'s members itself (`Initialize`, `GetWorkBufferSize`, `Finalize`, `DecodeInterleaved`, the destructors), not through `IOpusDecoder`'s vtable.
- **Cause:** the host took over only the constructor, which builds the SDK's software `OpusDecoder` in the object. Calls through the vtable then reach the software members, but a game that holds the decoder by value or by its own class calls the hardware members directly (the compiler devirtualizes them), and they ran on the software object. In Super Mario Party's `sdk`, `Initialize`, `DecodeInterleaved` and `GetWorkBufferSize` go to the hardware C interface (which the host serves with a second decoder state beside the object), and `Finalize`, `IsInitialized`, `GetSampleRate`, `GetChannelCount` and `Reset` read the hardware layout (`Finalize` calls through `+0x08`, `sdk+0x22ff10`). The multi-stream class is the same.
- **Fix:** each hardware member, both classes, binds to the software class's member of the same signature: a guest alias (`HLE_FORCE_ALIAS`, `hle.h`), an entry in the forced take-over table that binds every reference to the loaded modules' definition of another name, with no host code and no restated signature. The constructor is one too (the option in `w1` has no software counterpart); `C2` and `D2` bind to `C1` and `D1`, the same code without virtual bases. Each SDK defines the same member set for both classes of a pair (Super Mario Party's has `Reset` and no `Decode` or `SetContext`, ŌKAMI HD's the reverse); a target no module defines is logged as a red line and the reference keeps its binding. `t_symbols` checks the alias binding.
- **Found on:** Just Dance 2022 (`0100EA6014BB8000`, SDK 11.4.0; [PR #2746](https://github.com/seedds/nxnative/pull/2746), not in the games table) and [Rayman Legends: Definitive Edition](../../dm/games/01005FF002E2A000/README.md) (SDK 1.3.1; [PR #1540](https://github.com/seedds/nxnative/pull/1540)). The bindings were checked against Super Mario Party's and ŌKAMI HD's `sdk` symbols.

### A hardware Opus class decoded through the C interface

- **Symptom:** `FATAL Opus decoder <addr> was not initialized by the host` in `DecodeOpusInterleavedWithHardware` when playing an Opus track in a game that constructs and initializes `nn::codec::HardwareOpusDecoder` through the C++ class.
- **Cause:** The C++ `HardwareOpusDecoder` and `HardwareOpusMultiStreamDecoder` constructors and `Initialize` methods bind to the SDK's software classes. Those methods build the software `OpusDecoderType` or `OpusMultiStreamDecoderType` in guest memory at `this + 0x08` behind the vtable pointer, and register nothing in `objmap`. Just Dance 2022 initializes its decoder with `HardwareOpusDecoder::Initialize` at `main+0x843498` and passes `this + 0x08` to `DecodeOpusInterleavedWithHardware` at `main+0x843738`. `opus_soft` checked only `opus_mgr_dec_soft` and `objmap_get`, and the multi-stream C functions called `opus_soft` instead of checking `OpusMultiStreamDecoder`.
- **Fix:** When `objmap_get` finds no host block, `opus_class_member` in `hle_codec.c` reads the word at `hw - 8` with `vm_read_overwrite` and compares it against the software class vtable, `_ZTVN2nn5codec11OpusDecoderE + 0x10` or `_ZTVN2nn5codec22OpusMultiStreamDecoderE + 0x10`. When it matches, `opus_soft_for` and `opus_fini_for` pass `hw` directly to the SDK's software C functions without freeing guest memory. `t_codec_opus` tests both the C path and the mixed C++ and C path for single-stream and multi-stream decoders, plus null, low, unmapped, wrong-vtable, and uninitialized pointers.
- **Found on:** Just Dance 2022, `0100EA6014BB8000` v0, SDK 11.4.0, follow-up to [PR #2746](https://github.com/seedds/nxnative/pull/2746), not in the games table.

### SDK 21's hardware Opus decoder manager

- **Symptom:** `game called nn::diag abort: Result 0xe15` under `nn::codec::GetHardwareOpusDecoderManagerWorkBufferSize` (`sdk+0x323180`), the game's sound setup.
- **Cause:** SDK 21's asynchronous interface to the hardware decoder: a manager (`HardwareOpusDecoderManagerType`, with a system event, a decoder count and an I/O buffer count) owns decoders (`InitializeHardwareOpusDecoder` with a manager). The game enqueues one packet per call (`EnqueueOpusDataToHardwareOpusDecoder`, Nintendo's 8-byte header and the packet, as `DecodeOpusInterleaved` takes it; it expects all of it consumed), calls `ExecuteHardwareOpusDecoderDecoding` once per audio frame, dequeues finished frames (`DequeuePcmInterleavedDataFromHardwareOpusDecoder`) as many as the completed count, and reads the waiting / executing / completed counts and the free I/O buffers. It tells an initialized manager by the struct's first word.
- **Fix:** `hle_codec.c` keeps the manager in host state (its pointer in that first word) and decodes with the `sdk`'s software `OpusDecoder`: Enqueue queues the packet and takes an I/O buffer, Execute decodes every waiting packet on the caller's thread and signals the event, Dequeue hands back a frame and its buffer. So a request is never "executing". A packet the decoder refuses completes as 20 ms of silence, with a red line. `ResetHardwareOpusDecoder` and `FinalizeHardwareOpusDecoder` serve both interfaces.
- **Found on:** Xenoblade Chronicles 2, Nintendo Switch 2 Edition (`0400E95004038001`) (SDK 21.4.4: a mono manager of 128 decoders and 255 I/O buffers, a stereo one of 72 and 160, 48 kHz, 20 ms frames); [Star Fox](../../dm/games/0400E88025B1A000/README.md) (the same figures).

### One key for the two forms of the Opus decoder

- **Symptom:** `CRASH sig=11 addr=0` in `h_codec_HwOpusFini`, the first time the game finalizes a decoder.
- **Cause:** the older interface keeps the software state in `objmap` under the game's decoder object, and SDK 21's manager form its own record under the same key. `opus_mgr_dec_fini` told them apart by a field at +0x10, 0 in the software state as far as Star Fox had shown, but the work buffer's size in this one. It read the state as a record, so a pointer in it became the manager.
- **Fix:** a manager's decoder is kept under the object + 1 (`OPUS_MGR_KEY`), so the look-up itself says which form it is; `GetHardwareOpusDecoderSampleRate` and `ChannelCount` now also read a manager's decoder correctly.
- **Found on:** [Kirby Air Riders](../../dm/games/040077201BE50000/README.md) (SDK 20.5.26, 48 kHz stereo, the older form).

## Timing and catch-up

### At least one rendered frame between two updates

- **Symptom:** the light limiter crashed on a null state pointer (`ApplyLightLimiterEffect`, `sdk+0x228494` / `sdk+0x228614`).
- **Cause:** an effect's `NeedsInit` parameter state (`LightLimiterInfo::Update`, `sdk+0x21a988`) is set only on the update where `isNew` is true and cleared on `GenerateCommand`; a second `RequestUpdate` before any render overwrites it with the game's value. On Horizon (`device=0, mode=0`), `AudioRenderSystem::Update` (`sdk+0x20c264`) clears the renderer's `SystemEvent` under the update lock before returning `RES_OK`, so any signal from a frame rendered before the update is discarded and `WaitSystemEvent` always blocks for a fresh render. Because `ar_open` substitutes CPU + manual mode (`device=1, mode=1`), `OpenAudioRenderer` creates a separate `SystemEvent` (`a->ev`) that `ExecuteAudioRendererRendering` signals and the game waits on, while `AudioRenderSystem::Update` cleared its own unused internal event (`[this+0x1c0]`). A stale signal (from startup prefill or a frame rendered during a slow audio-thread step such as `AddLightLimiter`) let `WaitSystemEvent` return in ~0.05 ms and issue a second update with zero renders in between.
- **Fix:** `h_ars_Update` (`hle_audren.c`) holds the renderer mutex (`a->mu`, shared with `render_main`'s `exec()`) across `orig()` and, on `RES_OK`, clears `a->ev` (`hle_clear_system_event` for kernel events, `nn::os::ClearSystemEvent` for local CPU-auto events), restoring Horizon's atomic update-clears-event vs. render-signals-event contract. Until 2026-11, `h_ars_Update` worked around the stale signal by rendering synchronous catch-up frames into a 4-frame queue; removing that queue eliminates the catch-up side effects below.
- **Found on:** [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md). Verified on Wonder 1.2.1 (M4 Pro, macOS 27.2.1, `DM_AUDIO=1 DM_AUDIO_MUTE=1`): disabling catch-up without clearing `a->ev` reproduced the `sdk+0x228614` crash after `update #27`; enabling `hle_clear_system_event` with zero catch-up gave 0 back-to-back updates, 0 crashes and 0 underruns across 1,800 frames / 6,000 callbacks.
- **Check:** `t_audren_layout --cadence` and `t_audren_work` verify event clearing on `RES_OK`, preservation on failure / manual renderers, and stale-signal clearing on an event-paced driver. `DM_AUDREN_TRACE=1` logs each of the first 200 updates with the frames rendered since the previous one.

### A sound driver that never waits on the renderer event

- **Symptom:** the sound runs about 50 times faster than the output; the loop runs 11,000 updates a second on one core.
- **Cause:** Square Enix's `SQEX::Sd::Driver::Core::CoreAudioOut` (its loop at `main+0x442c5c0`) appends a wave buffer, mixes the next block on the same thread, calls `RequestUpdate` and takes the next released buffer. It waits on the renderer event only when no buffer is released. With the former catch-up renderer in `h_ars_Update`, every update rendered a catch-up frame and immediately released the buffer just appended, so the loop never waited; discarding full-queue catch-up output let it run unchecked, and waiting on the full queue instead stalled polling drivers ([An update that waited for the catch-up queue](#an-update-that-waited-for-the-catch-up-queue)).
- **Fix:** `h_ars_Update` no longer renders catch-up frames (`hle_audren.c`; see [At least one rendered frame between two updates](#at-least-one-rendered-frame-between-two-updates)). `RequestUpdate` releases no buffer early and clears `a->ev` atomically, so `CoreAudioOut` waits on the renderer event and paces at 5 ms on `render_main`'s renders, as on Horizon. Until 2026-11, a 4-frame catch-up queue waited up to 50 ms when full and did not signal the renderer event on queued playback (which had caused every frame to become a catch-up on [Big Brain Academy: Brain vs. Brain](../../dm/games/0100620012D6E000/README.md), about 38,000 catch-up renders instead of 37).
- **Found on:** [DRAGON QUEST XI S: Echoes of an Elusive Age – Definitive Edition](../../dm/games/01006C300E9F0000/README.md). Not rerun live since catch-up removal; `t_audren_layout --cadence` models `CoreAudioOut`'s append/update/event-wait loop with 2 wave buffers across 250 blocks (250 fresh renders, 0 underruns).
- **Check:** `audren: rendered 12000 frames, N of them not silent` shows whether a game's sound reaches the output.

### An update that waited for the catch-up queue

- **Symptom:** movies play at about half their rate (16 fps for a 29.97 fps Bink movie), frames of about 62 ms with the GPU at 0.4 ms and the CPU nearly idle; `catch-up renders so far` grows by about 1,800 per 2,000 renders while a movie plays.
- **Cause:** Bink's sound driver on `nn::audio`'s renderer polls from the game's rendering thread, several times per movie frame: `RequestUpdateAudioRenderer`, then `GetReleasedWaveBuffer` (Batman: Arkham Asylum 1.0.1, `main+0x950a0`). With the former catch-up renderer in `h_ars_Update`, each poll rendered a catch-up frame, filled the 4-frame queue, and then waited about 5 ms for `render_main` to play a frame, stalling the rendering thread (the same wait dropped Assassin's Creed: Brotherhood's Bink opening to ~10 fps in [PR #1402](https://github.com/seedds/nxnative/pull/1402)). On the Switch an update never renders or waits for a frame.
- **Fix:** `h_ars_Update` no longer renders catch-up frames or waits (`hle_audren.c`), replacing the catch-up workaround with Horizon's `ClearSystemEvent` semantics ([At least one rendered frame between two updates](#at-least-one-rendered-frame-between-two-updates)). Polling updates return immediately with zero audio rendering on the calling thread, and `render_main` drives all 5 ms frames.
- **Found on:** Batman: Arkham Asylum (`0100E870163CA000`, 1.0.1, SDK 14.3.0; [PR #3272](https://github.com/seedds/nxnative/pull/3272), not in the games table): with the full-queue wait removed, the opening movie `101_BATMOBILE_INTRO.BIK` (1280x720, 29.97 fps) went from 16 to 30.0 fps and menus/gameplay held 60 over about 40 minutes of play (retesting the root-cause catch-up removal on Arkham Asylum remains open).
- **Check:** `t_audren_layout --cadence` verifies repeated polling `h_ars_Update` calls neither block nor render. `DM_AUDREN_TRACE=1` logs each of the first 200 updates with the frames rendered since the previous one.

### Burst renders when a device callback releases multiple blocks

- **Symptom:** villager dialogue crackles while music and sound effects play cleanly. On a 44.1 kHz / 256-frame device, `catch-up renders so far` grows by about 277 per 2,000 renders. `DM_AUDREN_TRACE=1` shows two renders between updates or two updates 0.02 ms apart followed by an 11.6 ms gap.
- **Cause:** a CoreAudio callback can return several 5 ms blocks together. `render_main` refilled them back to back, so the game's audio thread could coalesce two renderer event signals or wake twice before it could update between renders.
- **Fix:** after prefill, `render_main` spaces fresh renders at least 4.5 ms apart, using the output's returned blocks to set the number due. The timed wait releases `a->mu` so concurrent `RequestUpdate` calls do not block during pacing.
- **Found on:** [Animal Crossing: New Horizons](../../dm/games/01006F8002326000/README.md). The reporter confirmed clean dialogue on an M4 with 44.1 kHz Bluetooth audio using the original pacing patch. [Issue #2981](https://github.com/seedds/nxnative/issues/2981) · [PR #2983](https://github.com/seedds/nxnative/pull/2983)
- **Check:** `t_audren_layout --cadence` runs a concurrent `RequestUpdate` during the paced wait and checks 2,000 ordered PCM blocks at each of 44.1 kHz / 256 frames and 48 kHz / 512 frames. At 48 kHz / 512 frames, The Binding of Isaac: Rebirth on an M6 had one catch-up in the first 6,000 renders, down from 1,227 on main, with zero underruns in the first 2,000 device callbacks on both builds.

### Late audio producer wakeups despite fast rendering

- **Symptom:** constant static behind otherwise clean sound; the output settles near one queued block, with 12–38 underruns per 2,000 callbacks on speakers and up to 275 on AirPods, although rendering averages about 0.07 ms of each 5 ms block.
- **Cause:** `render_main` had ordinary time-sharing policy. Its guest-thread startup already requests interactive QoS, and AudioOut already signals a host semaphore when a block is released, but neither declares the audio producer's real-time scheduling requirement. Aggregate performance-core usage in the report does not establish the render thread's core placement.
- **Fix:** after output setup, the in-process renderer's worker requests `THREAD_TIME_CONSTRAINT_POLICY` with a 5 ms period/deadline and a requested 1 ms computation budget, and restores standard policy before teardown. A rejected request is logged and playback continues with its existing policy. `DM_AUDREN_RT=0` retains ordinary scheduling for A/B measurements. This is host-bound for every in-process renderer; the separate SDK 1 `audren:u` worker and guest-created audio threads are unchanged. The 4.5 ms fresh-render spacing remains necessary for [burst refills](#burst-renders-when-a-device-callback-releases-multiple-blocks).
- **Found on:** [The Legend of Zelda: Ocarina of Time](../../dm/games/0400486024DEC000/README.md), [issue #3059](https://github.com/seedds/nxnative/issues/3059). Two reporters observed underruns. On an M4, macOS 27.0.1, nichq50 reported four queued blocks and zero underruns across 16,000 callbacks on speakers and AirPods after applying only the policy patch; the attached text file is the patch, not a post-fix log.
- **Check:** `t_audren_layout` sets, reads and resets a real pthread's Mach policy, checks setup/teardown scope, and verifies intact PCM with policy rejection and opt-out. Its cadence fixtures retain 2,000 ordered blocks without simulated underruns at 44.1 kHz / 256 frames and 48 kHz / 512 frames; these do not simulate OS wakeup delay. On an M6 with macOS 27.2.1, XNU raised the requested 1 ms computation to 2.5 ms (half the constraint), consistent with [XNU's policy implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread_policy.c). This is a budget, not CPU time consumed.
- **Live validation:** [Isaac's audio scheduling checks](../../dm/games/01009BC00C38A000/README.md#audio-scheduling-checks) cover real 48 kHz USB output and 44.1 kHz built-in speakers on an M6, including the limits of its CPU/energy samples. [Breath of the Wild's scheduling validation](../../dm/games/01007EF00011E000/README.md#audio-producer-scheduling-validation-2026-11-20) covers SDK 20 and isolates a screenshot-associated frame-time flag with a matched policy-off/on comparison.
- **Open:** iOS device behavior and power impact, and power on the affected M4. The 44.1 kHz crackle reported in [issue #2796](https://github.com/seedds/nxnative/issues/2796#issuecomment-6998635365) was independently reproduced on `Mac mini Speakers` (M6, macOS 27.2.1): at 44.1 kHz (221-frame callbacks periodically releasing two blocks), `79f28b06`'s 4.5 ms pace wait overshot under non-RT scheduling (`DM_AUDREN_RT=0`: 322 underruns in a 5 s matrix, 1,183–1,255 per 2,000 callbacks in Ocarina of Time), while `2edad182` (`DM_AUDREN_RT=1`) reduced both to 0 underruns and 4.0 queued blocks; confirmation on the reporter's MacBook speakers at 44.1 kHz remains open.

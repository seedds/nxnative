# Threads

Guest threads, their synchronization and how the host schedules them. Each entry: symptom, cause, fix, the games it was found on. The [symptom index](../agents/symptoms.md) lists every symptom.

## Thread creation and cores

### Publishing a new thread's scheduler fields

- **Symptom:** TSan reports `thread_main` writing `host_work` while `thr_runnable` reads it during a same-core yield (`t_notify_sched`, issue #411).
- **Cause:** `CreateThread` had already linked the object into `g_all`, but its pthread initialized `host_work`, the Mach port and QoS without the scheduler lock `G`. `StartThread` could make the object runnable before those writes completed.
- **Fix:** initialize those shared fields and read the starting priority under `G`. `CreateThread` publishes the pthread handle and registry link together after `pthread_create` returns, rather than letting that call write a published field. The initial main thread obtains its QoS before publication; the priority getter/setter and deferred QoS updates also hold `G`. Readers keep the same lock, with no added startup wait, timeout or game rule.
- **Check:** the real start/exit and native-wait paths in `t_notify_sched`, both preemption modes, run under TSan with the `thr_runnable` suppression removed. The unsuppressed original reported the startup race. Changing priority before start and consuming the deferred update at a real gate also exposed the unlocked priority setter; the extended test covers that path with `DM_QOS_MAP=1`.
- **Found on:** host unit tests; no particular game's hang was attributed to this race.

### Starting a higher-priority thread on the caller's core

- **Symptom:** a parent returns from `StartThread` before a newly runnable higher-priority child pinned to its core finishes its work (deterministic regression, not attributed to a game failure).
- **Cause:** `StartThread` signalled the child's pthread but did not request the priority handoff already used when waking a waiter. Atmosphère's [`KThread::Run`](https://github.com/Atmosphere-NX/Atmosphere/blob/master/libraries/libmesosphere/source/kern_k_thread.cpp) makes the child runnable; scheduler priority rules then apply. It does not promise that an equal-priority or other-core child has entered its function before the call returns.
- **Fix:** `note_runnable` records the same handoff for starts and wakes (`hle_thread.c`). No unconditional child-entry handshake or timeout.
- **Check:** `make -C dm/host/tests GAME=010038B015560000 preempt` delays the child's host dispatch by 1 ms and 20 ms. With `DM_PREEMPT=0`, both delayed starts failed before the fix. Afterward both `DM_PREEMPT=0` and `1` pass; the broader mode already supplied the handoff before this correction. Equal-priority, other-core, migratable, host-helper, suspended and host-GPU-work children do not hold up the caller.
- **Found on:** the threading audit of [FINAL FANTASY TACTICS](../../dm/games/010038B015560000/README.md#threads); its affected workers are lower priority and initially migratable, so this correction does not remove its local wake cut.

### A thread's arguments in slots its starter reuses after connecting to a service

- **Symptom:** a crash at the very start of a new thread, reading through a null pointer it took from its argument (`main+0x1dc0`, in a boot stub's last thread, about once in a dozen boots), with the starter still in its next few calls.
- **Cause:** the thread reads its arguments from its starter's stack, and the starter reuses those slots a few calls after `StartThread`. [Mario Tennis Fever](../../dm/games/0400D4201C6EA000/README.md)'s boot stub builds them at `main+0x97c`, starts the thread and calls `nn::ro::Initialize`, then builds a string in them at `main+0xa04`. On Horizon `Initialize` connects to ldr:ro, several round trips, so the thread has long read them. The host's `Initialize` returned at once.
- **Fix:** `dm_thread_service_connect` (`hle_thread.c`), called by the host's `ro::Initialize`, waits until the threads started so far have been dispatched into guest code (at most 50 ms), then for a round trip (200 µs). Only `ro::Initialize` calls it so far. **Open:** like [File system calls are service requests](#file-system-calls-are-service-requests), this models a time rather than giving an order: the thread could still be stopped by the Mac between its dispatch and its read.
- **Found on:** [Mario Tennis Fever](../../dm/games/0400D4201C6EA000/README.md).

### Core mask changes move the ideal core into the new mask

- **Symptom:** per-core job queues never drained.
- **Cause:** a `SetThreadCoreMask` that pins a thread to other cores (ideal core −3 = keep) left the ideal core outside the new mask, so `GetCurrentProcessorNumber` reported a core the thread cannot run on.
- **Fix:** the host moves the ideal core into the new mask, as Horizon does, so `GetCurrentProcessorNumber` reports a core the thread can run on.

### Ideal core −2 resolves to the process default core

- **Symptom:** crash indexing a per-core table with a huge offset (index −2).
- **Cause:** threads created with ideal core −2 (*use process default*) were recorded as core −2, and `GetCurrentProcessorNumber` returned −2.
- **Fix:** −2 resolves to the process default core (0), and a negative core is never returned (`hle_thread.c`).
- **Found on:** [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md), in its font engine (`main+0x107dbc0`).

### Thread handle queries hold the scheduler lock

- **Symptom:** ASan reports a heap-use-after-free in `svc_thread_impl` reading `t->id`; TSan reports a race between `GetThreadId` and `CloseHandle`, or between `SetThreadCoreMask` and the target's `GetCurrentProcessorNumber`.
- **Cause:** `GetThreadId` (0x25), `GetThreadCoreMask` (0x0E) and `SetThreadCoreMask` (0x0F) looked up the handle table without `G`, the only thread SVCs that did. `CloseHandle` frees an exited thread under `G` at once when no wait holds it, so a query racing the close read a freed object. `SetThreadCoreMask` also wrote the ideal core in steps that `GetCurrentProcessorNumber` read without a lock.
- **Fix:** the three handle SVCs hold `G` across lookup and read, as the priority SVCs do; on Horizon a query racing a close returns either the value or invalid handle. `SetThreadCoreMask` computes the final core and mask first and stores each once with a relaxed atomic. `GetCurrentProcessorNumber` and `dm_yield_to_core_peers` load them the same way without `G`: games call it often (Pokémon Scarlet about 7,400 times a second), and only the thread's own pair is read.
- **Check:** `t_sync_wait` query-close (a query thread against `CloseHandle` of an exited thread, 200 rounds) and core-mask (`SetThreadCoreMask` against the target's own `GetCurrentProcessorNumber`). Before, ASan found the use-after-free in about one run in three and TSan the race in each; after, ASan and TSan are clean.
- **Found on:** a code audit, with host unit tests; no game failure is known.

### Free thread count (`svcGetInfo` type 24)

- **Symptom:** the main thread waits forever on an event right after `nnMain` starts, with only three or four threads created; `DM_THR=1` shows no `CreateThread` for the thread it waits on.
- **Cause:** Unity's thread start (`main+0x3e1a50`) creates a thread only when `nn::os::GetFreeThreadCount()` is at least 1. That is `svcGetInfo` type 24 (FreeThreadCount, Horizon 11 and later), which the host answered 0 like every type it did not know, so the thread was never asked for. The kernel answers the thread resource limit less the threads alive (Atmosphère `kern_svc_info.cpp`); `pm` gives an application 96 threads (`pm_spec.cpp`, 256 with a boost).
- **Fix:** the host answers 96 less the game's threads that have not exited (`thr_limit_used`; guest threads the host spawns for itself are left out).
- **Found on:** [Monster Train 2](../../dm/games/010051701FB46000/README.md) (Unity 2022.3.54f1 on SDK 18.3.5: `main+0x3e7288` starts a thread and waits for it to signal `main+0x539cf80`). With the fix the game creates 40 threads and reaches its title.
- **Note:** of the 20 games extracted on this machine, only this `main` imports the function.

### A thread closed before it starts ends

- **Symptom:** each `CreateThread` whose handle is closed without `StartThread` leaves a host pthread (1 MB stack) waiting for ever and lowers the free thread count for good.
- **Cause:** `CreateThread` starts the pthread at once, and it waited only for `started`. `CloseHandle` marked the object closed but did not wake it, and the object is reclaimed only once exited, which it never was; [`thr_limit_used`](#free-thread-count-svcgetinfo-type-24) counted it as alive.
- **Fix:** as on Horizon, where closing the last handle of a thread that never ran destroys it: `CloseHandle` of an unstarted thread wakes its pthread, which leaves through `thread_exit` without entering guest code; the object is freed with its slot. A `StartThread` before the close still runs the thread. A wait that already holds the object completes as for an exit.
- **Check:** `t_sync_wait` closed-unstarted: 24 real `CreateThread` / `CloseHandle` pairs return the object count and `thr_limit_used` to where they were (under ASan and TSan); before, they stayed 24 higher.
- **Found on:** a code audit, with host unit tests; no game failure is known.

### Pausing threads and reading their context for garbage collectors

- **Symptom:** in garbage-collected titles (Unity / IL2CPP), live objects freed, with their finalizers releasing native resources.
- **Cause:** the Boehm collector pauses each thread, reads its registers for roots and scans its stack. `SetThreadActivity` (0x32) and `GetThreadContext3` (0x33) were placeholders that only reported success: threads kept running and the context was empty, so roots held only in registers were missed.
- **Fix:** both really pause and report registers (`hle_thread.c`). A thread inside an SVC counts as paused at once, with the gate frame as its context (`thr_svc_enter` / `thr_svc_leave` around every gate SVC; it waits at the SVC exit while paused). A thread in guest code gets SIGUSR2, and the handler saves the ucontext and waits there. A thread in host code is retried every 100 µs. The context is Horizon's 0x320-byte `ThreadContext`.
- **Found on:** Unity / IL2CPP titles in general.

### A pause acknowledged past its resume

- **Symptom:** in an IL2CPP title, about once an hour, a crash on a thread that keeps working while the collector has the world stopped: an indirect call to a non-code address with `0x30` in the top byte (Aokana: NVorbis's `BufferedReadStream.Seek` on FMOD's stream thread).
- **Cause:** `paused` outlived the request it acknowledged. A pause that found the thread inside an SVC set it at once, and the resume did not clear it. The thread then left the SVC by `thr_svc_leave`'s lock-free exit (no pause pending) and ran guest code with the flag still set. The next `SetThreadActivity(pause)` saw the flag, sent no SIGUSR2 and returned with the thread running; `GetThreadContext3` gave an all-zero context. The same happened when the pause was met by `thr_svc_enter` and the resume came before the SVC returned. IL2CPP's liveness pass (`Resources.UnloadUnusedAssets`) marks objects by setting bit 0 of their class word while the world is stopped, and the running thread made a virtual call through a marked word.
- **Fix:** the resume clears `paused`, and a thread that waits for the resume in the signal handler sets it again on every wakeup, as the SVC exit already did (`hle_thread.c`). Clearing alone is not enough: a new pause can come before the woken thread has retaken `G`, SIGUSR2 is blocked inside the handler, and the requester would wait for ever.
- **Check:** `t_pause` pauses a thread again after a resume from inside an SVC (entered from guest code and from host code), and resumes and pauses again while the handler is parked; `t_pause_stress` stops four threads that alternate real `SleepThread` SVCs with guest code about 3,700 times a second, marks a word and checks that none ran. Before, the two SVC cases failed in every run and the stress test found a running thread within the first few dozen stops; after, all pass. With the clearing alone, the parked-handler case hangs.
- **Found on:** Aokana - Four Rhythms Across the Blue (`0100990011866000`, Unity 2018.4.22f1 IL2CPP with FMOD): three of five automated play sessions crashed at `BufferedReadStream.Seek`, each time on FMOD's stream thread, which sleeps in `SleepThread` between buffers and so was mostly paused inside an SVC.

### A pause holds its target until it returns

- **Symptom:** ASan reports a heap-use-after-free in `svc_thread_impl` (`SetThreadActivity`) reading `paused` or waiting on `pcv` of a thread that exited during the pause.
- **Cause:** a pause of a thread in host code loops: it lets go of `G` to send SIGUSR2 and to wait 100 µs. The target could exit and its handle be closed meanwhile; `thread_exit` then freed the object (closed, exited, no wait reference), and the loop read it again.
- **Fix:** the pause takes a reference (`thr_t.refs`, the count synchronization waits already take) before the loop and drops it with `thr_put` after; the last holder of a closed, exited thread frees it.
- **Check:** `t_pause` exit_and_close_during_pause: a pause waits on a thread in host code, its handle is closed and it exits. Before, ASan found the use-after-free; after, the pause returns and the object is freed.
- **Found on:** a code audit, with host unit tests; no game failure is known.

### SVCs leave the stack below sp untouched

- **Symptom:** in a garbage-collected title whose collector stops threads cooperatively, live objects freed while their thread sleeps, and their memory reused: a crash in the collected runtime's code on a pointer made of another object's bytes (Streets of Rage 4: `CRASH sig=11` at `main+0x46a4`, BRUTE's `SyncBlock::GetSyncBlock`, on `0x5b005b00000002`, a string's length 2 and "[["), in about two boots of three, during the first seconds of loading.
- **Cause:** Horizon's kernel never writes a thread's stack during an SVC. The host's SVC gate opened its 800-byte register frame below the guest's sp and ran the SVC's host code there. BRUTE's Boehm-style collector parks a thread entering a blocking call (`main+0x2ff4c80`: setjmp, then the sp, published) and scans that stack from the recorded sp up. In `Thread.Sleep` the SDK path to `svc 0xB` is all tail calls, so the parking function's frame, which holds the caller's x20 (a loop's only reference to an array), is popped but not overwritten. The scan finds the array there on the Switch; the gate's frame overwrote that word (with the saved `fpcr`), the collector freed the array, and another thread's `string[]` took its memory.
- **Fix:** the gate runs on a stack of the thread's own (`entry.S` `dm_gate`, `thread.c` `guest_gate_stack`): each thread's KGATE slot points to a static stub that loads its gate-stack top, and the register frame and the host's SVC code go there. A guest thread's gate stack is the idle rest of its own pthread stack, so it outlives the thread's exit from inside `ExitThread`; the guest main thread, whose guest code runs on its pthread's stack, gets a mapped one. Below the guest's sp only the rewriter's gate block writes, its 16-byte push of x29 / x30. The frame records the block's sp at `regs[99]`, where the thread dump, `GetThreadContext3`'s sp and `guest_caller` read the guest's stack and return address. No rewriter or game change.
- **Found on:** [Streets of Rage 4](../../dm/games/0100EC9010258000/README.md) (MonoGame through Sickhead's BRUTE, SDK 9.3.1): after the change, six boots in six reached the frame loop (before, two in three crashed).

### Same-core wake handoffs

- **Symptom:** crashes around movie changes in the game's own player threads, about one run in two: `SignalEvent` → `MultiWaitImpl::NotifyAndWakeupThread` on a null MultiWait at address 0x20; `WaitAny` walking freed holders; a worker reading a freed object at `main+0x225338`. The other way round, a handoff that waits too widely: a black screen at boot that never loads a texture (`packaged textures: first uploads 0`), or a load that never ends behind an animated loading screen, with the thread dump's `same-core handoffs N, total T ms` larger than the run itself.
- **Cause:** Horizon schedules the highest-priority runnable thread on a core ([Mesosphere's scheduler](https://github.com/Atmosphere-NX/Atmosphere/blob/master/libraries/libmesosphere/source/kern_k_scheduler.cpp)). A lower-priority thread that wakes a higher-priority thread pinned to its core cannot continue until that work blocks. The host's pthreads run in parallel. The earlier approximation also confused host dispatch state with guest readiness: `wake()` cleared the guest wait before the pthread resumed, but `thread_info` could still report that pthread waiting. The caller then continued too soon. Its 5 ms timeout opened the same hole under a longer host delay; the recorded `yield_pending` flag was unused unless the profile enabled checks after every thread SVC. The first unbounded handoff then waited for every runnable higher-priority thread pinned to the caller's core, not only the ones its wake made runnable. The host runs a lower-priority thread beside such threads at all other times, and a core's busy loaders, job workers and pollers are seldom all blocked at the same moment, so a wake could hold its caller for minutes.
- **Fix:** every game's thread SVC honours `yield_pending`. Before returning, it waits for the threads its wakes made runnable that are higher priority and pinned to the caller's core, and for those such a thread makes runnable in turn while the handoff lasts (Dread's dispatcher wakes the worker), until each blocks, sleeps, yields to any thread (`SleepThread(-2)`, which takes it off its core so that lower-priority threads run there), exits, is suspended, or enters explicit host GPU work (`svc_thread` / `dm_yield_to_core_peers` in `hle_thread.c`). A wake records the thread in the waker's current handoff and in those the waker belongs to (`note_runnable`, at most four); blocking ends that (`hand_leave`), and a handoff ends when its caller's thread SVC returns (`hand_epoch`). Guest runnable state is authoritative, including the wake-to-pthread-resume interval; a host dispatch snapshot cannot release the handoff, and there is no timeout that lets unfinished work through. A higher-priority peer the wake did not make runnable does not hold the caller, as at every other point on the host. Host-created helpers and threads that can run on another core are excluded.
- **Check:** `make -C dm/host/tests GAME=010093801237C000 preempt` delays a woken pthread's dispatch by 1 ms and 20 ms through real event, mutex and condition-variable SVCs. The worker's payload and exit must precede the signaller's return. The original implementation failed both delays; changing readiness alone fixed 1 ms but still failed 20 ms. Equal-priority, other-core, migratable, host-helper, suspended and host-GPU-work peers do not block the caller. Its handoff-scope cases add a busy higher-priority peer that nobody woke: the woken worker must still finish first and the signaller must return (the whole-core wait never returns), a worker woken by the woken dispatcher must finish before the signaller returns (fails without the recorded chain), and a woken thread that yields to any thread releases the signaller (never returns without that rule). The native-mutex case wakes a higher-priority pinned peer while holding the mutex it needs; the signal must return at that native block, and the peer finishes after unlock (hangs without the wait annotation).
- **Found on:** [Metroid Dread](../../dm/games/010093801237C000/README.md), whose per-build movie request-ring gates and `core_preempt on` setting are now removed; the whole-core wait on [The Legend of Zelda: Tears of the Kingdom](../../dm/games/0100F2C0115B6000/README.md) ([issue #247](https://github.com/seedds/nxnative/issues/247)) and Donkey Kong Country: Tropical Freeze ([issue #259](https://github.com/seedds/nxnative/issues/259), section 6; no profile here).
- **Native helper joins:** `dm_host_thread_join` also releases the guest core
  during a native helper's lifetime, preserving an enclosing host-work scope.
  [Xenoblade Chronicles 3](../../dm/games/010074F013262000/README.md) exposed an
  audio-unit setup join in `AKEventManager` during a later stall. That sample
  establishes the missing scheduler annotation, but does not establish an
  unbounded Apple audio-unit construction deadlock. The preemption regression
  gates a native helper, verifies that a same-core signaller returns while the
  peer joins it, then checks completion, the join result and nested host work.
- **Scope:** these are cooperative thread-SVC handoffs, not a complete asynchronous guest scheduler. The optional `core_preempt` profile key (`DM_PREEMPT=0` / `1` overrides it) additionally checks already-runnable peers after every thread SVC; it defaults off. Historically that broader policy moved [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md)'s first frame from 0.6 s to 2.9 s by waiting for busy decompression threads. Wake-triggered handoffs apply with either setting.

### A same-core handoff holds only a waker pinned to that core

- **Symptom:** the picture stops for good while sound goes on; the main thread spins in the game's own wait loop (a `sample` of the process shows it in guest code, no SVC), the other guest threads wait, and the job workers it waits for sit in `svc_thread` → `dm_yield_to_core_peers` → `nanosleep`.
- **Cause:** the [same-core handoff](#same-core-wake-handoffs) held the waker until every higher-priority thread its wake made runnable on its core had blocked, whatever the waker's own affinity mask. Batman: Arkham Knight's job workers (priority 43, mask 0x5) finish a job and signal the main thread (priority 29, pinned to core 0), which right away hands them two more jobs and spins on a counter until both are done (`main+0x12f8010`, the counter `main+0x511c0f0`); it never blocks, so the worker that signalled it never came back, and as New Story loaded neither job ran. Horizon's scheduler moves a thread preempted on one core to another core of its mask that runs nothing of higher priority (Mesosphere's `KScheduler` migrates suggested threads), so there the worker goes on on core 2. The host also gave the guest main thread an affinity mask of 7, where Horizon creates every thread, the main thread too, with its ideal core alone (`KThread::Initialize`).
- **Fix:** `dm_yield_to_core_peers` returns at once for a caller whose mask allows another core, and such a waker is not marked for the handoff (`note_runnable`, `hle_thread.c`); the main thread's mask is 1 (core 0). A pinned waker keeps the handoff as before. `make -C dm/host/tests GAME=<id> preempt` has the case (exclusion 7: the signaller's mask is 0x5, and it returns before the woken worker's payload).
- **Found on:** [Batman: Arkham Knight](../../dm/games/0100ACD0163D0000/README.md): every route run froze at New Story (frame 7,800 in one, 11,700 in another); with the fix the opening cutscene plays.

### Lock-free queues published without barriers

- **Symptom:** the picture stops and stays (sound goes on) at random places, about one run in two: every task worker waits on its own event, and the task a waiter waits for counts a subtask that is marked queued but is in no queue (the ring's head equals its tail).
- **Cause:** a game's task ring publishes an item with two plain stores, the item and then the new tail, with no lock on that side, and its pop reads the tail and then the item with no barrier between. ARMv8 lets another core see those stores, and satisfy those loads, out of order; the Switch's Cortex-A57 cores practically never show it, Apple's cores do: a worker sees the new tail with the slot's old null, takes the empty slot (head + 1, the slot cleared) and the item is lost.
- **Fix:** the game's own code is wrong, so a per-build cut (its `patches.py`) puts a `dmb ishst` between the push's two stores and a `dmb ishld` between the pop's two loads, in the place of reloads of the tail and the head whose values the instructions around them take from registers instead.
- **Found on:** [Batman: Arkham Knight](../../dm/games/0100ACD0163D0000/README.md) (push `main+0xc5adbc`, pop `main+0xc5ab30`), by [pull request #340](https://github.com/seedds/nxnative/pull/340), whose runs froze in 2 of 3 before the cuts and in none of 5 after; another engine's queue of the same shape can drop items the same way.

### A host lock held across a same-core handoff

- **Symptom:** the game freezes when a movie starts playing beside the game (a guide movie in a corner of the screen): the last frame stays, the process idles at a few percent of a core, and the thread dump shows a lower-priority job thread `running/not waiting` with its backtrace in the movie player (`ReleaseOutputBufferIndex`), the main thread waiting for it, and the movie's input thread `running/not waiting` too. A `sample` of the process shows the job thread in `md_pump` → `md_event` → `dm_yield_to_core_peers`, and the input thread in `h_movie_SendIn` → `md_pump` waiting for a pthread mutex.
- **Cause:** the host's movie decoder holds its decode lock (`dmu`) across guest code: the "input available" and "output ready" events are signalled with the SDK's `SignalEvent` from inside `md_pump`. The signal woke the movie's higher-priority threads pinned to the signaller's core, so the signaller's [same-core wake handoff](#same-core-wake-handoffs) waited for them to block before its SVC returned. One of them, the input thread, had called `SendInputBufferForDecode` and was waiting for `dmu` in host code. A thread waiting for a host lock still counted as runnable, so the handoff never ended and the lock was never released. On Horizon that lock is guest-visible (the SDK's decoder holds an `nn::os` mutex there), and a thread waiting for it is blocked.
- **Fix:** `dm_host_lock` (`hle_thread.c`) takes a host lock that HLE code holds while it runs guest code. A guest thread that has to wait for it is in a [native HLE wait](#native-hle-waits-release-the-guest-core) (`dm_thread_native_wait`) while it waits: blocked for `thr_runnable`, and out of the handoff that made it runnable, so the handoff does not wait for it. The movie decoder takes `dmu` and the deferred-event lock `g_dfmu` with it (`hle_movie.c`). Releasing `dmu` before signalling instead would let a signal land after `Stop` has returned, on events the game is tearing down (the reason `md_defer_body` signals under its lock).
- **Check:** `make -C dm/host/tests GAME=010093801237C000 preempt`, handoff scope "woken thread waiting for the signaller's host lock": the signaller holds a host lock across its signal and the woken higher-priority worker waits for it with `dm_host_lock`. The signaller must return before the worker finishes; without the native wait around the lock the test never returns.
- **Found on:** [Kirby and the Forgotten Land](../../dm/games/01004D300C5AE000/README.md): the first guide movie ("A Jump", 480×270 VP9) froze the game on the first walk from the beach, every time. The job worker (priority 46) and the movie threads (priority 44) are all pinned to core 0.
- **Found on:** [Xenoblade Chronicles 3](../../dm/games/010074F013262000/README.md), whose 140-second opening VP9 movie stopped at its first output release. A live stack sample identified the input thread in `md_pump` waiting on `dmu`, and the output thread holding it inside `SignalEvent` → `dm_yield_to_core_peers`.

### Simultaneous crashes of several threads

- **Symptom:** several threads crash at once and the dumps interleave, then the process hangs instead of exiting.
- **Cause:** Unity's job threads tend to crash together.
- **Fix:** `crash.c` lets only the first crashing thread print (`crash_gate`); the others stop in `pause()`, and a 15 s alarm ends the process if the dump itself stalls.
- **Found on:** Unity titles in general.

### Watchdog sample output paths are literal arguments

- **Symptom:** `watchdog: sampling failed` and no thread stacks when `DM_WATCH_SAMPLE` contains an apostrophe, such as `/tmp/John's Mac/hang.txt`; shell syntax in the path can also run commands, and long paths are truncated.
- **Cause:** `crash.c` interpolated the path into a single-quoted command in a fixed-size buffer, then called `system()`. An apostrophe ends the shell quote.
- **Fix:** spawn `/usr/bin/sample` directly with the PID, one-second duration, `-f` and the unchanged path as separate arguments. Spawn file actions redirect stdout and stderr to `/dev/null`. Setup, spawn, wait, nonzero exit and signal failures retain the failure log; an interrupted wait resumes. The watchdog still exits with `128 + SIGALRM` after sampling.
- **Found on:** the [static-analysis audit in issue #313](https://github.com/seedds/nxnative/issues/313#issuecomment-6543080671), reproduced with synthetic paths; no game-specific failure is claimed.

## Synchronization and address arbitration

### `SignalToAddress` type 2 with count ≤ 0

- **Symptom:** none seen; found while investigating [Fire Emblem Engage](../../dm/games/0100A6301214E000/README.md)'s demo crash, which it did not change (that was the address-space shortage, [Size-aligned regions exhaust the alias address space](memory.md#size-aligned-regions-exhaust-the-alias-address-space)).
- **Cause:** for `SignalToAddress` type 2 (`SignalAndModifyByWaitingCountIfEqual`) with count ≤ 0 and waiters present, the new value is `value − 2`, not `value − 1` (mesosphere `KAddressArbiter`; Ryujinx and yuzu agree). The host had −1.
- **Fix:** the host writes `value − 2`, the specified behaviour.

### `WaitForAddress` type 3: 64-bit wait if equal

- **Symptom:** a 64-bit wait could return at once or block when it should not (not met in a game).
- **Cause:** Horizon 18 added a 64-bit "wait if equal" arbitration type, which SDK 19 exports as `nn::os::WaitForAddress(const long*, long)`; the host used to fall into its 32-bit "wait if less than" test.
- **Fix:** type 3 compares the 64-bit value (`hle_thread.c`).
- **Found on:** [Pokémon Legends: Z-A](../../dm/games/0100F43008C44000/README.md) (SDK 19.3.11): Z-A does not call it, but the SDK has it.

### Unity's stream buffer handshake loses a wake-up on Apple cores

- **Symptom:** boot stops before or soon after the first frame with the CPU at 0% and every guest thread waiting on a condition variable: the main thread in `nn::os::AcquireSemaphore` after posting a command to `UnityGfxDeviceWorker`, the worker in `AcquireSemaphore` too, one condition wait after it (`wait #` one higher); 3 of 5 Mac runs, at random points.
- **Cause:** a memory-order race in the game's code, not a host bug. Unity 2018.4's `ThreadedStreamBuffer` (the ring buffer every Unity worker thread is fed through) wakes a sleeping side with a Dekker handshake: the reader that finds nothing sets "reader sleeping" with a store-release and loads the write position again before sleeping on its semaphore; a writer stores the write position with a store-release and then checks that flag (and the mirror pair for a writer short of space). The second access of each side is a plain `ldr`, and AArch64 lets a plain load complete before an earlier store-release is visible, so both sides can read the old value and neither signals. The Switch's Cortex-A57 allows it too, but Apple cores hit it within seconds.
- **Fix:** an engine-wide rule turns each of those loads into a load-acquire (`ldar`), which a store-release before it orders after the store: eight sites in four functions, matched by function in any game's main (`dm/tools/engine_patches.py`; until 2026-11-09 a per-build cut in FINAL FANTASY CRYSTAL CHRONICLES 1.0.3's `patches.py`); 14 of 14 runs boot and keep presenting.
- **Found on:** [FINAL FANTASY CRYSTAL CHRONICLES Remastered Edition](../../dm/games/0100CE4010AAC000/README.md) 1.0.0 and 1.0.3 (Unity 2018.4.2f1, SDK 8.2.1: 1.0.0 `main+0x1e425b0` and the stream functions after it, the same sites +0x25380 in 1.0.3). The rule also matches [Raging Loop](../../dm/games/010020400E1C2000/README.md) 1.0.0 (Unity 2018.3.10f1, the same four functions, 2026-11-09); Unity 2017.4 (Cuphead, AI: THE SOMNIUM FILES) has other code there, not reviewed. On the other mains on the drive it matches nothing.
- **Check:** another Unity title that stops this way: look for `stlr` followed by a plain `ldr` of the other word in its `ThreadedStreamBuffer` (the functions around the `AcquireSemaphore` the worker waits in).

### Unity's constant-buffer table changed by two threads at once

- **Symptom:** boot crashes in its first second of shader loading, in a `std::map` copy walking a node pointer that is no pointer (`0x7e600004755`, `0x3`), on the main thread or `UnityGfxDeviceWorker` / `UnityPreload`, under a `vector::insert` of 40-byte entries; 3 of 7 Mac boots, the others run on.
- **Cause:** a race in the engine's code, not a host bug. Unity 2018.4's GfxDevice keeps one table of constant-buffer layouts (`UnityPerDraw`, `UnityPerMaterial`, `VGlobals`, ...), a vector sorted by name hash and size whose entries each hold a map of their members. The shared device changes it with no lock; only the graphics-job devices take the registry's mutex. Two threads use the shared device at once: the main thread queues "set this constant buffer" to the render thread, whose queue publishes each command at once, and then registers the layout itself on the real device (look it up, insert it, fill its member map), while the render thread runs the command (look it up, insert it when missing). Probes showed both inserting the same new layout 0.1 ms apart; an insert shifting the entries copies the maps the other thread is changing. It happens with graphics jobs off too. The Switch's timing hides it.
- **Fix:** a build-bound stub (the rewriter's `STUBS`, [Ori and the Will of the Wisps' `patches.py`](../../dm/games/01008DD013200000/patches.py)) runs Unity's own registry mutex, which is recursive, around every function of the table's API when it works on the shared device: on the main thread the register and the member lookup, on the render thread the per-draw parameter apply, the sets, the value writes and the slot updates, and the inserts, resets and the copy into a graphics-job device (probes of every function by thread found no other users). 10 of 10 boots ran on, with the render thread's CPU time in the same scenes unchanged. The binding is `build`: no other Unity 2018.4 main on the drive shares these functions (Ori and the Blind Forest's build has other code), so no fingerprint rule could be checked.
- **Found on:** [Ori and the Will of the Wisps](../../dm/games/01008DD013200000/README.md#startup) 1.2.1 (Unity 2018.4.24f1).
- **Check:** another Unity 2018 title that crashes this way: probe its constant-buffer insert (the function comparing names with `VGlobals`, `PGlobals`, `UnityPerMaterial`, ...) for the thread and device of each call.

### Trinity's rendezvous loses its release on Apple cores

- **Symptom:** the picture stops and sound goes on, at a random frame (3,000 to 51,300, about 100 s at the quickest), with no `[RED]` line and the GPU idle and caught up. `main` is parked in `nn::os::WaitConditionVariable`, called from the park in Trinity's submit loop. The release flag is set, the state word is 1, the mutex is free, and no `SignalProcessWideKey` was ever issued for that key.
- **Cause:** a memory-order race in the game's code, not a host bug. The completer sets the release flag with a plain `strb`, then reads the main thread's state word with `ldar`, and returns without a wake if it is 2. A load-acquire does not order an earlier plain store, so the flag can stay invisible after that read. Main left the state at 2 when it woke its own participant at the start of the submit, and it runs out of work about when the completer runs. It resets the state to 0, reads the flag as 0, sets the state to 1 and parks; then the flag lands and nothing wakes it. Main's side is ordered (its `stlr` is followed by a spinlock's `ldaxr`), so the completer's pair alone allows this. Armv8 allows it on the Switch's Cortex-A57 too; whether it happens there is not known.
- **Fix:** `patch_nso.py` puts `dmb ish` between the store and the load (`trinity_completer_sites`), in any module with exactly one function of that shape; several change nothing and give a red line. The function has no free word, so `mov x29,sp` gives up its own: backtraces skip this frame, and nothing in it reads x29, since its frame holds only the saved registers. The binding is `engine`: no build ID or fingerprint, so an update that keeps the code keeps the fix. Of the 542 rewritten modules on the game drive, only Scarlet 1.0.0's `main` matches. No host change can do this: TSO allows the same reordering, and a spurious wake only re-checks the event, which stays signalled.
- **Check:** a standalone test of the two instruction sequences on an M4 Pro lost the release in 13,515 of 2,000,000 rounds with main's path about 110 ns longer, in 15 at about 1.6 µs and in none at about 6 µs; with the barrier, in none of 15,000,000. **Open:** this is the code and that test, not a run of the game. Proving it takes long clean runs of a build that froze, past the 94,800 frames an earlier clean run reached.
- **Found on:** [Pokémon Scarlet](../../dm/games/0100A3D008C5C000/README.md#threads) 4.0.0 ([issue #1250](https://github.com/seedds/nxnative/issues/1250)); the completer read in 1.0.0 (`main+0x28f872c`), and 4.0.0's at `main+0x2d0010c` by the issue's addresses. The same park appears in a [Violet 1.0.0 report](https://github.com/seedds/nxnative/issues/271#issuecomment-6549600165). Issue #1250 says Legends: Z-A has the same rendezvous; not checked, and if its completer has another shape it does not match.

### Lock acquire without acquire ordering runs a queue item twice

- **Symptom:** a game that runs on the Switch crashes on the Mac 10 to 60 s into a scene, at a different place each run, with garbage in a list the game just built (Breath of the Wild 1.6.0: `h_nvnBufferGetAddress` called with a row's metadata word as the buffer pointer, `main+0x14ef6e0`; also faults in `main+0x12970dc`, `+0x13615f4`, `+0x1445d48`, `+0x1472470`). A trace of the draw-list builders shows two threads inside the same view at once, running the same job descriptor.
- **Cause:** the game's own spin lock takes the lock with `ldxr w9,[x23]; cbnz w9,<ldxr>; stxr w9,w8,[x23]; cbnz w9,<ldxr>`: an exclusive load with no acquire ordering, and no barrier after the loop. The architecture lets the loads that follow (the queue's count, head and ring) be satisfied before the lock is held; the game ran on the Switch's Cortex-A57 without that showing (why is not known), Apple cores do it, so two workers read the same head, both pop it and both run the job. The unlock is ordered (`dmb ish` before the store), and Nintendo's SDK locks use `ldaxr`. The same loop followed by `dmb ish` is ordered and harmless: Tears of the Kingdom's main has 32 such, Super Mario Bros. Wonder's 33, all fenced. In Breath of the Wild 1.6.0 the job queue pop (`main+0x13a0784`) and submit (`main+0x13a0068`) have the bare form, 412 loops of this shape in the module (counted without the barrier check; 1.9.0 has none of either form); Super Mario 3D All-Stars' main has 7.
- **Fix:** `patch_nso.py` gives every exclusive access ordering ([Exclusive accesses without ordering](#exclusive-accesses-without-ordering)): this `ldxr` becomes an `ldaxr`. It first did so for this loop's shape alone (an exclusive load, a `cbnz` back to it, a store-exclusive of a non-zero value to the same address, a `cbnz` back to the load, no `dmb` after it), which matched none of the 126 distinct modules on the game drives in 2026-11, Breath of the Wild 1.6.0 and Super Mario 3D All-Stars not among them.
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md) 1.6.0 ([issue #251](https://github.com/seedds/nxnative/issues/251)): the same job descriptor ran on two threads 8 us apart.
- **Check:** another game that fails like this: trace which job a worker takes (a branch slot at the job entry, a lock-free per-thread ring); the same descriptor on two threads at once is this bug. A plain `ldar` / `stlr` pair or `dmb` the game left out is not an exclusive access: the rewriter's rule does not reach it.

### Exclusive accesses without ordering

- **Symptom:** a game's lock-free list or job chain uses data another thread wrote just before publishing it, and reads it as it was before (a job chain runs the previous round's callback, and the thread waiting for its signal waits for good); or a lock taken with `ldxr` lets two threads into the same queue item ([Lock acquire without acquire ordering runs a queue item twice](#lock-acquire-without-acquire-ordering-runs-a-queue-item-twice)). Rare, at random points, with no `[RED]` line.
- **Cause:** a memory-order race in the game's code, not a host bug. Armv8's exclusive accesses order nothing unless they carry it: the accesses after an `ldxr` / `ldxp` without acquire may be satisfied before it, and those before a `stxr` / `stxp` without release may be seen after it. A writer that fills a node with plain stores and links it with `ldxp` / `stxp` lets another core see the link first. The games ran on the Switch's Cortex-A57 without that showing; Apple cores do both. A litmus test on an Apple M6 (a plain store, then a 64-bit counter published with each form; the reader takes the counter with `ldar`, then the data): in 100 million rounds the data was stale 12,858 times after `stxr` and 10,961 after `stxp`, never after `stlxr`, `stlxp` or `stlr`, and 1.9% after a plain `str`.
- **Fix:** `patch_nso.py` sets bit 15 of every `ldxr` / `ldxrb` / `ldxrh` / `ldxp` and `stxr` / `stxrb` / `stxrh` / `stxp` in the text (`exclusive_order_sites`; data blocks excluded): the same instruction with acquire (`ldaxr*`, `ldaxp`) or release (`stlxr*`, `stlxp`). The binding is `host`: every module of every game, by encoding alone, with no shape list or address. Ordering only removes outcomes, so no correct program changes behaviour. An atomic increment after four plain stores cost the same either way on the M6 (3.1 to 3.6 ns, and 14 to 17 ns with two threads on one counter). Nintendo's own SDK atomics already use the ordered forms. The words are left out of `<name>.changed.tsv`: a cheat that writes over one runs its own instruction, which nothing else depends on.
- **Found on:** no game in the table is known to fail this way. The S2Arm project reported both kinds on its copy of this rewriter: Need for Speed Hot Pursuit Remastered (job chain nodes published with `stxp`) and 1-2-Switch (a lock taken with `ldxr`). Of the 123 distinct modules on the game drives that the rewriter takes (2026-11), 78 have unordered exclusive accesses, 1,045,422 in all (Donkey Kong Country Returns HD's main has 136,432 stores alone, The Rogue Prince of Persia's 82,642).
- **Check:** `dm/tools/tests/test_exclusive_order.py` (every form found, the ordered forms, CAS, CASP, `ldar` and `stlr` left alone); the rewriter's statistics line counts `exclusive_ordered`. Each of those 123 modules rewritten with and without the rule: every other output identical, and the images differ only in bit 15 of unordered exclusive accesses (1,046,921 words, the extra 1,499 in the patch area's copies of exclusive windows), at the same rewrite time. A/B runs with one host and only the modules swapped: Fire Emblem Engage's attract demo for 200 s (the same scenes, p50 frame time 16.66 and 16.56 ms, no crash or `[RED]` line) and Super Mario Odyssey's regress route (frames 4,500 to 6,300 within 3 pixels of a second run of the old modules).

### Late PhysX task destructor after the unlock

- **Symptom:** a PhysX worker crashes in a task's `removeReference` with a null task manager, right as the game switches to 30 fps (`pc=main+0x10ccf28`, `lr=main+0x13c236c`); on the iPhone and in 2 of 5 Mac runs, in every Mac run with 12 busy loops loading the CPU.
- **Cause:** the game publishes completion before task teardown ends, then reuses the same task. Its main thread rebuilds each world's completion task before `simulate`; the worker sets done, notifies and unlocks inside `run`, then calls `release`, whose destructor clears `mTm`. Another core may rebuild it in between. This is a guest lifetime race: an unlock cannot protect subsequent destructor writes. PhysX's [task contract](https://github.com/NVIDIAGameWorks/PhysX-3.4/blob/master/PxShared/include/task/PxTask.h) places recycling in `release`, after `run`, and its `PxLightCpuTask` destructor clears `mTm`. There is no measured Switch timing guarantee that makes the ordering safe. The game's offsets, affinities and replay evidence are in its note.
- **Fix:** a per-build cut makes that one `release` a `ret` (its `patches.py`); the destructor frees nothing and the step rewrites every field.
- **Check:** `dm/tools/check_thread_cuts.py` replays the original construction, release and `removeReference` instructions with a forced late release: the original faults at the recorded null-manager load; normal release-before-rebuild succeeds; the registered cut preserves the new task. This controlled replay has no host mutex or graphics implementation in its failure path.
- **Found on:** [The Legend of Zelda: Link's Awakening](../../dm/games/01006BB00C6F0000/README.md). How it was found is in [05](../agents/05-debugging.md#racy-crashes-load-trace-gates).

### The thread ID at ThreadLocalRegion+0x110 (SDK 22)

- **Symptom:** `game called nn::diag abort: Result 0, call site sdk+0x153c34` during `main`'s static initialisers, `bt: sdk+0x153c34 sdk+0x137eb4 sdk+0x13dc50 sdk+0x13fa90 sdk+0xa4d64 main+0x134 run_module_inits+0xa8 guest_main+0x15c main+0xfc start+0x1a20`, and no game code on the stack at all.
- **Cause:** those frames are `pthread_mutex_lock+0xa4`, `nn::nlibsdk::heap::TlsHeapCentral::LockMutexSlow`, `nn::nlibsdk::heap::CentralHeap::MakeCache` and `nn::mem::StandardAllocator::Allocate`, called out of `__nnmusl_init_dso`: the first heap lock of the SDK's own allocator. `pthread_mutex_lock` takes a slow path when `InternalCriticalSection::IsLockedByCurrentThread` reports the mutex is the caller's, and that check is `mrs tpidrro_el0; ldr w8,[x8,#0x110]; ldr w9,[x0]; and w9,w9,#0xbfffffff; cmp w8,w9; cset w0,eq` — **the owner is the 32-bit thread id at `ThreadLocalRegion+0x110`**, which SDK 22's `InternalCriticalSection::Enter` (`sdk+0x14b560`) writes from there. The host wrote only +0x1F8 (the thread object pointer), which is what SDK 16's mutexes compared, so +0x110 stayed 0, which is the owner word of an unlocked mutex: every unlocked mutex read as the caller's, and the abort fired on the first one.
- **Fix:** the host stores each thread's kernel ID, the one `svcGetThreadId` answers (`thr_t` id, from 0x51 up, never 0), at `ThreadLocalRegion+0x110` as well as the thread object at +0x1F8: `guest_thread_set_id` in `thread.c`, called by `hle_thread.c` when a guest thread starts and for the main thread before any guest code runs. SDK 22 still wants +0x1F8 for the current thread: `ThreadManager::CreateThread` (`sdk+0x149a78`) and its thread init (`sdk+0x149ff0`) both `str x0,[tpidrro_el0+0x1f8]`.
- **Check:** during the bring-up the thread's ThreadLocalRegion showed +0x110 at 0 with +0x1F8 set; with the fix the allocator's first lock takes the fast path and the boot reaches `nnMain`.
- **Found on:** [Well Dweller](../../dm/games/0100217023F6C000/README.md) (SDK 22.2.0). Any SDK 22+ game that locks a mutex before `nnMain` would hit this; a game whose mutexes are all taken by a thread that already owns them would not notice.

## Yields and spin waits

The yield back-off (`DM_YIELD_BACKOFF`) and the rewriter's spin waits (`patch_nso.py` "Spin waits", `dm_spin_wait` in `hle_thread.c`), with their measurements, are in [development.md](../development.md#power) ("Yield loops", "Spin loops").

### Timer slack in guest sleeps (`sleep_precise`)

- **Symptom:** a 30 Hz game thread runs at 27 Hz, and whatever it paces comes out slow (cutscenes at 36 ms per frame instead of 33.3; gameplay was fine at 60).
- **Cause:** macOS timer slack: `nanosleep` and `mach_wait_until` overshoot by about 10% at any QoS (measured: 33 ms → 36.4 ms, 5 ms → 6.1 ms, 1 ms → 1.26 ms). Dread's sound thread (`main+0xf95b0`) reads a millisecond clock, updates, then sleeps "33 ms minus this round's work", so on the host its period was 36.9 ms. The cutscene loop renders a frame whenever the audio play position, which that thread refreshes, moves (`main+0x119a3d0`; the position is played samples ÷ sample rate of the cutscene's stream), so cutscenes ran at about 27 fps.
- **Fix:** `SleepThread` sleeps three quarters of the remaining time per step until within 20 µs (`sleep_precise` in `hle_thread.c`).
- **Found on:** [Metroid Dread](../../dm/games/010093801237C000/README.md): cutscenes at 33.3 ms, the sound thread at 33.2 ms. [Super Mario Bros. Wonder](../../dm/games/010015100B514000/README.md)'s frame-time p95 also went from 19.7 to 18.4 ms.
- **Note:** timed waits (`WaitSynchronization`, condition variables) still use the host's own timeouts.

### Sleeps under 20 µs take the yield path

- **Symptom:** a guest thread keeps a core at 100% with billions of `SleepThread` calls.
- **Cause:** `sleep_precise` returns at once for anything under 20 µs (its nanosleep would overshoot), so a loop of such sleeps never sleeps.
- **Fix:** sleeps under 20 µs take the yield path and its back-off (plain yields for the first 2 ms of a run, then short sleeps).
- **Found on:** [Super Mario Galaxy](../../dm/games/010099C022B96000/README.md): Hagi polls with `SleepThread(100 ns)` (`main+0x517c`), 1.4 billion calls in 200 s, and the render thread nearly as busy. The two threads went from 199 s and 171 s of CPU per 200 s to 5 s and 19 s per 120 s, at the same frame rate.

### Short timed waits are polls

- **Symptom:** a thread polls at full speed although the power line's yields (if any) show no back-off sleeps; a `sample` of the host shows it in `svc_thread` → `block` → `pthread_cond_wait` with timeouts of nanoseconds, between plain `cthread_yield`s.
- **Cause:** a guest loop that waits with a timeout of a few hundred nanoseconds (a condition variable, an event) until another thread signals. Each wait times out at once, as it would on Horizon, so the loop spins. When it also sleeps under 20 µs between its waits, those sleeps take the yield path ([Sleeps under 20 µs take the yield path](#sleeps-under-20-µs-take-the-yield-path)), but each wait was another SVC between two yields, so every yield began a new run and the back-off never started; a loop of waits alone had no yield at all.
- **Fix:** a wait with a timeout under 20 µs (`WaitProcessWideKeyAtomic`, `WaitSynchronization`, `WaitForAddress`) is a step of the run of yields (`poll_wait_begin` / `poll_wait_end` in `hle_thread.c`): it continues the run when the SVC before it was one of the run's steps and under `SPIN_GAP_NS` (20 µs) of guest work came after it, and once the run has lasted the back-off's start (2 ms) its timeout becomes the back-off's sleep. A lengthened wait still ends at once when it is signalled. A wait that is signalled ends the run. The yields' register test does not apply to waits, since the SDK's own frames hold the time left at the SVC (SDK 3.5.1's `InternalConditionVariableImplByHorizon::TimedWait` keeps it in x21); a loop that works more than 20 µs between its waits starts a new run at each one.
- **Found on:** [Hyrule Warriors: Definitive Edition](../../dm/games/0100AE00096EA000/README.md#power) (KTGL, SDK 3.5.1): its main thread waits for its frame's event with `TimedWaitEvent(30 ns)` and `SleepThread(1 µs)` in turn, its update thread with `TimedWaitEvent(500 ns)` alone. In its first battle at 60 fps on the Mac: CPU 102% → 27% of a core, CPU energy 4.6 → 1.5 W, wakeups 358,000 → 72,000 a second, frame time p95 17.5 → 16.9 ms.
- **Check:** `make -C dm/host/tests GAME=<id> build/t_pollwait && dm/host/tests/build/t_pollwait`: loops of waits alone and of waits between short sleeps (condition variable and `WaitSynchronization`) back off after 2 ms, a loop with 30 µs of work between its waits does not, and a lengthened wait returns at the signal.

### Short sleeps are polls

- **Symptom:** an idle game keeps a performance core awake and the phone warm: the power line shows tens of thousands of wakeups a second, most of the CPU time on performance cores, and a Unity job worker (`Job.Worker 0`) at the top of its yielders, while the frame needs little work.
- **Cause:** a loop that sleeps a few tens of microseconds between looks at a flag. On the Switch such a sleep costs little; here each one is a host sleep and a wakeup of a core, and at that rate the system keeps the thread on a performance core. Sleeps under 20 µs already took the yield path ([Sleeps under 20 µs take the yield path](#sleeps-under-20-µs-take-the-yield-path)), but from 20 µs on the guest's sleep was kept as it was. Unity 6's idle job workers do this: Hollow Knight: Silksong 1.0.30000 `main+0xbd99e0` calls `SleepThread` with a global 25 µs between looks at the job queue, about 25,000 times a second from one worker.
- **Fix:** a sleep from 20 µs up to the back-off's longest sleep (250 µs; `DM_YIELD_BACKOFF` sets both, and `=0` turns this off with the rest of the back-off) is a step of the run of yields, as a short timed wait is (`poll_sleep` in `hle_thread.c`, the rule of [Short timed waits are polls](#short-timed-waits-are-polls)): it continues the run when the SVC before it was one of the run's steps and under `SPIN_GAP_NS` (20 µs) of guest work came after it, and once the run has lasted the back-off's start (2 ms) it sleeps the back-off's length when that is longer (one `nanosleep`). Before that, and for a loop that works more than 20 µs between its sleeps, the guest's own sleep runs as before, so handoffs between working threads keep their timing. Off under the deterministic clock. Silksong's worker loop chooses by a global between this sleep and a yield, which the back-off already covered. Open: such sleeps are not clock waits ([Clock waits sleep to their predicted end](#clock-waits-sleep-to-their-predicted-end)), so a frame limiter made of short sleeps and clock reads would end each wait up to 250 µs late; no game is known to wait that way.
- **Found on:** [Hollow Knight: Silksong](../../dm/games/010013C00E930000/README.md#frame-rate) (Unity 6000.0.50f1). On the Mac (M1 Pro, first room, 60 fps, the old and new hosts in turn): wakeups 29,000 → 8,000 a second, CPU energy 0.46-0.48 → 0.32 W, frame-time p95 within run-to-run noise. On an iPhone Duo (A20 Pro), two play sessions of 5 and 15 minutes: CPU energy (median of the 5 s power lines) 0.63 → 0.09 W, wakeups 37,700 → 14,700 a second, the share on performance cores 86% → about 0%, 60 fps in both; dropped frames 0.17% → 0.25% (not the same route; small hitches of 2 to 6 frames now and then, open).
- **Check:** `make -C dm/host/tests GAME=<id> build/t_pollwait && dm/host/tests/build/t_pollwait`: a loop of 25 µs sleeps backs off at 2 ms and not before, 300 µs sleeps keep their length (but back off with a 500 µs cap once the back-off is longer), no sleep backs off with the back-off off, and 25 µs sleeps with 30 µs of work between them never back off (the first fails without the change).

### Yields that make progress return at once (`thr_yield`)

- **Symptom:** a loading screen sits for a minute with the CPU nearly idle; one thread yields thousands of times a second, every yield a back-off sleep (the power line's top yielder, with as many back-off sleeps).
- **Cause:** the thread was working, not waiting: its loop calls `nn::os::YieldThread` once per item, and the back-off made each yield a 250 µs sleep.
- **Fix:** a yield whose caller's x19–x28 changed since the last one is progress (`thr_yield` in `hle_thread.c`; the SDK reaches the SVC through tail branches, so those registers are the loop's own): it returns at once with no host call, and the run starts again. Polls keep those registers (Three Houses' limiter, Galaxy 2's Hagi sleep poll at `main+0x11ec`); counters move them.
- **Found on:** [Animal Crossing: New Horizons](../../dm/games/01006F8002326000/README.md): a black screen with the plane icon for 77 s after the opening movie, `SaveProc` at about 2,600 yields a second, its grid walks over the new island (`main+0x157d020`) yielding once per cell; also about 40 s of the same at boot. The island now shows about 10 s after the movie, as with `DM_YIELD_BACKOFF=0`. Polls that keep their registers: [Fire Emblem: Three Houses](../../dm/games/010055D009F78000/README.md), [Super Mario Galaxy 2](../../dm/games/0100FD8022DAA000/README.md).
- **Check:** check such a change on [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md) outdoors: its `PlacementMgr` and `RadarMgr` turned out to yield per item too, and a `sched_yield` on each of their 200,000 yields a second cost a third of a core more than the back-off had; with no host call, CPU energy fell instead (numbers in [development.md](../development.md) "Yield loops").
- **Note:** a temporary log of which of x19–x28 move at each yield, per thread, is what told the two kinds apart.

### A wait at two yields is not progress

- **Symptom:** one guest thread keeps a host core at 100% with about a billion yields a minute (`SVC 0xb` in `DM_HLECOUNT`), none of them a back-off sleep, while the game itself plays normally.
- **Cause:** the loop waits at two yields whose callee-saved registers differ, so each yield looked as if the loop had moved on since the last one, and returned at once. Hades' `NetworkPollThread` (`main+0x27aaa0`) yields between its passes with w23 = 0, and in each pass yields while the nifm request is on hold with w23 = 2,000, its retry count.
- **Fix:** a yield is progress only when x19–x28 differ from both of the last two yields (`thr_yield` in `hle_thread.c`): a loop that comes back to the registers of the yield before last is waiting, and the run goes on to the back-off. Counters and cursors (Animal Crossing's grid walk, Breath of the Wild's batches) never come back, so they still return at once.
- **Found on:** [Hades](../../dm/games/0100535012974000/README.md), with [Network requests stay on hold before they settle](services.md#network-requests-stay-on-hold-before-they-settle). Neither change alone was enough: in 60 s of its smoke route the process used 117 s of CPU on `main`, 119 s with only the nifm change (627 million submits, a pass now ended at the second query) and 122 s with only this one (1.38 billion queries, the 50 ms hold still timed out). With both it used 62 s, as with the poll thread's yields turned into sleeps: 216,000 yields, most of them back-off sleeps.
- **Check:** a temporary per-thread count of the yields only this rule keeps in a run, and of the back-off sleeps those runs then took, on boots and play of other games: Tears of the Kingdom's main thread and ModuleSystem workers about 0.1% of their yields (761 of 926,116 on the main thread in 120 s) and no back-off sleep; Breath of the Wild outdoors at most 7 per thread in 150 s, no back-off sleep; Three Houses up to 95 per thread, Donkey Kong Country: Tropical Freeze about 1,000 on the main thread, neither with a back-off sleep from them; Kirby at most 1; Celeste, BALL x PIT, Bayonetta and Ghost Trick none. Their frame rates matched `main` in runs that kept the window's focus (a run whose window loses focus to another app drops to about 30 fps, on `main` as well).

### Clock waits sleep to their predicted end

- **Symptom:** a game's frame limiter that yields and reads the clock holds 59.4–59.5 fps instead of 60 (frame time p50 about 16.8 ms instead of 16.68; the HUD rounds it to 60), and uses more CPU energy than the same game sleeping: the power line's top yielder is the main thread with thousands of yields a frame.
- **Cause:** the yield back-off ([development.md](../development.md#power), "Yield loops") lets a run of yields spin for its first 2 ms, which protects handoffs between threads, and then sleeps an eighth of the wait so far, up to 250 µs. A limiter waits for a time, not for another thread, so the spin is pure cost (about 9,700 plain yields a frame on a performance core in Three Houses), and since the back-off cannot know the deadline, each wait ends up to 250 µs late, plus a quarter for `nanosleep`'s slack ([Timer slack in guest sleeps](#timer-slack-in-guest-sleeps-sleep_precise)). A shorter cap trades one for the other: 100 µs gave 16.73 ms at 0.6–1.0 W.
- **Fix:** every guest read of the system counter counts on its thread (`dm_clock_reads`, `guest_clock_read_wait` in `hle_os.c`, through the `cntpct` gate and `svc GetSystemTick`). A run of yields whose passes read the clock is a clock wait (`thr_yield`, `clock_wait` in `hle_thread.c`): it backs off from its start, with no 2 ms of plain yields. A clock wait that ends at a steady period also knows its deadline, its last end plus the period: the loop followed (one per thread, by its x19–x28) learns the period from the times its waits end, and after three periods in a row within 250 µs of each other a wait sleeps on time (`sleep_precise`) to 150 µs before the predicted end, then polls with plain yields. A wait that ends at the first poll after such a sleep may have ended late: the first time, the period is taken 300 µs shorter (one learned from waits the back-off ended carries their lateness); the second time in a row, the period changed (a game going from 30 to 60) and is learned again, so such a change costs two late waits. A prediction that comes early (the period got longer) costs only polls and back-off sleeps. `DM_YIELD_CLOCK=1` keeps the back-off from the start without the predicted sleep, `=0` makes clock waits ordinary yields; the power line's top yielders show `clock waits N, M of them slept to a predicted end`.
- **Found on:** [Fire Emblem: Three Houses](../../dm/games/010055D009F78000/README.md#frame-rate), whose frame limiter (`main+0x5be430`) had a per-build cut that made it sleep; the cut is removed. On the Mac in a window, 100 s from the boot to the title: without the cut, the old back-off 59.4–59.5 fps, frame p50 16.80–16.85 ms, 0.28–0.79 W of CPU; backing off from the start alone 59.4–59.5 fps, 0.19–0.35 W; with the predicted sleep 59.8–60.0 fps, 16.67–16.81 ms in most windows (up to 17.06), 0.09–0.16 W, about 1,330 wakeups a second, 294–300 of every 300 waits slept to their predicted end. With the cut it was 59.9 fps, 16.68 ms, 0.11–0.49 W.
- **Check:** `make -C dm/host/tests GAME=<id> build/t_clockwait && dm/host/tests/build/t_clockwait`, on a test clock that only sleeps and yields advance: a yield loop that reads the clock backs off from its start and one that does not after 2 ms; a limiter at a steady period sleeps to its predicted end and ends within a few yields of its deadline; a longer period never makes a wait later than the back-off's own lateness; a shorter period costs two late waits, then the waits end on time again.

## Events and notifications

### Synchronization waits retain objects and completed notifications

- **Symptom:** a wait times out after its event was signaled and cleared; closing and reusing a handle redirects a blocked wait to an unrelated event, or a wait on an exiting thread never completes. A signaled first entry also hides an invalid later handle. `ResetSignal` on a thread handle returns `0xfa01` (invalid state) instead of `0xe401` (invalid handle).
- **Cause:** `WaitSynchronization` kept the caller's handle array and looked up its numbers again after waking. It neither retained the original objects nor recorded which signal completed the wait. Event and thread destruction followed handle ownership alone. The event SVCs treated a thread handle given to `ResetSignal` as a resettable object in the wrong state; the kernel accepts only a readable event (or a process) there, and invalid state means a readable event that is already clear.
- **Fix:** as Horizon's `KSynchronizationObject::Wait`: reject more than 64 handles (`0xee01`), copy the handles and resolve every one (any invalid handle, the current-thread pseudo-handle and an event's write end included, is `0xe401`), and retain each event or thread until the wait returns, in the thread's own record (`thr_t.wobjs`, as the kernel's per-thread sync object buffer). Notification records the first matching index under `G`; later clearing or closing cannot undo completion. Thread reclamation waits for outstanding wait references. Ready objects, then a zero-time poll, precede a pending cancellation, and `CancelSynchronization` completes a blocked wait at once or else marks the next one. `ResetSignal` returns invalid handle for anything but a readable event. The short-poll back-off and deterministic-clock waits are unchanged.
- **Found on:** synthetic host regressions in [`t_sync_wait.c`](../../dm/host/tests/t_sync_wait.c); six of its seven groups fail on the host before the fix (all but cancel-release). No game failure is known.

### Service-event producers follow the binding lifetime

- **Symptom:** a host helper thread aborts when signalling a destroyed `SystemEvent`; repeated `vi::GetDisplayVsyncEvent` calls double the event's tick rate. Rapid replacement can abort with `too many vsync events`, or a retired vsync worker can signal another service's event at reused storage.
- **Cause:** lazy binding calls the SDK's `CreateSystemEvent`, which requires a guest thread. Checking only the guest address also mistakes a replacement binding for the original event, even if its kernel handle number is checked: both can be reused before the next tick. An eight-slot worker table counts destroyed events until their workers next run.
- **Fix:** `hle_signal_system_event` retains lazy binding on guest threads; host threads skip an unbound event and log once. Each service-event binding gets a monotonically increasing identity. `hle_signal_system_event_binding` matches that identity and signals under the same lock as `CloseHandle`, so a stale producer cannot signal a replacement. The vi registry keeps one worker per binding identity in an allocated list; a worker whose binding closed removes only its own entry and exits. A new vi binding at reused storage gets its own worker, while repeated requests for a live binding share the existing one.
- **Found on:** synthetic host regression cases in [`t_system_event.c`](../../dm/host/tests/t_system_event.c), using real binding and event SVCs with worker startup held until after destruction and handle reuse; no game failure is claimed.
- **Check:** duplicate vi registration, nine rapid replacements before the first tick, storage and handle reuse by a different service, vi rebinding at reused storage, host signalling after destruction, and guest lazy binding. The capacity and unrelated-service cases fail on the original PR #202 and pass with lifetime identities and the allocated registry.

### One auto-clear event shared by a pool's workers

- **Symptom:** the main thread waits forever on a job's done event at boot while every worker sleeps, two of them on one event (`main+0x1426c` waiting on `Job::m_doneEvent`); 4 of 6 Mac runs.
- **Cause:** the engine puts a job in worker k's private queue but signals one shared SDK auto-clear event. Its condition wake chooses by priority, then FIFO; it has no target-worker identity. The wrong worker checks only its own queue and sleeps again. This is a guest assumption about waiter order, exposed by host timing. Host `pick` / `wseq` agrees with Atmosphère's [condition-tree comparator](https://github.com/Atmosphere-NX/Atmosphere/blob/master/libraries/libmesosphere/include/mesosphere/kern_k_thread.hpp) and [`Signal`](https://github.com/Atmosphere-NX/Atmosphere/blob/master/libraries/libmesosphere/source/kern_k_condition_variable.cpp), including the historic 0.19.0 implementation. This describes the SDK's condition-based auto-clear event; kernel readable events instead notify all synchronization waiters. Game offsets and observations belong in its note.
- **Fix:** the game's own wait wrapper (`main+0x12500`, `{event, pending}`) signals the event once more when it takes a nonzero pending word after waking, and nothing set it: a build cut makes the signal set it first (its `patches.py`), so a worker woken in another's place passes the wake on; 6 of 6 runs boot.
- **Found on:** [FINAL FANTASY TACTICS - The Ivalice Chronicles](../../dm/games/010038B015560000/README.md).
- **Check:** `t_preempt` checks priority/FIFO selection and mutex reacquisition through real condition SVCs. `dm/tools/check_thread_cuts.py` runs the game's actual signal and wait wrappers with both worker arrival orders: only the original wrong-worker cases strand a job. The game's note records the Mac boot comparison with the corrected host.
- **Note:** an unconditional `StartThread` child-entry handshake changed the timing but did not eliminate the hang and is not a kernel guarantee. The separate [same-core start handoff](#starting-a-higher-priority-thread-on-the-callers-core) applies only when priority and affinity require it.

### The oe notification event and its queue

- **Symptom:** abort in `os::WaitSystemEvent` under `oe::PopNotificationMessage` (The Legend of Zelda: Link's Awakening); one guest thread at about 1000 ms/s on the iPhone only, the phone hot, CPU energy 5–7 W (Monster Hunter Rise's `MessageSuperviseThread`, priority 32, in the `[nvn] threads` lines).
- **Cause:** the host keeps the notifications in a queue of its own. The blocking pop waits on the system event `oe::Initialize` would have created, and the host's `Initialize` is a no-op. Monster Hunter Rise's thread waits on `oe::GetNotificationMessageEvent()` with `os::WaitAny`, which does not clear an event, then pops notifications until the queue is empty. The host only ever signalled its notification event, so after the first focus change (iOS changes focus at launch; the Mac does not) it stayed set and the loop never blocked again.
- **Fix:** the host now implements the blocking pop on its notification queue (a condition variable, then the `TryPop` path), and the event follows the queue as the am service's does: set while a notification is queued, cleared when the last one is popped (`hle_oe.c` `mq_ev_sync`, `hle_clear_system_event`).
- **Found on:** [The Legend of Zelda: Link's Awakening](../../dm/games/01006BB00C6F0000/README.md) (SDK 8.2.0, the blocking pop); [Monster Hunter Rise](../../dm/games/0100B04011742000/README.md) (the event).
- **Check:** Mac repro `DM_OE_SCRIPT=focus=2@5,focus=1@6` (the script also starts at the game's first `GetNotificationMessageEvent`, since such a game pops only once the event fires): before 995 ms/s, CPU 109%, 6.97 W; after, the thread is idle and CPU energy is 0.05 W.

### Native HLE waits release the guest core

- **Symptom:** Paper Mario: The Thousand-Year Door 1.0.1 stays black before its first frame. The main thread stops at `main+0x32796c`, after starting `SYS_Notification`; the priority-28 notifier is in `oe::PopNotificationMessage`, while the priority-44 main thread waits for its same-core wake handoff.
- **Cause:** the notification HLE blocks in a host `pthread_cond_wait`, outside the guest kernel's wait bookkeeping. The notifier remains classified as runnable and retains its inherited handoff, so its lower-priority waker cannot continue even though the notifier has no work.
- **Fix:** `dm_thread_native_wait` marks the blocked native-wait interval under the scheduler lock and drops the inherited handoff. `PopNotificationMessage` enters that state while holding the queue mutex, waits, and restores runnable state after reacquiring the mutex. Ordinary native execution is still runnable.
- **Found on:** [Paper Mario: The Thousand-Year Door](../../dm/games/0100ECD018EBE000/README.md#startup).
- **Check:** the original PR #291 reproducer on upstream `1402ded2` blocks until its watchdog exits with code 99. `make -C dm/host/tests GAME=0100ECD018EBE000 notify-scheduler` now uses real `CreateThread`, `StartThread`, wait-for-exit and close SVCs; only the assembly transition to a guest stack is replaced by a C test entry. The original notification HLE strands `StartThread` until the watchdog exits with code 99. The fixed HLE passes 100 runs in each scheduling mode, including a wake without a queued message, runnable-state restoration and delivery of focus notification 15. The full host test suite (`make -C dm/host/tests GAME=0100ECD018EBE000 run`) also passes with CoreAudio access. The game's note records its separate Mac startup comparison and iPhone report.

### File system calls are service requests

- **Symptom:** every save slot shows NO DATA and `Play Time 0 mins`, right after "Save was successful" and with a save imported from elsewhere, though the files are there and a commit is logged. Reopening the save screen reads no save file (`DM_FS=1`). The terms of service come back at every boot, since the system data save is refused too.
- **Cause:** a game's worker that sets a flag after `StartThread` returns and clears it as its last act relies on Horizon's order. Digimon Story Cyber Sleuth's save manager (`main+0x16cdf0` and its neighbours) sets its busy byte after the thread call, and its priority-38 worker on the priority-44 main thread's core clears it at its end. On Horizon the worker preempts main, its first file system call blocks in `svcSendSyncRequest` until fsp-srv replies, and main sets the byte meanwhile. The host answered in the worker's own thread, and the [same-core handoff](#same-core-wake-handoffs) held main until the worker exited, so main's store came last, on every run, and the byte stayed set. Later starters refused to run, and their callers, which ignore that, read the last status left behind: "no file", shown as NO DATA.
- **Fix:** the file system hooks call `dm_thread_service_request` first (`hle_fs.c`, `hle_thread.c`). The caller leaves any handoff it belongs to, as it would by blocking. Leaving is not enough for a started thread, whose remaining calls can end in microseconds, before its starter's 50 µs poll sees it. So the first request of a thread whose `StartThread` holds its caller also waits until that caller is back in guest code, then 200 µs for a service round trip. The wait is bounded at 5 ms, since the starter may be waiting for a peer that needs this thread.
- **Note:** on Horizon too this order comes from the time a request takes, not from a guarantee; the 200 µs is a model of that, so a starter stopped by the host for longer than that at this exact point would lose the race as before. Only file system calls are service requests here so far; another HLE that stands for a blocking request would call the same function when a game shows it needs that. Waking (not starting) a thread gets the release but no wait, so a reading thread woken for every request does not pay 200 µs each time.
- **Check:** `make -C dm/host/tests GAME=<id> preempt` (`service_request_start`): with no request the starter is held to the worker's end and the flag stays set, as the game saw it; with one or two, in both scheduling modes, the worker sees the flag and clears it. On the game: a save, reopening the screen, loading and saving again, twelve overwrites in a row, a restart.
- **Found on:** [Digimon Story Cyber Sleuth: Complete Edition](../../dm/games/010014E00DB56000/README.md#saves) ([issue #769](https://github.com/seedds/nxnative/issues/769)).

### Queue polls with exclusive retries and no clrex

- **Symptom:** Breath of the Wild 1.6.0 shows frames of 100–600 ms every few seconds while the GPU's work stays at 8–17 ms; in every stall the main thread and both workers are in one job queue poll (`main+0x12c0e48`). It is the starvation 1.9.0 had in the same poll ([CPU hitches](../../dm/games/01007EF00011E000/README.md#cpu)): the workers take and release the queue's lock at full speed, and the main thread, whose item they wait for, loses nearly every exclusive store to them.
- **Cause:** the spin-wait rule's lock case (`spin_lock` in `patch_nso.py`) knew the lock only as 1.9.0's compiler writes it: a failed test clears the reservation (`clrex`) and branches back to the exclusive load. 1.6.0's compiler branches straight back (`ldxr w; cbnz w,<the load>; stxr; cbnz`), and its release retries its compare the same way. Neither was taken as a lock, so the poll was no spin wait; only the acquire's own retry loop, two instructions, passed a spin gate.
- **Fix:** `spin_lock` takes both forms; the next exclusive load replaces the reservation a failed test leaves, so `clrex` changes nothing there. A lock sequence at a loop head is one node of the poll it heads; when it heads none, the head is the sequence's own retry loop, a spin wait as before. That matters beyond this poll: Breath of the Wild 1.6.0 has 412 locks of this form, Tears of the Kingdom's main 32, Super Mario Bros. Wonder's 33 ([Lock acquire without acquire ordering runs a queue item twice](#lock-acquire-without-acquire-ordering-runs-a-queue-item-twice)), Mario vs. Donkey Kong's main 4 (test-and-test-and-set, `main+0x470fa8`); the rule's first version took the gates of those waits away. No game addresses are in the rule.
- **Found on:** [The Legend of Zelda: Breath of the Wild](../../dm/games/01007EF00011E000/README.md#cpu) 1.6.0 ([PR #2118](https://github.com/seedds/nxnative/pull/2118)), with the measurements.
- **Check:** `dm/tools/tests/test_spin_waits.py`: the poll in both forms, a lock that heads no poll and one that heads its poll, and polls that must not count (a path without the release, a release of another address, a failed store retried elsewhere). On a module, `DM_SPIN_LIST=1` lists the poll's head with its back-edge.
